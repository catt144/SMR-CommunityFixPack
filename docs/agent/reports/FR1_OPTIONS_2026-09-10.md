### 2.2 · Source overlays: direct mounts blocked, helper route remains

**SOURCE:** the sandbox blacklist (`G/CommonLua/Modding/Mod.lua:1280–1438`)
removes direct `MountFolder`, `MountPack`, asynchronous mounts, `io`, unrestricted
`os`, `load` and `require`; `:1620` exposes only `os.time`. Ordinary mod assets
mount in their mod namespace (`:866–883,1771`), so dropping a `Shaders/` folder
into a mod does not by itself shadow the engine’s root shader mount.

**SOURCE:** global **`DlcMountFolder(dlc, folder)`** remains a separate route:
`G/CommonLua/Dlc.lua:379–385` tests `dlc.folder .. "/" .. folder` and calls
the engine’s `MountFolder(folder, path, "seethrough")` in its own environment.
It is not in the examined blacklists. **INFERRED route, [NEVER RUN]:**
`DlcMountFolder({folder=CurrentModPath}, "Shaders")` could overlay source via
that shipped helper. This does not require exposing native mounts to mod Lua.
Actual visibility, ordering, packed-mod behavior and source-cache invalidation
remain unmeasured. Neither `ReloadShaders()`’s presence in developer tooling nor
`DlcReloadShaders` proves a retail mod will rebuild the intended DXIL.

**SOURCE / INFERRED cost:** `S/Reflections.fx:440–513` consumes a counter-driven
ray-work queue; `:515` starts the separate `REFLECT_FULL` branch. Blindly putting
the full-path body under the rays define can mismatch native dispatch counts.
A semantics-preserving control-flow rewrite or a correctly gated diagnostic
replacement needs both an ABI check and rendering tests. A no-op shader can
isolate a crash but produces no reflections and is not a final fix.

### 2.3 · Persistence and Proton detection

**SOURCE:** `G/CommonLua/Core/GlobalStorageTables.lua:270–328` reads
`AppData/LocalStorage.lua` through `LuaValueEnv()` and assigns
`EngineOptions=LocalStorage.Options`. This is serialized data, not a general
executable `.ini`. `:337–356` provides SaveLocalStorage/SaveEngineOptions.
`Core/options.lua:373–403` applies known option defaults and their `OptionsData`
`hr` mappings; an arbitrary saved `SSRTraceHiZ` or `hr.Foo` key has no startup
reader. Per-mod persistence exists (`Mod.lua:1487–1514`), but a later mod read
cannot move execution before `InitRenderEngine` on the next boot.

**SOURCE / conditional route:** known engine startup fields do have an early
reader. `Core/options.lua:34–59` reads saved `GraphicsApi`/adapter selection;
`:10–15,443–452` enumerates supported APIs and hides a one-choice UI. A mod could
persist a **supported** alternative. **UNKNOWN:** whether retail exposes any
alternative to D3D12; inventing `d3d11`/`vulkan` is not a route check.

**SOURCE:** `Core/autorun.lua:125–144` gates Lua-side `-cfg`, `-run` and `-map`
handling to non-goldmaster builds; developer `user.lua` is also conditional.
A native generic `-hr.Name=value` parser is **UNVERIFIED**. The probe’s custom
launch marker is parsed by its own Lua using GetAppCmdLine, which the game’s
mod code already uses (`Mod.lua:46`); it is not an engine startup switch.

**MEASURED bench / SOURCE:** Proton presents the Windows build, so
`Platform.linux` does not work as a gate (B; vanillahunt README §2b).
The binary has `wine_get_version` at `0xfc8b78` and the `Proton/Wine: %s` log
format at `0xfc8cc8`, but no Lua-accessible equivalent was found.
Hardware/OS getters appear in `G/CommonLua/Libs/Paradox/PdxSDK.lua:639–655`;
adapter lookup is `Core/options.lua:59,80`. Adapter names, Windows-version
strings, `steamuser` paths and driver strings are **heuristics**, not a proved
exclusive detector. No verified sandbox route to environment variables,
registry or Wine native calls was found.

**INFERRED distribution design:** a separate explicitly enabled PC workaround
or a deliberate custom launch marker can fail closed without automatic Proton
detection. An ungated global `hr` change would also affect Windows; `Platform.pc`
can exclude consoles but cannot distinguish Windows from Proton. Ordinary
gameplay fixes should not acquire silent global renderer changes.
