- **Why this was derived.** The `split-optins` verification matrix (chain prompt
  4) needs three different MOD SETS, and Mod-Manager driving is DESCOPED for the
  rig (`WORKFLOW.md`, capability envelope: *"the enable click stays human"*). A
  Mod-Manager matrix therefore costs the owner three separate visits. The
  question was whether the folder can be taken away instead — and whether doing
  so costs them their tick.

- **The route, re-derived from Src 2026-08-12** (`CommonLua/Classes/Mod.lua`,
  installed at `A:\SteamLibrary\steamapps\common\Project Spark\ModTools\Src`):

  ```
  GetModsToLoad()          :1992   list = table.icopy(AccountStorage.LoadMods)
                           :1996-2012  the ONLY table.remove is for BLACKLISTED
                                       mods, and its TurnModOff is guarded by
                                       `and Mods[modId]` — a missing mod cannot
                                       reach it
                           :2016-2027  list = table.ifilter(...): an id with no
                                       Mods[id] is dropped from the LOCAL list
                                       with ModMessage("Couldn't find mod %s
                                       from your account storage.")
  ModMessage()             :115-125  appends to ModMessageLog and returns.
                                     ⛔ NOT a modal — nothing blocks.
  ```

- ⛔ **The one routine that WOULD cost the owner their tick, and why it never
  runs.** `WaitErrorLoadingMods` (`:2032-2050`) walks the account's enabled list,
  and for every id that did not make it into `GetModsToLoad()` it calls
  `TurnModOff(mod_id, "updatePreset")`, then `SaveAccountStorage(500)`, then a
  blocking `WaitMessage`. That is exactly the outcome to avoid — and it is
  reached from **one** place, `OnMsg.PreGameMenuOpen` (`:2230-2241`).
  `Msg("PreGameMenuOpen")` is raised in **exactly one place in the whole Src** —
  `CommonLua/UI/MainMenu.lua:15`, inside `OpenPreGameMainMenu` — and Surviving
  Mars Relaunched **replaces that function** at `Lua/init.lua:1` with a body that
  opens `PGMainMenu` and never raises the Msg. ⇒ **`OnMsg.PreGameMenuOpen` never
  fires in this game and `WaitErrorLoadingMods` is dead code.**

- ⇒ **Consequence, and it is the one that matters operationally:** taking a
  junction out of `%AppData%\Surviving Mars Relaunched\Mods\` puts the process in
  D13's **state (4), a real uninstall** — the mod's def is not loaded, its code
  never runs, its global is absent — while `AccountStorage.LoadMods` keeps the id
  and the owner's tick. Putting the junction back restores the mod on the next
  launch with no human action. It is strictly stronger than the state (3)
  Mod-Manager disable (which still loads the mod DEF) and it is the configuration
  a player who never installed the other mod actually has.

- ⛔⛔ **A LIMIT, MEASURED 2026-08-14 (the combined sitting), ON THE ONE CLAUSE
  ABOVE THAT IS OPERATIONAL RATHER THAN STRUCTURAL: "Putting the junction back
  restores the mod on the next launch with no human action" DID NOT HOLD.** The
  rescue junction was pulled at the `d13-rescue` close-out and restored by this
  sitting between its moment A and moment B. On the next launch the mod's **def
  loaded** (`Loaded mod def Save Rescue (id SMR_CommunitySaveRescue, v0.01-000)`)
  but its **code did not run**: `Loaded mod items for:` listed the Test Kit alone
  and `rawget(_G, "SMRSaveRescue")` was `nil`. The config gate stopped the run
  before it measured anything; the repair was **one owner Mod-Manager tick plus a
  restart**, i.e. exactly the cost this fact exists to avoid.
  (Log: `archive/cs_b1void_Mars.exe-20260814-12.40.27.log`; the successful retry
  after the tick is `archive/cs_b1_*`, gate `save-rescue :: 1/1 active`.)
  * ⚠️ **TWO CANDIDATE CAUSES, AND THIS LEG DID NOT DISTINGUISH THEM.** (a) The
    owner opened the MOD MANAGER while the folder was absent — ⛔ **something the
    2026-08-13 matrix never did**; its nine launches round-tripped the junction
    with nobody ever entering that screen, so the account write this fact reasons
    about (`GetModsToLoad` filtering a local list, never `SaveAccountStorage`) was
    never tested against a screen that saves account storage on exit. (b) The tick
    was already lost at the 08-13 close-out pull and nothing re-checked it between
    then and 08-14. `account.dat` is compressed, so a direct read settles neither
    (a raw scan finds none of the four ids, including the Test Kit that
    demonstrably IS enabled — the check proves nothing in either direction).
  * ⇒ **WHAT BINDS NOW.** The structural half of this fact stands and is
    unaffected: a missing folder is filtered non-modally, `WaitErrorLoadingMods` is
    dead code, and a pull IS D13 state (4). ⛔ **What may no longer be assumed is
    that the mod comes back ENABLED.** Any leg that restores a junction must
    verify the mod's registry in-game before measuring — the config gate is not
    optional insurance here, it is the thing that caught this — and must budget an
    owner tick as a possible cost whenever a Mod-Manager visit has happened
    anywhere in the round trip.
  * **The cheap experiment that would settle it**, for whoever needs this next:
    pull a junction, restore it, launch WITHOUT anyone opening the Mod Manager in
    between, and read the registry. Green ⇒ cause (a) and this fact gains a
    "never open the Mod Manager mid-round-trip" clause. Red ⇒ cause (b) and the
    original claim was over-general from the start.

- ⚠️ **Two clauses this fact does NOT cover.** (1) `WaitWarnAboutSkippedMods`
  IS live (called from the landing-spot and challenge screens and
  `Lua/Tutorial.lua:56`) and CAN block on a modal — but it only ever names
  DECLARED DEPENDENCIES, and neither the fix pack, the opt-in mod nor the Test
  Kit declares one, so it has nothing to say about this configuration. An
  unattended leg that starts a NEW GAME through the landing screen must still
  respect it. (2) `rmdir` WITHOUT `/s` removes the reparse point only; `Remove-Item
  -Recurse` on a junction is the hazard to avoid, and the arming script refuses
  any path that is not a reparse point.
