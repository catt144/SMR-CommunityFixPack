- **Deleting a savegame agent-side, with the game closed, does NOT stick.** The
  next Steam launch writes it back. MEASURED 2026-08-11 (`unattended-2`), and
  the measurement is the file system's own metadata:

  | | before launch 1 (01:14) | after launch 2 (01:28) |
  |---|---|---|
  | `.sav` files in the save dir | **55** | **69** |
  | `CB1STAGE` / `CB2STAGE` / `CORUN0` / `CORUN1` / `U1STAGE` | absent | present |
  | `CB2F85` / `CB2PKEY` / `CB2PKEY2` / `CB2UNINSTALL` | absent | present |
  | `U1C0PROOF` / `U1C1HEAL` / `U1C2PT35` / `U1C6FORCED` / `U1C6HEALED` | absent | present |

  **Fourteen files**, and every one of them carries `CreationTime` between
  **01:17:04 and 01:17:33 on 2026-08-11** — inside the launch-1 window — while
  its `LastWriteTime` is its ORIGINAL date (2026-08-03, -08-04, -08-10),
  preserved. A file created tonight whose contents are dated a week ago was
  written tonight from a stored copy.

- ⭐ **The restore happens BEFORE the game process starts.** Steam was invoked
  at 01:17:00.8, the 14 files appeared 01:17:04–01:17:33, and `Mars.exe`'s
  process start time is **01:17:34**. So this is Steam's pre-launch sync, not
  anything the game does. `steam_autocloud.vdf` sits in the same directory and
  was rewritten at each launch.

- ⚖️ **This CLOSES the open hypothesis and clears two sessions that were
  recorded as having failed.** The save-dir close-out gate was recorded as
  "FAILED TWICE (same 4 files)" — batch-1's audit and batch-2's prep both found
  staged saves they had deleted. **They had deleted them.** Steam put them back.
  The remedy is not more diligence at close-out; the deletion is being undone by
  something outside the repo and outside the game.

- ⛔ **Consequence for every close-out from here.** A save-dir listing taken
  with the game closed proves the deletion happened; it does **not** prove the
  file stays gone, and the next launch is where it comes back. The listing rule
  (WORKFLOW "Co-runs") still stands — it is what caught this — but a session may
  only claim "deleted", never "gone for good", until Steam Cloud is off for this
  title. **Prediction, with its falsifier:** `U2STAGE`, `U2RT1` and `U2RT2`,
  deleted 2026-08-11 01:28, will be back after the next launch. If they are not,
  the mechanism above is wrong and this fact needs re-deriving.
  ⭐ **CHECKED THE SAME NIGHT, AND IT HELD.** The owner launched at ~01:57 to
  re-enable the pack; all three were on disk again by **01:57:47**, creation
  stamps from that minute, original modification dates preserved — plus a fourth,
  the extensionless `U2RT1` artifact from run 1. So the mechanism is confirmed on
  two independent launches by two different people, and the prediction that would
  have falsified it was written before the check.

- **The remedy is one owner tick**, and it is on `PLAYTEST_CHECKLIST.md`:
  Steam → Surviving Mars: Relaunched → Properties → General → **untick "Keep
  game saves in the Steam Cloud"**, then delete the strays once more.

- ✅ **TICKED 2026-08-11** (owner: *"Steam settings done"*, same day as the
  measurement). The 14 strays were deleted immediately after — 732 MB — and
  the directory verified at **55 `.sav` files**, the exact pre-restore

  ⛔ **Still owed: one post-untick launch.** The untick is the owner's setting

  ⚠️ **Note for the next reader: a byte-copy has the SAME metadata shape as a
  Cloud restore** (fresh `CreationTime`, old `LastWriteTime`). The 2026-08-11
  01:17 measurement's signature is only diagnostic when nobody has been copying
  saves. Diff against the expected-survivor list, not against the shape alone.

- ⚠️ **ONE THING THAT DOES NOT RECONCILE, recorded rather than waved off.** The
  directory held **56** `.sav` before this session staged its copy. Three were
  created that morning (the two autosaves + `PT-15`), leaving **53**
  pre-existing against a **55**-file baseline — **two short**.
  * It does **not** weaken the verdict above: a restore *adds* files, and this
    is a shortfall, not a surplus. Different direction, different question.
  * Most likely **autosave rotation** — the only two autosaves in the directory
    were both created that morning, so older ones were probably rotated out.
  * ⛔ **But it cannot be proven, because the 55-file baseline was recorded as a
    COUNT and never as a LIST.** There is nothing to diff against. That is a
    lesson for this fact's own methodology: **record the names, not the
    number** — a count cannot survive the first ordinary play session.
  * Cheapest resolution: ask the owner whether they deleted anything that
    morning. Otherwise the next close-out lists names and the question closes
    forward instead of backward.
