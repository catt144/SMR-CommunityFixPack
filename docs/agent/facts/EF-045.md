- **`RealTime()` does NOT advance across a loading screen, so a harness that
  times its own steps with `RealTime()` deltas understates any step containing
  a load** (MEASURED 2026-08-04, co-run #0 — log
  `docs/archive/corun0_Mars.exe-20260804-10.51.15.log`). The same `LoadGame`
  call was timed twice in that one run: the harness read
  **`STEP 2-loading-save END 864ms`** from `RealTime()` either side of the
  call, while the engine's own `GetPreciseTicks`-based line for the identical
  call read **`Game loaded on map BlankBigCanyonCMix_09 in 9968 ms`**
  (`Savegame.lua:1095/:1114`). An **11.5× understatement**, and it is not
  noise: `RealTime` is advanced per rendered frame, and `LoadGame` blocks
  inside `WaitRenderMode("ui", …)` (`Savegame.lua:1099`) where no frames run.
  **Consequence for any rig that reports its own costs:** a step spanning a
  loading screen must be timed by the engine's `Game loaded on map … in Nms`
  line, by OS-side file timestamps, or by an external clock — never by a
  `RealTime()` delta. Real-time *threads* still run and still yield correctly
  (`Sleep` is unaffected as a scheduling primitive); it is the *reported
  elapsed value* that is wrong. See [[EF-015]] for the sibling trap in the same
  area — the log path a harness must use to report anything at all.
- ⛔ **Do not even PRINT a `RealTime()`-delta step line for a step that spans a
  loading screen** (co-run #1 correction C8, 2026-08-04). Co-run #1's probe
  printed `STEP 2-loading-save END 874ms` a few lines from the engine's own
  `9784 ms` line for the identical load — honest by the rule above (it was not
  *trusted*), and still a trap: a future reader quotes the wrong number out of
  the log. A step spanning a load takes its number from the engine's line or
  prints none.
