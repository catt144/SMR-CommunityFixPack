### F12 — "Low Storage" warning never fires for Food/maintenance resources  `[tested: Code/Fix_LowStorageWarning.lua — PT-07 PASS 2026-07-27 on the repaired build: Food fires once/steady a sol/clears silently on organic recovery; Machine Parts fires once ("1 Sols, 12h") after forced-malfunction consumption; first run caught the second defect below]`
`Lua\ResourceTracking.lua:218-224, 229-234` — `supply*24/v*24` = `((supply*24)/v)*24`,
always 0 or ≥24 under integer division, guard requires `0 < x < 3` → unsatisfiable.
Grid branches (:259-303) are correct. Consts: `_GameConst.lua:4,10-11`. **Fix:** replace
`ResourceTracking.GatheredResourcesOnHourlyUpdate`: `MulDivRound(supply, HoursPerDay, v)`
vs `MinDays* × HoursPerDay`.

**Second defect found live in PT-07 (2026-07-27) — maintenance/food "Food"-key
collision; REPAIRED same day, A/B pending.** With the warning finally able to
fire, the user reported a flash + the "Warning! Insufficient resources" voice
replaying every game hour. Console instrumentation (wrapping AddNotification /
RemoveNotification / RemoveObjectFromNotification, then per-city tick markers)
pinned it: the notification was destroyed and recreated once per hour INSIDE the
surface city's own tick — remove first, add after. Root cause: `"Food"` appears
in `maintenance_resources_consumed_yesterday` too, and the maintenance loop and
the dedicated food branch write the SAME `"Food"` object key on the SAME
`InsufficientResources` notification. The maintenance loop runs first, computes
maintenance-based hours (guard fails for Food), takes its else-path and
`RemoveObjectFromNotification("Food", …)` — deleting the food branch's entry;
as the only object, that destroys the whole notification, and the food branch
recreates it a line later → FX + voice replay hourly (voice plays only on
whole-notification creation: `VoicePerObject` is false on this preset,
`NotificationUI.lua:197-207`). Latent in the shipped body — with the broken math
neither branch could ever add, so there was no entry to fight over. Diagnostic
red herrings ruled out on the way: user dismissal (the `dismissed` flag was
false on every destroy; the 2-real-minute `SuppressTime` re-nag is D02's
territory, not this), threshold flapping (reproduced with farms OFF, monotonic
70h < 72h), object validation (`IsObjValid`/`IsValidMapObject` both pass string
keys), and a second stale body (City and ResourceTracking dispatch the same
function address). **Repair:** the maintenance loop now skips `k == "Food"` —
the food branch owns that key (`-- FIX (F12, second defect)` block in the fix
file). PT-07 re-run + fresh A/B pair pending.

## ⭐ 2026-09-08 — game 1.1.0: what changed, and what hotfix 2 did about it

⛔ **Nothing above this line is edited.** The 1.0.7 record stands exactly as it was
written and every citation in it was true of **1.0.7.396349**. This section adds only
what game **1.1.0.403908** changed, read against the shipped 1.1.0 body on 2026-09-08.

1.1.0 did not repair the broken maintenance/Food math — it **replaced both warnings with a different mechanism**. `ResourceTracking.lua:222-310` now raises `InsufficientResources` for Power, Water and Air only (`:255-256`, `:276-277`, `:297-298`), so the projection branches this fix repaired are gone and there is nothing left for the module to patch. REMOVE stands.

⛔ **CORRECTION, same day, and it reverses what this section first said.** The first draft of this observation claimed *"a 1.1.0 player gets no low-Food warning at all"* and routed a feature request to the checklist on that basis. **That was WRONG, and it was wrong because the check was one file deep** — `ResourceTracking.lua` was grepped and the whole tree was not. The owner challenged it on the obvious ground that the DLC's stated focus is food, which makes silent deletion of food warnings implausible. Re-derived tree-wide, **both** warnings are alive and were rebuilt, not dropped:

* **Food → `StarvingColonists`** ("Missed Meals", voiced *"Warning! Food shortage"*, `Data/NotificationPreset.lua:1387-1404`). Per-dome, driven by `Community:UpdateStarvationNotification` (`Community.lua:536-543`) off `GetFoodServiceFailures` (`Dome.lua:2718-2745`), which reports a per-dome reason breakdown and a severity, and re-fires after dismissal only when it gets **worse** (`food_service_dismissed`, `DismissFoodServiceUntilWorse`). Driven from six status-effect transitions (`Data/StatusEffectPreset.lua:90,94,120,123,270,273`), `StatusEffects.lua:46` and `Community.lua:163`. ⭐ It is **NEW in this branch** — `SavegameFixups.InitStarvingColonistsNotification` (`Dome.lua:1034`) exists to light it up on migrated saves.
* **Maintenance → `MaintenanceStuckBuildings`** ("Maintenance Problem", voiced *"A building is about to malfunction"*, `NotificationPreset.lua:1103-1120`), driven by `UpdateObjectInNotification(self, self:IsMaintenanceStuck(), ...)` (`RequiresMaintenance.lua:342`). Its text covers buildings *"about to or already"* stopped, so it is a leading indicator too.
* ⚠️ **The evidence was in the line I had already read and skimmed past.** `ResourceTracking.lua:316` — `FixupObjectNotification("InsufficientResources", "g_InsufficientMaintenanceResources", "InsufficientMaintenanceResourcesNotif", empty_func)` — is the MIGRATION off the old maintenance notification, i.e. a signpost to where it went. I logged it as "a fixup, not a live warning" and drew the opposite conclusion from it. `RequiresMaintenance.lua:345` carries the matching migration comment.

**What is honestly different for the player**, now that it is derived rather than assumed: the retired warning was a *projection* ("N sols of supply left"); the replacements fire on **state** — colonists reaching Starving, buildings about to stop. So there is no longer a days-of-supply forecast, but the player is warned, by name of dome and building, with severity. That is a change of mechanism, not a loss of warning, and it is not a gap for this pack to fill.
