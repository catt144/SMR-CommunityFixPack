A **Mod-Manager disable followed only by a return to the MAIN MENU** does not

- `CONDITIONS pack=81/81 active | speed=3 | loads_this_process=2 | note=leg T:
  after the Mod-Manager disable` — the pack's code and **all 81 registrations
  are still live**, with the Mod Manager showing "Disabled".
- **But its persisted permanent is already gone.**
  `Unpersist missing permanent: Mod/SMR_CommunityFixPack | Fallback permanent:
  … [7]` appears **twice** in that same pack-loaded process (sitting log lines
  **2787** and **2829**) and in **none** of the six loads taken before the
  Mod-Manager round trip.

⇒ **The four states:** (1) the pack's own per-module toggle off; (2) a
Mod-Manager disable **without** a process restart — permanent gone, code and
registrations live; (3) a Mod-Manager disable **with** a full restart; (4) a
real uninstall.

**State (3), measured the same day, is clean:** `CONDITIONS pack=0/0 active`,
`Loaded mod items for: SMR_CommunityFixPackTestKit` (the kit only), zero
`[LUA ERROR]` across the whole process, and zero new log lines after ~1 minute
of sim at speed 3. Six lines name the pack and all six are accounted for: two
mod-def loads, one items-load, the save's own recorded mod list, one unpersist
fallback, and `This savegame tries to load Mod Community Fix Pack … which is
present, but not loaded`.

⛔ **CONSEQUENCE TO ROUTE, and it reaches backwards.** Nothing in PT-53 E, the
co-run rig envelope, or any prior brief said a Mod-Manager disable needs a
**full process restart** to take effect. **Any earlier uninstall-style reading
taken without one was measuring state (2), not an uninstall.** PT-20's 98-vs-98
comparison is the named case to re-check — owner decision, on the checklist.

⚠️ The `Unpersist missing permanent` line is therefore **not diagnostic of an
uninstall**: it occurs in state (2) with the pack fully loaded. It should not be
read as evidence either way without the `pack=n/n` gate beside it.
