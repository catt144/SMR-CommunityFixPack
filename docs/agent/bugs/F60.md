### F60 — Dome free-space uses `working`, assignment uses `ui_working` (P2, med)  `[fixed: Code/Fix_DomeFreeSpaceMismatch.lua]`
`Dome:RefreshFreeLivingSpaces` (`Dome.lua:2832-2834`) omits `player_enabled` →
`GatherFreeLivingSpaces` counts by `working` (`_GameUtils.lua:475-483`); unpowered
residences count 0 for births/immigration gates while `ChooseResidence` (:412) still
assigns to them. Power flicker desyncs the two views. **Fix:** pass consistent member.
*Implemented as sketched* — a full replacement of the two-line method passing
`player_enabled`; there is nothing to wrap, the fix IS the argument. Which member is the
intended one is settled three ways: `ChooseResidence` (`Residence.lua:404-412`) and
`Colonist:UpdateResidence` (`Colonist.lua:2309-2316`) both gate on `ui_working`, and the
two functions immediately above `GatherFreeLivingSpaces` in the same file —
`GetFreeWorkplacesAround` (`:443-455`) and `GetFreeWorkplaces` (`:457-473`) — tally
capacity on `b.ui_working` unconditionally. The `player_enabled` parameter has no caller
anywhere in Src, so nothing else changes meaning.
*Deliberately not touched:* `MicroGHabitatBase:RefreshFreeLivingSpaces`
(`MicroGHabitat.lua:42-44`) has the identical omission, but a habitat's `working` state is
its life support — F73's subject, not this defect.
Probe: `DomeFreeSpaceMismatch` in `30_Probes_Wave3.lua`.

## 2026-09-09 — 1.1.0: the gate this module was written for no longer reads the tally (hotfix-2 terminal audit, link 99)

Source-read on both trees, NOT measured. 1.1.0's dome gate stopped reading
`free_spaces`: `Community:HasFreeLivingSpaceFor` (`Lua/Buildings/Community.lua:402-418`)
and `Community:HasAnyFreeLivingSpace` (`:366-384`) iterate the residences directly
on `residence.working and (not dome or dome.working)`, while `ChooseResidence`
still assigns on `home.ui_working` (`Lua/Buildings/Residence.lua:452`). On 1.0.7
`HasFreeLivingSpaceFor(traits)` read `self.free_spaces` (1.0.7 `Community.lua:334-346`)
— that was the seam this module repaired. Our copy (`Fix_DomeFreeSpaceMismatch.lua:61-65`)
still passes `"player_enabled"` to the live `GatherFreeLivingSpaces` (`_GameUtils.lua:535-558`,
whose `traits` bucket became `filters` — carried, cannot throw), so on 1.1.0 the
corrected tally feeds only `GetAvailableResidences` (`_GameUtils.lua:356-367` →
passenger counts, `CargoRequestNew.lua:358`, `LanderRocketCargoRequest.lua:215`),
the UI (`Dome.lua:2600`, `:3877`, `:3908`; `ColonyControlCenter.lua:1320`, `:1330`)
and `Dome:CheckLivingSpace` (`Dome.lua:4281-4283`).

| | tally (`free_spaces`) | gate (`HasFreeLivingSpaceFor`) | assignment (`ChooseResidence`) |
|---|---|---|---|
| vanilla 1.1.0 | `working` | `working` | `ui_working` |
| with the pack | `ui_working` | `working` | `ui_working` |

Neither is consistent. With the pack an enabled-but-unpowered residence counts
as free for the passenger request while the gate refuses it — the original
desync mirrored onto a different consumer. Which is better for a player is
unmeasured (an unpowered-but-enabled residence + a passenger rocket is the
control). ⇒ **REMOVE candidate for hotfix 3**, decided after a measurement; not a
change in hotfix 2. No status moved. `reports/HOTFIX_2_AUDIT.md` §1 F-4.
