### F112 — C39's compensation now over-pays 8 building families, because 1.1.0 removed the compensation it was correcting (our own defect, patch-induced) (P2, high — filed)  `[filed 2026-09-08: source-read, not yet reproduced]`

**⚠️ A DEFECT OF OURS THAT THE EXISTENCE SWEEP CANNOT SEE** (`EF-076`): every
target `Fix_AutomationLawCompensation` declares still exists, so the module
passes its `Require` and applies. What changed is the *meaning* underneath it.

**What C39 was.** In 1.0.7 the three automation laws cut `max_workers` by
**label**, while `Workplace:GetWorkshiftPerformance` re-derived a compensating
`law_scale` only under `IsKindOf("Factory")` / `IsKindOf("ResearchBuilding")` /
`IsKindOf("Service")` — by **class**. Eight template families carry an
automation label, are `Workplace`s, and fail all three class gates (the four
Workshops, `SecurityStation`/`SecurityPostCCP1`, `DroneFactory`, …), so they ate
the worker cut and got none of the compensation. Vanilla's own comment said the
block "assumes that there's a modification in max_workers matching the value on
automation_workforce_reduction, and tries to reverse its effect". C39 paid the
eight the uplift the shipped gate could not reach them with.

**What 1.1.0 did.** The compensation is **gone — not moved, deleted.** Verified
across the whole 1.1.0 tree, not just the one file:

- `law_scale` appears **nowhere** in any `.lua` in `ModTools\Src`. Zero hits.
- The dev comment quoted above is gone.
- `automation_workforce_reduction` now appears **only in `Data/LawDef/`** — the
  law data — and in no game-logic file.
- 1.1.0's `GetWorkshiftPerformance` (`Lua/Buildings/Workplace.lua:269-294`) has
  no class gate and no scale term at all: shroud check → `active_shift`
  resolution → `max_workers == 0` early return → `GetWorkersPerformance(shift)`
  → `Max(…, auto_performance)` if automated → a `FarmBase`/`Pasture`
  RemoteFarming term → return.

**The laws still cut `max_workers`** (`Data/LawDef/LawDef-Technology.lua:17`,
`:91`, `:110`, `:178` — `Percent = "automation_workforce_reduction"`). So on
1.1.0 the automation laws reduce workers and **nobody is compensated**. Uniform,
and plausibly deliberate.

**The failure.** `compensation_delta` returns 0 for `Factory` /
`ResearchBuilding` / `Service` on the explicit reasoning that they are "already
paid by the shipped gate" (`Code/Fix_AutomationLawCompensation.lua:179-182`) —
a gate that no longer exists. It still returns a **non-zero delta** for the
eight out-of-class families. Net effect on 1.1.0:

> the 8 buildings C39 was written to bring UP to parity are now the only
> buildings in the game receiving automation compensation at all.

C39 has become the inverse of itself: it no longer removes an asymmetry, it
manufactures one, in our favour, invisibly, in any colony running an automation
law. ⛔ This is a **player-visible balance divergence**, not a crash and not a
cosmetic — which makes it the more dangerous of the two 1.1.0-induced defects
(see [[F111]]).

**Fix shapes, for the owner (`FIX_POLICY` §4a):**
- **(a) Self-disable on 1.1.0.** Add the vanilla-shape check the module's
  premise depends on — if no compensation block exists, there is nothing to
  correct — and let `Require` decline. Matches the pack's idiom and is the
  conservative read of "repair a defect, never rebalance".
- **(b) Retire C39** as fixed-by-removal upstream.
- **(c) Keep paying the eight**, on the argument that the *original* unfairness
  (label cut without class compensation) still exists and is now merely
  universal. ⛔ This is a **rebalance, not a repair**, and `FIX_POLICY` §4a puts
  it squarely with the owner — the pack does not ship balance opinions.

⛔ **Not actionable from source alone.** The A/B is cheap and attended: enact an
automation law on 1.1.0, read a Workshop's Performance with the pack on and off.
Decision 99 owns the disposition. ⚠️ C39's status is `tested-unattended` and its
frozen index row still reads `filed` — do not let this entry's filing be read as
a status move on C39 itself.
