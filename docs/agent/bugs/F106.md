### F106 — post-build parent-class method wraps don't reach subclass instances in copy-flattened hierarchies; F33 suspect no-op (P2, high)  `[filed 2026-08-24 — derived at Src during F105; one console read settles the F33 instance; audit scope is checklist 74]`

## The mechanism (SOURCE tier, derived 2026-08-24 during F105's fix-shape work)

The class builder (`CommonLua/Core/classes.lua`, build entry `OnMsg.Autorun`
`:980`) resolves single-parent inheritance in `ResolveValues` (`:693-729`):

* If the parent's classdef sets **`__hierarchy_cache`** (true on `Building`,
  `Building.lua:157`; also CObject/Object/Preset/XWindow and a few others), the
  child **chains**: `meta = parent` (`:708`), and the child's built table holds
  only its own declared members.
* If the parent is **un-flagged** — `ConstructionSite`,
  `LandscapeConstructionSiteBase`, `ClearWasteRockConstructionSite`, most
  intermediates — the child **COPIES every member of the parent's built table
  into its own** (`:701-705`) and takes the parent's metatable.

The `:986-988` comment states the split in prose. Consequence for the pack,
whose `00_Core` applies every fix **after `ClassesBuilt`**:

> **A `{class = C, method = M}` wrap installed by assignment on built class `C`
> is dispatched from an instance of subclass `S` ONLY IF `S` resolves `M`
> through the metatable chain — i.e. only when `M`'s declaring class is a
> flagged ancestor. When `M` is declared on any un-flagged class, every
> descendant owns a build-time reference COPY of vanilla `M`, and the wrap
> patches a table those instances never consult.**

This is `EF-066`'s unswept watch made sharper: EF-066 worried about subclasses
that *override* the method; the copy branch means the wrap also misses
subclasses that merely *inherit* it. Failure mode is unchanged — under-coverage,
the unreached instances keep vanilla behaviour, defect included; never new harm.

Unaffected wrap kinds: `SetGlobal` replacements (most of the pack); wraps where
the wrapped class is the exact instantiated class; combined methods (`Init`/
`Done`) installed at classdef time (EF-066's composition mechanism); multi-
parent (complex-inheritance) classes go through a related copy path
(`:663-691`) that this derivation did NOT sweep — treat as unknown.

## The first confirmed-derived victim: F33 / `Fix_SmallLandscapeSites`

The module wraps `LandscapeConstructionSiteBase.GetClosestDests` (declared
there, `:178-193`). Every real landscaping site is one of the three LEAF
classes (`LandscapeConstructionSite`, `ClearWasteRockConstructionSite`,
`TerrainPaintConstructionSite` — `LandscapeConstructionSiteBase` is never
instantiated), the whole chain below `ConstructionSite` is un-flagged, and the
only caller (`DroneApproach`, `:195-205`) dispatches on the instance ⇒ **the
leaf tables hold the vanilla copy and the F33 clamp never runs.** F33's status
is `fixed` — no attended test ever contradicted this, so no measurement is
being overturned. If confirmed, the small-site drone crash the module promises
to fix still ships live.

⚠️ By the same rule the F105 fix (`Fix_LandscapeCostRefresh`) installs per leaf
class, not on `ConstructionSite` — correct under either model.

## ⛔ Derived, not measured — the settling observation (one console read)

In a booted game with the pack loaded:

```
rawget(g_Classes.LandscapeConstructionSite, "GetClosestDests")
```

* **non-nil** and ≠ `LandscapeConstructionSiteBase.GetClosestDests` → the leaf
  holds a build-time copy the wrap missed → **F106 CONFIRMED**, F33 flips to
  broken-fix.
* **nil** → the leaf chains to the base at dispatch → the wrap reaches it →
  this entry's mechanism is wrong for this hierarchy: rewrite it, and say so
  loudly.
