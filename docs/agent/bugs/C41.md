### C41 — Depot resource picker fails to APPEAR at all (OG witness) — carries F76's unrefuted residue  `[filed 2026-08-03 by chain-12 QA (job 10) so F76's closure buries nothing — cand; unreproduced third-party symptom + one measured lead; nothing built]`

**Why this row exists.** F76 is **closed — refuted** (its named mechanism was
falsified by measurement and source, and its load-failure claim did not
reproduce). But two things in its orbit are NOT refuted and must not vanish
under that closure; the F76 adjudication routes them here.

1. **The OG witness, a DIFFERENT symptom.** `BUG_LIST_AUDIT.md` §2.2: *"The
   icon which should appear when I click on a deposit does not appear!"* — the
   picker failing to APPEAR, against F76's appears-in-the-wrong-place. It was
   the stated reason F76 held P1. OG-era, never reproduced, no mechanism ever
   attached — but it is a real player report and it was never adjudicated on
   its own merits until now.
2. **The one measured lead that would produce exactly that symptom (F76's M5,
   2026-08-02).** `terminal.GetMousePos()` **can** return coordinates outside
   `desktop.box` — one logged pass read `mouse (6148, 2350)` against
   `desktop.box (0,0)-(3840,2160)`. `align_pos` comes from that same call, and
   an out-of-range anchor makes `UpdateLayout`'s clamps slam the dialog into a
   screen corner — for a player whose game window is not at the virtual-desktop
   origin (second monitor, windowed offset), the picker would open somewhere
   they are not looking, i.e. *"does not appear"*. ⚠️ On THIS machine there is
   no persistent offset (passes #4-#7 read anchor ≈ mouse; setup unchanged
   since the original filing), so the lead is for OTHER setups and is untested.
3. **Two unexplained environment deltas from the 2026-07-27 filing**, recorded
   not discounted: the entry pinned UI Scale ~80–85% (measured `1900` = 100%),
   and a **3751-px** window (measured 3840; 3751 is not a standard mode).
4. **The designed instrument exists:** the `F76MISS` forwarding hook (prompt
   11's design) — install it, and any click the picker never receives prints
   where the engine thought the mouse was. One line of console on any setup
   that ever shows the symptom.

**Disposition: `cand`.** No F-number unless the symptom is ever reproduced or a
second witness lands with setup details. If a Relaunched player ever reports
"the picker doesn't show", the first question is their monitor layout, and the
instrument above is the one-sitting answer.

### ⭐⭐ THE M5 LEAD IS MEASURED 2026-08-04 (co-run #1) — an out-of-range anchor DOES displace the picker; ⛔ but the picker still APPEARS, 40/40

**Run conditions.** Retail `Mars.exe` **1.0.7.396349**, cold load of a staged
COPY (`CORUN1.savegame.sav`) of `TEST2H TRAIN`, pack **81/81 active**, speed 3,
session uptime ~6 min (run 1) / ~1 min (run 2), zero `[LUA ERROR]`. Raw lines:
`docs/archive/corun1_Mars.exe-20260804-12.42.47.log` and
`corun1b_Mars.exe-20260804-12.54.14.log`. Instrument: F76's own M2 post-wrapper
on `ResourceItems.UpdateLayout`, logging anchor, box, container, scale, live
mouse and `desktop.box` **on one line**.
**FORCED:** the open (`OpenResourceSelector` called directly with
`RCTransport:InteractWithObject`'s own storage-branch context,
`RCTransport.lua:419-424`) and, in run 2, the cursor being parked off-window.
**ORGANIC:** the anchor — `ResourceItems:Init` reads the live mouse either way
(`ResourceItems.lua:11`), which is the only quantity this lead is about.

**1 · The out-of-range mouse is REPRODUCIBLE, not a one-off.** Item 2 above
rests on a **single** logged reading and is explicitly weakened there as *"what
an ordinary cursor excursion onto a second display looks like"*. Measured now:

| reading | value |
|---|---|
| `terminal.desktop.box` / `scale` / `UIL.GetScreenSize()` | `(0,0)-(3840,2160)` / `(1900,1900)` / `(3840,2160)` |
| `UIL.GetSafeArea()` | `0 0 3840 2160` — the whole screen, as M1 found |
| first census read of `GetMousePos()`, before anyone touched anything | **`(6710, 2294)`** — already out of range |
| 60 s poll at 5 Hz while the owner swept both monitors | **29 / 300** reads outside `desktop.box`; `x` range `0..7665` |
| run 2, cursor parked on the second monitor | **20 / 20** opens with `ANCHOR_OUT=true` |

⭐ **So `terminal.GetMousePos()` reports VIRTUAL-DESKTOP coordinates while
`terminal.desktop.box` is window-local.** That is exactly the hypothesis M5
states and could not test.

**2 · ⭐ The safe-area clamps are NOT innocent for an out-of-range anchor — and
that is new.** F76's M1 measured the clamps innocent and the M2 block concluded
the picker "opens exactly at the cursor"; **both were established for an
IN-RANGE anchor only**, which is all that was ever fed to them. With the cursor
parked off-window:

```
L2C LAYOUT #14 anchor=(6021, 1259) ANCHOR_OUT=true box=(2224, 830)-(3840, 1259)
      cont=(2096, 830)-(3968, 1202) scale=(1425, 1425) mw=1616 mh=429
      mouse=(6021, 1259) desk=(0, 0)-(3840, 2160)
```

The x clamp (`ResourceItems.lua:58-59`) fired and produced exactly
`x = 3840 - 1616 = 2224`, `maxx = 3840` — **the dialog pinned to the right
screen edge while the cursor is 2181 px further right, on the other monitor.**
That is *"renders far from the cursor"* with a measured mechanism, on the entry
whose parent's headline claim was falsified for the in-range case.

**3 · ⭐⭐ BOTH CLAMPS FIRE, AND THE BOTTOM-RIGHT CORNER SLAM IS CONFIRMED TO THE
PIXEL** (run 3, `docs/archive/corun1c_Mars.exe-20260804-13.23.08.log`).

The pre-registered prediction was a corner slam. **Run 2 saw only the x clamp
fire and this entry first recorded the corner half as REFUTED, on the stated
grounds that "the y clamp needs an anchor below 2160 and this monitor geometry
cannot produce one." ⛔ That reason was false and the verdict was wrong.**
Display 2 is **3840×2560**, 400 px TALLER than the game's box, so a cursor in
its bottom strip gives `y > 2160`. Run 2's parked cursor sat at `y≈1259` and
never sampled it. **"Refuted" was really "unsampled"** — a distinction this
project has a rule about, and it was breached here before being caught.

Run 3 sampled it. The prediction was **computed from the measured dialog size
and written into the log before any picker opened**:

```
PREDICTED  box (2224,1731)-(3840,2160)      x = 3840-1616,  y = 2160-429
MEASURED   L2D cycle 1/12 anchor=(5305, 2269) (x_out=true y_out=true)
           box=(2224, 1731)-(3840, 2160)  CORNER=true  items=9  dialog=ALIVE
```

**All four edges match exactly.** The flip branch (`:53-56`) correctly did not
fire, as predicted — it needs `y < 0` and `y` started at `2269 - 429 = 1840`.

⚠️ **n = 1 for the corner** (the cursor returned to display 1 after the first
cycle; the other 11 cycles read `x_out` only or in-range, and are logged). That
is honest but weak-sounding for the wrong reason: `UpdateLayout` is a
deterministic arithmetic computation, not a stochastic effect, and the single
sample reproduced a four-number prediction derived from source. The remaining
uncertainty is whether the *anchor* recurs, not whether the *layout* does.

⭐ **And the F76 pass-#8 reading is now retro-explained exactly:** `mouse (6148,
2350)` has `x` on display 2 and **`y = 2350`, past the game box's 2160 and
inside display 2's 2560** — i.e. that reading was already a both-clamps anchor
and would have produced this same corner box. It was never anomalous; it was the
cursor on the other monitor, which is also why it appeared once in eight passes.

**4 · ⛔ WHAT DID NOT REPRODUCE, and it is the entry's own symptom.** The picker
**appeared 20/20 in run 1 and 20/20 in run 2** — including all 20 opens whose
anchor was out of range. The OG witness's *"the icon does not appear"* did
**not** reproduce, and `0/40` is a **rate bound across 40 forced opens, not a
refutation**. A false positive was designed out rather than left to chance:
`ResourceItems:GetItems` closes the dialog when it has nothing to show
(`ResourceItems.lua:80`), which looks identical to the symptom, so the item
count was logged per cycle (`items=9` throughout).

**5 · ⛔ Reachability is UNPROVEN and is not claimed.** Producing this needs the
player to click a depot *while their cursor reads outside the game window* —
not an ordinary action. Nothing here identifies what the OG witness saw; their
monitor layout remains unknown. **The entry stays `cand`, nothing is built.**

### ⭐ ENVIRONMENT RESOLVED 2026-08-04 (owner supplied the Windows display readouts) — the arithmetic closes exactly

This entry briefly recorded an "unexplained environment disagreement" between
three coordinate systems. **There were only ever two; the third was a bad
measurement of mine and is withdrawn.** A PowerShell `System.Windows.Forms.Screen`
read reported `2560×1440` and `2560×1707` because the process was **not
DPI-aware** and Windows is at **150%** (`3840/1.5 = 2560`, `2160/1.5 = 1440`,
`2560/1.5 ≈ 1707`) — those are logical units, not pixels.

| | actual |
|---|---|
| display 1 — Odyssey G7 | **3840 × 2160** at `(0,0)` |
| display 2 — BenQ RD280UG | **3840 × 2560** at `(3840,0)` |
| real virtual desktop | **`0..7680 × 0..2560`** |
| game `desktop.box` / `screen` | `(0,0)-(3840,2160)` — **exactly display 1's native pixels**, fullscreen on display 1 |
| max `GetMousePos` x measured | **7665** — inside 7680, display 2's right edge ✔ |
| max `GetMousePos` y measured | **2559** — display 2's height is 2560 ✔ |

⭐ **Every observation closes to the pixel, and the lead is confirmed rather
than merely supported:** `terminal.GetMousePos()` returns **raw virtual-desktop
coordinates spanning both displays**, while `terminal.desktop.box` is **the game
window's own display only**. Any cursor position on display 2 is out of range by
construction, permanently, for as long as the game is fullscreen on display 1.
**Banked as `agent/facts/EF-046`** — it is a UI-wide property, not a C41 detail,
and it constrains any future repair: ⛔ a fix that "converts" the anchor
unconditionally would break the ordinary in-range case that F76's M1/M2 measured
as correct. Detect out-of-`desktop.box`, do not transform every anchor.

⛔ **Also withdrawn: "the game's numbers are not the ones the 2026-08-02 F76
sitting recorded."** They are identical — that sitting measured
`desk (0,0)-(3840,2160)`, `scale (1900,1900)`, and so did this one. **The setup
has not changed.** The apparent change was the same DPI-unaware read. ⚠️ Item 3
above (the UI-scale and 3751-px deltas from the 2026-07-27 filing) is a
*separate* question and is **not** resolved by this.

⭐ **What this does to the "does not appear" question.** It supplies the first
*measured* mechanism by which a player's picker ends up somewhere they are not
looking, and it makes the discriminator cheap for any future report: ask for
their monitor layout, then read `terminal.desktop.box` against
`terminal.GetMousePos()` — one console line, no picker needed.
