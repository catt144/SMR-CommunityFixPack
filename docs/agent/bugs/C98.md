### C98 — The 1.1.0 rewrite of the drone carried-resource drop lost its guaranteed-placement fallback (P3) `[cand 2026-09-15: SOURCE-VERIFIED diff; loss branch UNPROVEN-REACHABLE; NOT reproduced; NOT ours]`

⛔ **NOT REPRODUCED.** Everything below is the 1.0.7 → 1.1.0 source diff plus a player's words.
⛔ **NOT OURS.** MEASURED: `grep -rn "DropCarriedResource\|GetNavigationPos\|SetCommandCenter\|PlaceResourcePile\|GetPassablePointNearby" Code/`
returns exactly one hit, `Fix_ArrivalDeaths.lua:240`, which calls `GetPassablePointNearby` on its
own position in an unrelated colonist path. No pack module touches the drop.

⚠️ **PRIORITY IS PROVISIONAL.** P3 because the only *observed* symptom is a retrievable pile. ⭐ **If the
loss branch below is ever shown reachable, this is a P2** — silent resource destruction on a routine
player action.

#### The report (INHERITED, not verified) — and the reporter corrected themselves

Steam, **simmy2109**, 2026-09-14, owner-relayed screenshot. Comment **#6**, 6:07pm:

> *"If I reassign a drone, it looks like whatever resource it is carrying is destroyed. The resource
> was simply dropped in previous versions."*

Comment **#7**, ten minutes later, superseding it:

> *"Actually, they are not destroyed… the specific scenario I'm seeing is when a drone that is
> assigned to a rocket is unloading resources. If I drone is reassigned while holding one of those
> resources, it gets dropped over at the corner of the rocket. This causes the resource counter to
> drop (why I thought it was destroyed), but the resources just need to be picked up from that
> location. Multiple resources can end up stacked in that same spot."*

⭐ **The inversion worth recording: they retracted the half that matches a real new code path, and kept
the half source does not explain.** See both sections below. No log, no save, no mod list supplied.

#### The function was rewritten for 1.1.0 — the diff

**1.0.7.396349** (`Lua/Units/Drone.lua:1843-1864`), the whole drop:

```lua
local passable_point = self:IsValidPos() and map:GetPassablePointNearby(self, self.pfclass, self.radius*200, self.radius + 30)
if passable_point then
    PlaceResourcePile(passable_point, self.resource, amount, map)
else
    PlaceResourcePile(self:GetPos(), self.resource, amount, map)
end
```

**1.1.0.403908** (`Lua/Units/Drone.lua:2066-2105`):

```lua
local pos = self:GetNavigationPos()
local filter, q, r
if IsValid(self.holder) then
    --pos is the holder's exit point; a pile left in the doorway blocks passage
    filter = NotExitHex
    q, r = WorldToHex(pos)
end
local passable_point = IsValidPos(pos) and map:GetPassablePointNearby(pos, self.pfclass, self.radius*200, self.radius + 30, filter, q, r)
local drop_pos = passable_point or (IsValidPos(pos) and pos)
local left = amount
local producer = GetProducerWithFreeSpaceAtPos(map, drop_pos, self.resource)
if producer then
    left = left - producer:DepositProduced(self.resource, Min(left, producer:GetFreeStockpileSpace()))
end
if left > 0 then
    if drop_pos then
        local place = delayed and PlaceResourcePile_Delayed or PlaceResourcePile
        place(drop_pos, self.resource, left, map)
    else
        assert(false, "Drone carried resource lost - nowhere to drop it")
    end
end
```

Three behaviours changed:

1. **The anchor moved** from the drone object to `self:GetNavigationPos()`, which returns
   `self.holder:GetImmediateExitPos(self) or self.holder:GetPos()` when the unit is held and
   `self:GetPos()` otherwise (`Lua/Units/Unit.lua:486-491`). A `NotExitHex` filter keeps a pile out
   of the doorway when held.
2. **A producer deposit was added** — `GetProducerWithFreeSpaceAtPos` absorbs the load first if
   something at the drop position has stockpile room.
3. ⭐ **The unconditional fallback was removed.** 1.0.7's `else` placed a pile at `self:GetPos()`, so
   a carried load could not be lost. 1.1.0 replaces it with `assert(false, "Drone carried resource
   lost - nowhere to drop it")`. Asserts do not fire in a retail build, so that branch **destroys the
   load silently**. The engine's own message says so.

⛔ **REACHABILITY NOT ESTABLISHED.** `drop_pos = passable_point or (IsValidPos(pos) and pos)` is nil only
when `IsValidPos(pos)` is false. No case was found where that holds for a drone about to drop. Until
one is, this is a latent branch, not a demonstrated defect — ⛔ **do not describe resources as being
destroyed in 1.1.0 on the strength of this entry.**

#### Why the reporter's OWN explanation is probably wrong

Their #7 attributes the placement to the rocket. But the anchor only leaves the drone's own position
when `self.holder` is valid, and **`Lua/UniversalRocket.lua` contains no `holder` reference at all** —
a drone unloading a rocket does not appear to be held by it. With no holder, 1.1.0 computes the drop
from `self:GetPos()`, which is what 1.0.7 did.

⇒ **"At the corner of the rocket" is most likely a drop near the drone, and the drone is at the
rocket** — unchanged behaviour the player has newly noticed, not a regression. ⛔ INFERRED: the holder
question was settled by absence of the symbol in one file, not by observing a drone in play.

#### Control — what separates the two readings, in play, with no save needed

⭐ **Reassign a drone that is carrying a resource in open ground, far from any rocket or building.**

| observation | verdict |
|---|---|
| the pile lands next to the drone | the anchor is the drone; #7's rocket attribution is wrong and the placement is unchanged from 1.0.7 |
| the pile still lands at a rocket/building corner | a holder IS set on that drone; this entry's holder reasoning is refuted and the anchor change is live |

⭐ **Second control, for the stacking claim:** reassign several loaded drones at one rocket. A single
deterministic spot implies an exit-point anchor; scattered spots imply per-drone positions.

⛔ Neither control touches the loss branch. That one needs a case where `IsValidPos(pos)` is false.

#### ⭐ How to settle this WITHOUT reproducing it — the owner's route, 2026-09-16

The owner's read is that this scenario is nasty to engineer in a playtest. It does not need to be
engineered, and a desk audit **cannot** close it: `GetPassablePointNearby` is a **C export**
(`CommonLua/LuaExportedDocs/Game/realm.lua:66` is a doc stub only), so where the pile lands is
engine-side and unreadable. The instrument is the answer, not a repro.

⭐ **A log-only wrapper on `Drone:DropCarriedResource`**, recording per drop: the drone's position,
`self.holder`, the computed `drop_pos`, **the distance between drone and drop point**, the resource,
and which path fired (`PlaceResourcePile` vs `PlaceResourcePile_Delayed`, plus the nil-`drop_pos`
branch). The whole question collapses to one number:

| observation | verdict |
|---|---|
| distance ≈ 0 | anchored on the drone; 1.1.0 behaves as 1.0.7 here and the report is a player newly NOTICING long-standing behaviour |
| distance large **and constant across different drones** | anchored somewhere fixed; a real 1.1.0 regression and this entry's priority rises |
| `drop_pos` nil ever observed | ⭐ the silent-loss branch is REACHABLE — promotes item 3 above from latent to real, and this becomes P2 |

⭐ **It needs no reproduction at all.** The wrapper fires on *every* carried-resource drop, not only
reassigns, and drones carry resources constantly — so ordinary play yields a population within
minutes and the reassign case falls out of it. TestKit only, log-only, 0 shipped hashes, no booked
sitting. ⇒ **Ride it on the next TestKit link** beside the quick-build row and the deferred
crew-trace slot rather than making it its own errand.

##### ✅ BUILT 2026-09-16 — `SMRTest.Log.DroneDrop`, TestKit `acafc74`. ⛔ NOT RUN IN PLAY YET.

A Kit-page arm/disarm button; arm it and play normally, then read the `DISTANCE=` field against the
table above. Two design points that are the answer to the two hazards this section names, so a
reader does not re-derive them:

- ⛔ **`drop_pos` is NOT recomputed.** Calling the C export a second time *samples* it again and need
  not return the point the real call used. The probe wraps `PlaceResourcePile` and
  `PlaceResourcePile_Delayed` for the duration of the drop and reports where the pile really landed,
  so the distance is measured against the actual outcome.
- ⭐ **The loss branch is decided without the C export at all.** `drop_pos` is nil **exactly** when
  `IsValidPos(self:GetNavigationPos())` is false (`Drone.lua:2082`), a pure-Lua read the probe takes
  before the call. ⇒ **`valid_pos=false` in the log is the reachability proof this entry asks for**,
  and it promotes item 3 to real and this entry to P2 on a single line.
- ⚠️ It wraps **`FlyingDrone` as well as `Drone`** — classes are flattened at build time, so a wrap of
  the parent alone would never fire for a flying drone.

⚠️ **The two desk questions below are still unopened**, and the probe does not answer either: it
reports where the pile landed, not why the C boundary put it there.

⚠️ **Two desk questions the audit CAN settle, folded in here rather than lost:**
1. **1.0.7 passed an OBJECT, 1.1.0 passes a POINT** — `GetPassablePointNearby(self, …)` became
   `GetPassablePointNearby(pos, …)`. At a C boundary that is a real semantic difference and is the
   one way 1.1.0 could relocate the drop **with no holder involved at all**. ⛔ Untested.
2. **Two undocumented arguments.** The doc stub is `(map, pt, pfClass, nMaxDist, nMinDist, filter)`;
   1.1.0 passes `filter, q, r` — two beyond the documented signature. What `q, r` do is unread.

⚠️ **And narrow the holder claim properly.** This entry rests "a rocket-unloading drone is unheld" on
the absence of `holder` from `UniversalRocket.lua`. Drones **can** be held — `AncientArtifactInterface.lua:72`
does `drone:SetHolder(self)` — so the claim needs the presence side counted, not one file's silence.

#### Not opened

conserved · whether the resource counter the reporter watched excludes loose ground piles, which
would make the counter drop correct rather than a symptom · whether `PlaceResourcePile_Delayed` (the
