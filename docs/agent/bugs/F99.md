### F99 — `TrackConstructionSite:Complete` dereferences an emptied element list (`start_el` nil, `TrackElement.lua:805`)  `[filed 2026-08-03 from the owner's live log — cand, severity open, nothing built]`

**How it was found.** Not by looking for it. The F11 rider sitting called
`FlushLogFile()` for an unrelated reading and the log review (protocol step 4)
turned up **14** identical `[LUA ERROR]` lines, **session ~1h**. Reported here
verbatim rather than attributed away — the standing rule is that "not caused by
our leg" is an attribution verdict, never a dismissal.
*(⚠️ Count corrected 2026-08-03, second-opinion chain: the 14 matching lines are
**7 throws** — 7 `[LUA ERROR]` headers each paired with a C-side `Error calling
Lua function "exec" from C` line for the same throw. The other two archived logs
contain zero.)*

```
[LUA ERROR] Lua/Buildings/TrackElement.lua:805: attempt to index a nil value (local 'start_el')
  Lua/Buildings/TrackElement.lua(805):  method Complete
  Lua/Buildings/ConstructionSite.lua(2483):  method Complete
  Lua/Cheats.lua(115):   <>
  [C](-1):  method MapForEach
  Lua/Cheats.lua(126):  global CheatCompleteAllConstructions
```

Locals at the throw (from the engine's own dump): `start_el | nil`,
`end_el | nil`, with `track_obj`, `el1` and `el2` all live `TrackGridElement`/
`TrackBase` objects on map 1.

**The defect.** `TrackElement.lua:800-807`:

```lua
local el1, el2 = self.track_obj.start_el, self.track_obj.end_el
ProcessTrackElements(ResolveMap(self.track_obj), self.track_obj.elements)
local start_el = self.track_obj.elements[1]
local end_el = self.track_obj.elements[#self.track_obj.elements]
start_el:AutoConnectTracks()
```

`ProcessTrackElements` → `OrderTrackElements` (`Tracks.lua:520-624`) **clears and
rebuilds** `elements` — that is F48's own finding, re-used here. When the rebuild
returns empty, `elements[1]` is nil and line 805 throws. Note `el1`/`el2` on the
first line snapshot `start_el`/`end_el` and are then **never read again**: the
shipped code captures exactly the fallback it needs and discards it.
*(⛔ The clear-and-rebuild route is REFUTED 2026-08-03 — the rebuild cannot come
back empty; the list was empty BEFORE line 802. See "Mechanism settled by
reading" below. The `el1`/`el2` observation stands.)*

**Why it is not cosmetic.** The throw aborts `Complete` partway. By line 805 the
code has already run `DoneObject(self)` (destroying the construction site) and
`element:ApplyToGrids()`, but has NOT reached `table.clear(element.track_obj.repair_cgs)`
or `Msg("TrackBroken", element.track_obj, false)`. So the site is gone while the
track is never told it stopped being broken — a partially-completed track, 14 times
in one session. `error()` does not unwind mod or game code (`agent/facts/EF-008`),
so execution continues with that state in place.
*(⛔ The last sentence is WRONG and superseded 2026-08-03: `EF-008` is about
`assert()`, and this was a genuine runtime `error` — the paired log lines show
each throw unwinding all the way out of the console `exec`. Execution does NOT
continue; everything after line 805 in that whole cheat pass is abandoned. See
"Severity, both directions" below — milder AND worse than this paragraph says.)*

⚠️ **ATTRIBUTION — the honest limit, stated before anyone quotes this entry.**
Every observed hit came through `CheatCompleteAllConstructions()`
(`Cheats.lua:126` is in the stack) while the owner was cheat-building an
underground setup for the F11 rider. That cheat finishes **every** site at once,
including track stubs with an incoherent element list that ordinary play would
not leave lying around. `quick_build` is **not** what makes `start_el` nil — the
empty rebuild is, and a normally-completed track reaches the same unguarded line —
but **"a player hits this without cheats" is UNPROVEN and is not claimed here.**
Severity is therefore left open rather than guessed.

**Not ours.** No pack code appears in the stack; the site is vanilla
`Lua/Buildings/TrackElement.lua`. FIX_POLICY §4a (WHO BENEFITS) is satisfied on
the face of it — a player finishing a track would benefit — but only if the

**Adjacent but not covered by** F44 (twin elements sharing `node_idx`), F45

### ⛔ Mechanism settled by reading 2026-08-03 (f11-f99-review chain, terminal prompt — overturns BOTH prior write-ups)

**The clear-and-rebuild route is refuted.** `ProcessTrackElements`
(`Tracks.lua:807-837`) returns immediately on an empty list (`:808`); with
`#elements == 1` or an invalid `elements[1]` it takes the `:826` branch, which
never mutates the array; and every exit of `OrderTrackElements` from a
non-empty input leaves it non-empty — the `table.clear` at `:575` is followed
one line later by `elements[1] = start_el`; the no-`start_el` path asserts at
`:582` WITHOUT ever reaching the clear; the missing-adjacent path asserts at
`:616` and restores from `all_elements` (`:617-620`). **So
`self.track_obj.elements` was empty BEFORE line 802.** (Prompt 1's sealed
derivation had first proved the by-construction half — a NEW build's element is
inserted by `TrackGridElement:Init` and never removed before :803 — then
conceded to the filed route in its outbox; that concession was itself wrong.
Two sessions briefly agreed on a refuted route: chain rule 6's exact hazard.)

**Where the drain is.** `ExpandTrackFromElement` (`TrackElement.lua:714-742`)
absorbs the entire hex-connected component around a completing element: every
element whose `track_obj` differs is removed from ITS track's list
(`table.remove_value(el.track_obj.elements, el)`, `:729`) and reassigned
(`:737`). A track whose elements are all absorbed by a neighbour's completion
is left a husk — kept alive only by its remaining
`elements_under_construction` (repair sites are NOT in the hex grid walk; the
broken element is — `BreakTrackElement` only hides it, `Track.lua:639`, and the
site takes `params.track_obj = self`, `:635`). When that husk's repair site
finally completes, `element = self.broken` carries the NEW track while
`self.track_obj` is the husk: `:797-799` operate on `element.track_obj`
(correct), `:801-804` on `self.track_obj` (empty) → `elements[1]` nil → throw.
The one link not readable from Lua: `HexGetTrackGridElement`'s per-hex
tie-break between the hidden element and its site (C binding). The seven live
throws are the evidence it resolves to the element.

**The dead guard is the root enabler, and it is in no shipped-bug write-up.**
`:800` `if not self.broken then` was written to skip the block for repair
completions and never does — `:774` (inside the branch taken when
`IsValid(self.broken)`) has already done `self.broken = nil`, and on new builds
the field is `false`. So every repair completion enters a block written to
exclude it, cheated or not. (Edge nuance: an invalid-but-truthy `self.broken`
WOULD skip the block — the guard is dead for every real completion path.) The
dead locals `el1, el2` at `:801` — computed, never read — are the fingerprint
of the unfinished refactor.

### ⭐ THE HEX TIE-BREAK IS MEASURED 2026-08-04 (co-run #1) — `HexGetTrackGridElement` returns the HIDDEN ELEMENT

**What this closes.** The mechanism block above ends: *"The one link not
readable from Lua: `HexGetTrackGridElement`'s per-hex tie-break between the
hidden element and its site (C binding). The seven live throws are the evidence
it resolves to the element."* That was an inference back from a crash. **It is
now a direct reading.**

⚠️ **And the "not readable from Lua" framing was too strong.**
`HexGetTrackGridElement` is a one-line Lua wrapper —
`return hex_grid:GetObject(q, r, "TrackGridElement")` (`TrackElement.lua:1-3`).
Only `GetObject` is C, and the tie-break is answerable by **one runtime call**.
Recorded as a correction to this entry, not quietly fixed.

**Run conditions.** Retail `Mars.exe` **1.0.7.396349**, cold load of a staged
COPY (`CORUN1.savegame.sav`) of `TEST2H TRAIN`, pack **81/81 active**, speed 3,
session uptime ~6 min, zero `[LUA ERROR]`. Raw lines:
`docs/archive/corun1_Mars.exe-20260804-12.42.47.log`.

**FORCED: the break only.** ⚠️ **And by a better route than
`CORUN_RIG_SPEC.md` §6 named.** The spec says `CheatMeteors` at a position;
`BreakTracks` (`Meteors.lua:599-607`), which is what that cheat eventually
reaches, calls `track:BreakTrackElement(element, cg)` on each element that is
neither `start_el` nor `end_el` and carries no station. The leg drives **that
site directly** on one chosen element matching the same filter — same mechanism,
no disaster thread, no collateral, lottery removed (`WORKFLOW.md` leg-design
rule 2). **ORGANIC: nothing — and no repair was measured at all**, so this
entry's own constraint (the break may be forced, the **repair** must stay
organic) is untouched.

**Why there is a tie-break to read, re-derived rather than inherited.** The
repair site **is** a `TrackGridElement` by inheritance —
`TrackConstructionSite.__parents = { "ConstructionSite", "TrackGridElement" }`
(`TrackElement.lua:580-584`) — and `BreakTrackElement` only *hides* the broken
element, leaving it on its hex (`element:SetVisible(false)`,
`Track.lua:636-639`). So both objects genuinely match the class filter.

| reading | value |
|---|---|
| control, BEFORE the break, hex `(129,450)` | `TrackGridElement#4573` — the element itself |
| the break | `TrackBase#4569:BreakTrackElement(TrackGridElement#4573)` |
| element after | `visible=false`, still on `(129,450)` |
| site after | `TrackConstructionSite#14605`, `site.broken == element` = `true`, `IsKindOf(site,"TrackGridElement")` = **`true`**, on `(129,450)` |
| **`HexGetTrackGridElement(hex_grid, 129, 450)`** | **`TrackGridElement#4573` — THE HIDDEN ELEMENT** |
| confirm, 2 s later | `TrackGridElement#4573` — same |

**Consequence, and it is the one this entry already drew.**
`process_alien_elements`' neighbour walk (`TrackElement.lua:705-711`) sees the
**broken element** on that hex, so a completing neighbour absorbs it
(`:729`, `:737`) and leaves the original track a husk — the drain that empties
`elements` before `:803`. The route stands, now on a measurement instead of on
seven crashes.

⛔ **What this does NOT do.** It does not touch reachability. No-cheat
reachability stays **UNPROVEN**, FIX_POLICY §4 still bars building, §4a WHO
BENEFITS is still unsatisfied, and the entry stays **`cand`**. One hex, one
break, one save.

**This reading is wrong if:** the same read on a hex where the site was placed
*before* the element was hidden returns the site — i.e. if the tie-break is
insertion-ordered rather than class-ordered. **Not tested**, and worth one line
in any future sitting that has damaged track.

### Severity, both directions (2026-08-03)

- **Milder than filed: the auto-connect self-heals.**
  `g_ConstructedTracksQueue[track_obj] = GameTime() + 500` lands at `:799`, one
  line BEFORE the throw; the `ConstructedTracksCheck` repeater (`:677-693`)
  redoes the identical work 500 ms later WITH the guards this block is missing
  (`#track.elements > 0`, a re-check between the two calls, plus
  `TryConnectStations()`). The engine shipping a correctly-guarded copy of
  lines 803-806 is also the clearest statement of what a fix should look like.
- **Milder: on a clean build-out the un-run `table.clear(repair_cgs)` is a
  no-op** — `repair_cgs` is only populated by `Meteors.lua:609` and
  `TrainDisasterHandling.lua:58-59`. When it IS populated the damage is real
  and persistent: it is a persisted member (`Track.lua:41`), and non-empty
  means the track reports damage (`Track.lua:382`) and refuses deletion
  (`Track.lua:372`) until something clears it.
- **Worse than filed: each throw escaped the console `exec`** — the rest of
  that `MapForEach` pass and the second `for i=1,2` pass never ran, and
  `CurrentMap:ResumeTerrainInvalidations("cheat_all_constructions")`
  (`Cheats.lua:128`) was skipped — a leaked suspend, seven times over. Cheat-tag
  scoped, so no non-cheating player is affected.
- **The `F99RESIDUE 0 0` reading is NOT evidence of no damage** — it was taken
  after a reload, and load runs `SavegameFixups.RebuildBrokenTracksAndConnect`
  (`TrackElement.lua:824-837`), which sweeps exactly what the probe looks for.
  Re-run BEFORE a reload (rider on the checklist).
