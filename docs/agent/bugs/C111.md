### C111 — "Moving to a new Dome" names the dome the colonist lives in (P3) `[fixed 2026-09-24 on hubset: wording owner-approved; owner watched it work in 07B; pending audit]`

#### Must_Read_Header

The independent [cross-check](../reports/MIGRATION_CROSSCHECK_2026-09-24.md) confirms the display
mechanism, not the reporter's complete journey. Its recommendation to drop a cosmetic repair is
withdrawn by the 2026-09-24 resweep (dated section at the end): the text is fixed with the hub set.
The guard described below is outcome-redundant, not unreachable.
The 07 sitting REFUTED the first fix on its one live subject (see the dated sitting section); 06B found the cause.
The 07B pass saw the re-fix `e5fc0c6` work: the owner watched "Returning to Dome: Brussels". The owner approved the wording on 2026-09-24.

#### Report

Steam, 2026-09-24 (TheGodUncle): "my colonists decided they needed to move to a new dome, which
is the same dome they live in". Filed from the migration audit
([MIGRATION_AUDIT_2026-09-24.md](../reports/MIGRATION_AUDIT_2026-09-24.md), N3), which finds this is
what every foot migration shows, not a wrong destination.

#### Source (archived 1.1.1.405907; all lines cleared)

- `Colonist:TransportByFoot(dest_dome, passage_path)` sets `self.emigration_dome = dest_dome`,
  pushes its destructor, and calls `self:SetDome(dest_dome)` before any passage hop or Goto
  (`Lua/Units/Colonist.lua:3835-3841`). `SetDome` calls `SetWorkplace(false)` and
  `SetResidence(false)` for the old dome at once (`:437-438`).
- The infopanel Dome line reads `self.dome` through `GetDomeDisplayName` (`:4446-4450`); the status
  line's dome comes from `GetEmigrationDomeDisplayName`, which returns `self.emigration_dome or
  self.transport_task and self.transport_task.dest_dome` (`:4462-4465`).
- `Getui_command` (`:4672-4716`) returns the "Moving to a new Dome" text for `Transport`,
  `TransportByFoot` and `MigrateStep` when `self.emigration_dome` is set (`:4676`); when it is not,
  the chain reaches `else return tcommand or ColonistCommands["Unknown"]` (`:4713-4714`), the same
  text. The guard cannot change the output.
- So for the whole of a foot walk, the Dome line and the status line name the same dome. A rescue
  ride home (`Lua/Units/ColonistTransport.lua:464-471`: `CreateColonistTransportTask(self, false,
  home)` with `home = self.dome`) can show "Moving to a new Dome: <home>" by the fallback to
  `transport_task.dest_dome`; a stale `emigration_dome` takes precedence if present.
- `TransportByFoot` is unchanged from 1.1.0 (seat B inventory), so the display predates 1.1.1; the
  new multi-leg journeys and the pack's passage routing lengthen the walks and so the window.

Intent evidence (FIX_POLICY §4): an outcome-redundant guard and code contradicting its own
player-facing text (tell 6): the text says "new" for the dome the panel says the colonist lives in.

#### Harm

Cosmetic, but it reads as a bug to every player who opens a migrating colonist, and it produced a
field report attributed to the pack. No colonist is harmed.

#### Reach

R1: every foot migration, every rescue ride home, every stranded return.

#### Control

Open the infopanel of any colonist in `TransportByFoot`.

- **Supports:** the Dome line already names the destination while the colonist is still walking.
- **Refutes:** the Dome line names the origin until arrival.

#### Fix shape (owner decides)

A pre-wrapper on `TransportByFoot` could record origin in weak memory and tail-delegate (layer 2);
synchronous getter and `SelectDome` wrappers would both need to use it. The latter prevents a
displayed origin hyperlink selecting the destination. Midwalk reload loses the marker and reverts
to vanilla. Prefer, if this cosmetic work is ever chosen, neutral command-text table surgery
(§1.3, no blocking frame), preserving the destination hyperlink and respecting §6 localisation.
