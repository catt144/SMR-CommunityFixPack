### C103 — Open Domes stops passages being placed where dome trees stand (P3) `[cand 2026-09-17: owner-observed; cause not isolated]`

#### Report

Discord, 2026-09-16 (Triel the Wikishark): *"Tree block passage build. Open dome has much less
impassable slots where you can build passages"*, with a screenshot of an **Open City** showing
"Blocking objects" over its trees.

#### Observed (owner, 2026-09-16, game 1.1.0.403908)

In an ordinary dome, a passage was built on hexes where trees stand **before** the domes were
opened. After Open Domes, the placement cursor on the same kind of hex reads **Blocking objects**,
and the passage built earlier still stands. ⚠️ The save carries SMRTK cheat use; the domes were
opened with the game's Open All Domes cheat, not by terraforming. That route sets every
terraforming parameter to 100% and enacts the law (`Data/CheatDef.lua:1036-1052`). ⛔ SMRTK's
"Open all domes" leaf was NOT that route when this was written: it called the Lua `OpenAllDomes()`,
which only makes the glass transparent (`Lua/Buildings/Dome.lua:4034`) — `Dome:IsOpen` is defined as
"is the glass invisible" (`:1641-1645`), so that function carries no atmosphere, passage or colonist
behaviour at all, and the law is where the state lives.

⇒ **2026-09-17: the leaf now IS that route**, so this entry's control can be run. On the owner's
ruling the leaf was rebuilt to inline the cheat body — every terraforming parameter to 100%, then
`Policy_OpenDomes:Activate()`, then `OpenAllDomes()` — with vanilla's `NoTerraforming` and
`NoPolitics` guards kept (TestKit `82d4577`). ⚠️ Un-witnessed caveat carried over from that build:
`Dome:UpdateOpenCloseState` applies the visual open only `if not GetOpenAirBuildings(self:GetMap())`
(`Dome.lua:1770-1780`), so if the glass stays shut while the law reads active, that gate is the
reason and is itself a finding. ⛔ Terraforming to 100% is a world change — use a save kept for
this test only (owner ruling, same day).

#### Source (1.1.0 unless stated)

- A passage hex is refused by `GridConstructionController:CanExtendFrom`'s `passage_grid` branch
  (`Lua/Construction/GridConstruction.lua:586-618`), then `TestDomeBuildabilityForPassage`
  (`Lua/Passage.lua:384-437`). Reasons `dome` (edge connector refused), `roads` (hex not a subset
  of `dome:GetBuildableAreaShape()`) and `destroyed` all fall to `GetBlockingObjectsStatus()`
  (`GridConstruction.lua:1045-1058`). **The label does not mean an object blocked it**, and the
  obstructor tint then colours nearby objects, so a red tree is not proof.
- `Dome:GetBuildableAreaShape()` is `GetEntityBuildShape(self:GetEntity())` (`Dome.lua:1080`), and
  `Passage_IsShapeHexPoint` caches outline shapes by entity (`Passage.lua:2514-2530`). Open Domes
  swaps every dome to its `_Open` entity (`SetOpenAirBuildings`, `OpenAirBuilding.lua:108-165`;
  EF-061). ⇒ If an `_Open` entity's Build surface leaves out its tree hexes, those hexes fail as
  `roads` once the law is on.
- `TestDomeBuildabilityForPassage` is unchanged from 1.0.7 apart from whitespace. The
  `passage_grid` branch gained a full obstructor scan in 1.1.0 (1.0.7 had `--TODO: blocking
  units`), gated on `IsValid(self.template_obj)`. `template_obj` is "the building definition
  table" (`Lua/Construction/Construction.lua:822`).
- Open City: `PassageEdgeConnectorAllowed = false` in both 1.0.7 and 1.1.0
  (`Lua/BuildingTemplate/OpenCity.generated.lua`), as for the Geoscape Dome. It has no edge
  connections by design; that half of the Discord complaint is not this defect.

#### Measured (log `Mars.exe-20260916-23.13.48-6a91a190.log`)

- Line 725, cursor read in passage mode: `passage_grid false false requires_dome`.
  ✅ **`IsValid(template_obj)` = false**, so the 1.1.0 object scan did not run. ⚠️ The reason
  `requires_dome` renders "Dome required", not "Blocking objects", so the cursor was not on the
  refused hex. **Do not use this reason.** Line 726 lists the only colour-obstructor as
  `DomeMedium` / `DomeMedium_Open`.
- Lines 790-796, a per-dome tally of `CanExtendFrom`. Every entity printed **without** `_Open`
  (`DomeMega`, `DomeMedium`, `DomeBasic`), so the domes were closed then. ⛔ **It says nothing about
  the open state.** Its `obstructed` counts are existing buildings (`HexGetBuildingNoDome`).

#### Control — not yet run

With the domes open (`OpenAirBuildings` true), take the passage built before the law on the tree
hexes. Run the shape test on its own in-dome pieces, so the standing passage cannot count as an
obstruction:

```
*r local g=MainMap.object_hex_grid MapForEach("map","PassageBase",function(p) for i,e in ipairs(p.elements or {}) do local d=GetDomeAtHex(g,e.q,e.r) if d then local ok,why=TestDomeBuildabilityForPassage(g,e.q,e.r,"check_edge","check_road") print("SMRPASSAGE3", p.handle, i, e.q, e.r, d:GetEntity(), OpenAirBuildings, ok, why) end end end)
```

- **Supports the hypothesis:** the tree-hex pieces read `false roads` (or `false dome`) under an
  `_Open` entity, and `true` for the same pieces with the domes closed.
- **Refutes it:** they read `true` while open. Then the refusal comes from another branch, such as
  `HexGetBuildingNoDome` returning a non-dome building on the hex.
- **Vacuous if:** `OpenAirBuildings` prints false, or the entity has no `_Open` suffix.

A cheaper desk check needs no game: compare `GetEntityBuildShape("DomeMedium")` with
`GetEntityBuildShape("DomeMedium_Open")` hex by hex.

#### Reach

Every 1.1.0 player who reaches Open Domes and then wants a passage on a tree hex. Nothing here is
platform-specific. Workaround: other hexes of the same dome still accept passages.

#### Not opened

Whether the smaller area is deliberate (open-dome trees placed where the art expects no
connection) or a mismatch · whether buildings, not only passages, lose those hexes under `_Open`
· what a passage built before the law does to the trees when the law switches on · the Open City's
own tree hexes · every `_Open` entity other than `DomeMedium`.
