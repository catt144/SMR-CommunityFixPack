### C99 — A hub-connected Passage can become permanently undismantlable, blocking dome replacement (P2) `[cand 2026-09-15: blocking loop SOURCE-VERIFIED; the sticking clause NOT isolated; NOT reproduced; NOT ours]`

⛔ **NOT REPRODUCED.** The blocking loop and its predicate are read from source. **No stale state was
measured**, and which clause sticks on this player's colony is not established.
⛔ **NOT OURS.** MEASURED: `grep -rn "Passage" Code/` returns two files — a prose comment in
`Fix_TrackSalvageRefund.lua:39-40` citing `PassageBase:OnDemolish` as a *contrast*, and
`Fix_VacuumWalks.lua`'s use of `GetDomesPassagePath` for colonist routing. No module wraps passage
demolish, `WouldStrandHubColonists`, or anything a hub touches.

⚠️ **P2 because it is a progression blocker, not a cosmetic one** — the reporter cannot replace an
outgrown dome, which is a core mid-game action with no in-game workaround offered.

#### The report (INHERITED, not verified)

Steam, **Jäger**, 2026-09-14, comment #8 (the post shows as edited), owner-relayed screenshot:

> *"I've discovered a bug in my current game: connection tunnels (Dome) that are connected to a
> 'connection hub' can no longer be dismantled. You can click on 'Dismantle' – the red light flashes
> and then disappears – but nothing else happens; the drones don't react.*
>
> *The game has already progressed quite a bit; when I try to replace a dome that's become too small,
> I can't disconnect anymore."*

"Connection hub" is **`PassageHub`** (`Lua/PassageHub.lua`, `Data/BuildingTemplate/PassageHub.lua`);
this project already uses the term in [[F62]]. The "red light" is the `RotatyThing` lamp attached in
`PassageBase:OnSetDemolishing` (`Lua/Passage.lua:1092-1110`) and destroyed in that same function's
`else` arm — so the light appearing and going is the demolish flag being set and then cleared.
⛔ **What clears it is NOT established.** No log, no save, no mod list, no version supplied.

#### The blocking loop — where a dismantle order goes to die

`PassageBase:OnDemolish` (`Lua/Passage.lua:1162-1184`):

```lua
self.demolishing = true
local hub = self:GetConnectedHub()
if hub then
    self.hub_draining = hub
    hub.draining_passages = hub.draining_passages or {}
    hub.draining_passages[self] = true
    -- last exit of the hub: keep the tunnel connected until everyone inside or inbound has left
    while self:WouldStrandHubColonists() do
        WaitWakeup(1000)
    end
end
self.CanDelete = ret_false
self.cleanup_on_disconnect = true
self:DisconnectDomes()
```

⭐ **The wait sits BEFORE `DisconnectDomes` and before any salvage work.** A permanently true predicate
leaves the passage flagged `demolishing`, still connected, with **no drone ever dispatched** — the
reporter's "nothing else happens; the drones don't react", exactly.

⚠️ **The guard is not wrong in intent.** It exists so the hub's last exit stays usable until everyone
inside or inbound has left. The defect shape is a predicate that never goes false, not a needless gate.

#### The predicate, and the four ways it can stick

`PassageBase:WouldStrandHubColonists` (`Lua/Passage.lua:1130-1151`) returns **false** early — safe to
demolish — if any *other* passage on the hub `IsPFTunnelActive()`. Otherwise it returns **true** if any of:

| # | clause | why it could stick |
|---|---|---|
| 1 | `#self.traversing_colonists > 0` | a colonist genuinely stuck mid-traversal |
| 2 | `#(hub.units or empty_table) > 0` | ⭐ **stale container entry — the [[C42]] shape** |
| 3 | a sibling in `hub.draining_passages` with traversing colonists | mutual waiting between passages |
| 4 | `MapHasAny(hub, hub:GetRadius()*2, "Colonist", c.passage_hub == hub)` | a stale `passage_hub` marker |

⭐ **Clause 2 is the one to look at first.** [[C42]] is filed on precisely this shape — passage traversal
clearing `unit.holder` directly and leaving a stale entry in a passage container **forever**. C42 has
stood since 2026-08-03 as `filed`, source-only, **explicitly unobserved with nothing built**, and its
own measurement leg sampled a population of zero and so settled nothing. ⇒ **This report is a candidate
first field symptom for C42.** ⛔ INFERRED — C42 documents `el.units` on a passage *element*; that the
same mechanism populates `hub.units` is NOT traced here.

⭐ **Clause 4 is self-incriminating in the shipped comment.** The source says, above that line:
*"interrupted units are dumped from the holder onto the hub surface with unit.passage_hub still
marking them"*. The engine authors knew interrupted units keep the marker; nothing here proves it is
ever cleared for a colonist that never re-enters a passage.

⭐ **Clause 3 admits a mutual-wait reading worth testing.** A player replacing a dome plausibly marks
**several** hub passages for salvage at once. Each demolishing passage stops being an active tunnel,
so for each one the "another passage is still active" escape at the top fails, and each then waits on
the others through `draining_passages`. ⛔ NOT TRACED — whether `IsPFTunnelActive` actually goes false
on a demolishing passage was not checked, and it is the hinge of this reading.

#### Control — what we can settle ourselves, in order

⛔ **A reporter's save is the LAST resort here, not the first move.** Three cheaper routes come first
and none of them costs a player anything. Work them before a save is even considered.

**1 · Two of the four clauses are pure SOURCE questions.** Neither needs a running game, let alone
someone else's colony:
- does `IsPFTunnelActive` return false for a passage already marked `demolishing`? That alone decides
  the clause-3 mutual-wait reading.
- what clears `colonist.passage_hub`, and does any path clear it for a colonist dumped on the hub
  surface who never traverses again? That decides clause 4.

**2 · A TestKit probe reads the rest directly off a live game — this is exactly what the kit is for.**
`hub.units`, `hub.draining_passages`, each passage's `traversing_colonists`, and a sweep for colonists
carrying `passage_hub` are all plain container reads on a hub we build ourselves. ⭐ **[[C42]] already
ships a measurement recipe (`C42STALE`) for the element-level version — extend it to hubs rather than
inventing one.** C42's own leg sampled a population of zero, so it needs real traffic regardless; one
probe can serve both entries.

**3 · In-game separation on our own colony**, if the state can be reached at all:

| observation | clause it points at |
|---|---|
| dismantling a **single** hub passage works while dismantling several at once does not | 3, the mutual wait |
| one lone passage will not dismantle even with every sibling untouched and active | 1, 2 or 4 — the early escape should have fired, so the hub genuinely believes someone is present |
| a colonist is visibly standing on the hub | possibly legitimate, not a defect |
| nothing visible anywhere near the hub | 2 or 4 — a stale marker with no real colonist |

**4 · Only if all three come up empty** does a reporter's save become the route. ⛔ Even then it is
PULL-ONLY (`WORKFLOW.md` rule 5b, ck165): nothing is drafted, nothing goes on an owed list, and it is
never a nudge. ⚠️ **Asking a player for a save has a real cost** — owner's ruling 2026-09-15: players
are generally not comfortable sharing them and the request confuses non-technical users. The desk work
and the kit exist so this ask stays rare; spending it casually spends what they were built to protect.

#### Not opened

Whether `hub.units` is populated by the same route [[C42]] describes for `el.units` — the one trace

`colonist.passage_hub`, and whether any path clears it for a colonist dumped on the hub surface who

the loop sleeps 1000ms and relies on both · the reporter's build, mod list and whether the colony came
