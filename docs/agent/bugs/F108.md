### F108 — Extractor AI caps STAFFED extractors at 50, locking Russia's 160-Performance sponsor goal (P3, high behavior-confirmed)  `[fixed 2026-08-28: Code/Fix_ExtractorStaffedPerformance.lua — attended A/B, both controls witnessed]`

## The field report (Steam Workshop, 2026-08-28)

A player on a Russia playthrough reported that the breakthrough **Extractor AI**
— which "decreases an extractor's performance to 50 when not staffed" — applies
that 50 **even when the extractor IS staffed**, so the Russia sponsor goal of
"3 extractors with 160 performance" can never be completed once the breakthrough
is researched. The report is correct in every particular, and the mechanism was
already on file as supporting analysis under **F36** (a different symptom — see
below). This entry files the performance cap itself, which the pack did not fix.

## The mechanism (SOURCE — `Src` 1.0.7.396349)

1. **Extractor AI** (`Data\TechPreset.lua:1050-1075`, `id = "ExtractorAI"`,
   `param1 = 50`) applies `Effect_ModifyLabel automation = 1` **and**
   `auto_performance = 50` to the **MetalsExtractor** and **PreciousMetalsExtractor**
   labels. Its description scopes the 50 to unmanned use verbatim: *"Metals
   Extractors and Rare Metals Extractors can work **without Colonists** at 50
   Performance."* `OnResearched` also sets `g_ExtractorAIResearched = true`.
2. `Workplace:GetWorkshiftPerformance` (`Lua\Buildings\Workplace.lua:184`) returns
   `self.auto_performance` **outright** on an early branch whenever
   `self.automation > 0` (`:197-199`) — ABOVE the per-worker loop at `:219-228`.
   So for any extractor carrying the label, performance is a flat 50 regardless of
   workers, overtime or performance-boosting techs/upgrades. `UpdatePerformance`
   (`:242`) writes that 50 straight into `self.performance`.
3. The tech's text says the 50 is the *without-Colonists* number; the code applies
   it *with* Colonists too. That is the whole defect: **the automation flag —
   built for genuinely unmanned buildings — is bolted onto a building that keeps
   its four worker slots**, so the flag's "ignore workers, use auto_performance"
   semantics discard staffing on a still-staffable building. (Contrast the
   automatic, never-staffed `AutomaticMetalsExtractor`, which is `OutsideBuildingWithShifts`,
   not a `MetalExtractorWorkplace`, and for which a fixed cap is correct.)

## The sponsor-goal chain (why it locks a milestone)

* Sponsor **Roscosmos** (`Data\MissionSponsorPreset.lua`, `id = "Roscosmos"`,
  `display_name = "Russia"`) carries `sponsor_goal_4 = "ExtractorPerformance"`
  with `goal_4_param_1 = "3"` and `goal_4_param_2 = "160"`.
* The goal `ExtractorPerformance` (`Data\SponsorGoals.lua:467-492`) loops the
  `MetalsExtractor` / `PreciousMetalsExtractor` labels and counts extractors with
  `extractor.performance >= 160`.
* Once Extractor AI is researched, `extractor.performance` on every one of those
  labels is capped at 50 < 160, so the count can never reach 3. A breakthrough is
  irreversible, so the goal is **permanently unreachable on that save.** Achievable
  normally (staffed + boosted) only if the player never takes the breakthrough —
  a choice whose consequence the game never surfaces. This is an integration
  oversight (two systems, incompatible assumptions about the same labels), not a
  deliberate tradeoff; owner analysis 2026-08-28.

## The fix — BUILT + VERIFIED 2026-08-28 (owner ruling: FLOOR, not ceiling)

`Code/Fix_ExtractorStaffedPerformance.lua`. A **§1.4 chained post-wrapper** on
`Workplace:GetWorkshiftPerformance`: for a STAFFED `MetalExtractorWorkplace` with
`automation > 0`, return the greater of the worker-based performance and
`auto_performance`. 50 becomes a guaranteed **floor** for unmanned operation
instead of a hard **ceiling**.

* **Post-wrapper, deliberately NOT a body copy.** `GetWorkshiftPerformance` is
  already wrapped by `Fix_AutomationLawCompensation` (C39); a full-body
  replacement (the F36 style) would clobber that wrapper depending on load order
  (the §1.4b warning). The two are orthogonal and compose in either order: C39
  returns a 0 delta for `automation > 0` (its `:175` guard), this module acts
  ONLY on `automation > 0` extractors, and both call `orig`.
* **§1.5 reconstruction disclosure.** `staffed_performance()` reproduces vanilla's
  per-worker loop (`Workplace.lua:219-228`) + overtime additive (`:230-233`) at
  `law_scale = 100` — extractors are `Mine`/`ExtractorWorkplace`, never
  `Factory`/`ResearchBuilding`/`Service`, so vanilla's law lookup (`:204-206`)
  returns nil and law_scale is always 100 for them. Re-check that loop against
  `Src` on every game update; `orig` still runs in full on every call.
* **Scope** = `IsKindOf("MetalExtractorWorkplace")`, the common Workplace ancestor
  of both staffable extractors (`MetalsExtractor.lua:21`, parent of
  `MetalsExtractorBase` and `PreciousMetalsExtractorBase`). Every other automation
  building — drone-run buildings, automation-law buildings, the always-unmanned
  `AutomaticMetalsExtractor` — is untouched, so a fixed cap that IS intended stays.
* **No info-panel patch needed.** Extractors have `max_workers = 4`, so
  `GetPerformanceReasons` (`Workplace.lua:263-278`) uses the "Workshift workers"
  branch, not the "Automation +auto_performance" branch (that fires only at
  `max_workers == 0`) — the panel already reads the corrected number.
* **§3a save-safety: Layer 2, nothing persisted.** Synchronous, no yield, no table
  kept, no function stored on any object, no GameVar/modifier/thread. Lives in a
  class table, which savegames do not serialise. Remove the mod → vanilla on next
  load, nothing to clean up.
* **Not a buff into a free lunch.** To exceed 50 the player still pays the full
  geologist cost — identical to a player without the breakthrough. The fix removes
  a silent trap the tooltip never warned about; it does not remove the tech's cost.

## The verification — MEASURED ATTENDED, 2026-08-28

`docs/archive/f108_attended_Mars.exe-20260828-16.41.41.log`. Owner at the
keyboard; module confirmed loaded (`[CommunityFixPack] ExtractorStaffedPerformance:
applied`, `[active]`). One fully-staffed Metals Extractor, read before and after
researching the breakthrough (same extractor, same upgrades, selection held):

```
F108 BEFORE  MetalsExtractor  auto=0  auto_performance=0   max_workers=4  workers=12  perf=119
F108 AFTER   MetalsExtractor  auto=1  auto_performance=50  max_workers=4  workers=12  perf=122
```

* `auto` 0 → 1 and `auto_performance` 0 → 50 = Extractor AI genuinely applied —
  the exact state that pins vanilla to 50.
* `workers` stayed 12 = researching the breakthrough did NOT unstaff it (the one
  open uncertainty in the fix design; resolved — a player who staffs before
  researching keeps their workers).
* `perf` held at 122, did NOT collapse to 50. The only code path yielding > 50
  while `automation = 1` is this wrapper, so this is dispositive. The 119 → 122
  drift is live colonist-stat wobble between reads, in the right direction.

⭐ **Mirror control**, witnessed on the panel (owner is the attended witness): a
neighbouring Metals Extractor with **all work spots blocked**, automation on, read
**Building performance = 50** — production 10/Sol, the tech's advertised
"works without colonists at 50". Both halves proven: staffing wins, floor holds.

⭐⭐⭐ **The full field route completed, end to end (same day).** Not planned — the
owner pushed three staffed extractors to ≥160 (workers given the **Workaholic**
trait via `AddTrait` + maxed **Comfort**; **no Genius**, Amplify upgrade), and the
Roscosmos **`ExtractorPerformance`** goal ticked **3/3 and COMPLETED**, its
`+40% Rare Metals price` reward granted. This is the exact scenario the field
report said was impossible — a Russia save with Extractor AI researched — closed
end to end, not merely at the mechanism level. It also shows the goal is no
punishing optimisation once the cap is gone: ordinary good workers (Workaholic,
high satisfaction) clear it, which is what the goal was always meant to require.
