## 2026-09-11 — the deferred notification RIDES IN THE PLAYER'S SAVE; both outcomes checked and benign

Not covered by the build or the audit, and `FIX_POLICY` §3a is exactly about it.
The repair parks a one-shot `CreateGameTimeThread` between the vacancy and the
notification, and **game-time threads are persisted into the savegame by default**
(`CommonLua/Core/cthreads.lua:481-517` serialises every thread carrying
`threadPersist` with its sleep state; `:519-524` restores them; real-time threads
must opt in via `MakeThreadPersistable`). ⇒ **a save taken inside that one-tick
window captures a thread pointing at `notify_freed_home`.** The module's author
reasoned about upvalues — the right worry — but the thread itself being saved went
unchecked.

**SOURCE — both outcomes are benign, so §3a holds:**
1. **If the closure is persistable**, it is restored with the save. A load *without*
   the mod then resumes it, and the orphan gate `if not SMRFixPack then return end`
   — the first statement after the only yield — is exactly the right guard.
2. **If it is not**, the engine substitutes `__unpersisted_function__`
   (`CommonLua/Core/persist.lua:52-54`), whose body is `assert(false, "Unpersisted
   function!")`. By `EF-008` an assert does not unwind, so the thread simply ends:
   the notification is lost and the bed waits for the next heavy update — i.e. it
   **degrades to vanilla behaviour**, which is the correct failure direction.

⚠️ **Which of the two actually happens is NOT established** — no save was taken in
the window and no load was observed. It does not need to be, because both are safe;
record it as unmeasured rather than assuming (1). ⚠️ The window is one tick, so a
capture is unlikely but not impossible — autosaves are not synchronised with it.
⛔ Nothing here asks for a change to the repair. Rule generalised in `FIX_POLICY` §4.
