### C74 — the Rare Metals Extractor's hammer strikes with no sound or steam: zero `Hit` moments on its working animation (P3, cosmetic, vanilla) `[filed 2026-09-10: MEASURED attended; fix = checklist 139]`

**Field report (Steam, relayed by the owner 2026-09-10):** *"The Rare Metal
Extractor's hammer doesn't make a sound, even though there was one in the
original."* (the original = Surviving Mars, 2018).

#### Two skins — only one of them is defective

The building has two models (`Data/BuildingTemplate/PreciousMetalsExtractor.lua`
1.1.0): `entity = "UniversalExtractor"` (`:34`, the **hammer** rig — the
build-menu icon) and `entity2 = "RareMetalExtractorCP3"` (`:35`, a **spinning
drill**). `alt_entity_2_sponsor` (`:4-12`: BlueSun, Brazil, NASA, Roscosmos,
SpaceY, Japan, ISRO) makes the drill *"the default during placement"* for
those sponsors (field help, `Lua/Buildings/Building.lua:333`; applied at
`Lua/Construction/Construction.lua:1004-1012`). Both skins are offered
(`GetBuildingSkins`, `Building.lua:3429-3458`; `entitydlc2` defaults to `""`,
`:328`, and `IsDlcAvailable("")` is true, `CommonLua/Dlc.lua:76`), and a
finished building shows a **Change Skin** infopanel button
(`Lua/XDef/Infopanel.generated.lua:489-513`; `Building` inherits
`SkinChangeable`, `Building.lua:179`) — ROUTE WALKED by the owner.
- **Drill skin — not a defect.** It never strikes by design: the developers
  gave it its own continuous `start`-moment steam (`UniversalExtractor_Steam_02`
  targeting `RareMetalExtractorCP3Drill`, `Data/FXPreset/ActionFXParticles.lua`
  1.1.0 `:~1910-1926`) and no drill-targeted sound. Measured:
  `RareMetalExtractorCP3Drill working 0`.
- **Hammer skin — the defect.** The hammer visibly strikes; no strike sound
  and no steam puff ever play.

**Screenshots (owner, 2026-09-10, 1.1.0, NASA colony)** in
`agent/reports/c74_skins/` (1920-px web copies; full-res originals kept outside
git at `C:\Dev\SMR-ScreenCaptures\c74_skins\`): `01_drill_skin_CP3_sponsor_default`
(the placed default), `02_change_skin_button_2_skins` (the infopanel button,
*"Cycle through all 2 skins."*), `03_hammer_skin_UniversalExtractor` (after the
switch). ⚠️ All three show the infopanel's **Cheats** section (normal on a
playtest save) — crop or recapture before any public use.

#### MEASURED, attended (owner at the keyboard, 1.1.0.403908, NASA colony, 2026-09-10)

Console readout on a working hammer-skin extractor (screenshot):
`UniversalExtractorHammer working 0` and `hit thread live:` blank — the
tracker thread is dead (`IsValidThread` returns no value, `EF-031`). The same
readout on the drill skin is in the log
(`Mars.exe-20260910-11.21.03-6a91a190.log:198-205`, `sponsor: NASA` at `:174`).
Then `PlayFX("Working", "hit-moment1", building, hammer)` fired BY HAND
produced **both the strike sound and the steam puff** (owner heard and saw
them). **CONTROL (non-vacuity):** the same line on the drill skin — where
`GetAttach("UniversalExtractorHammer")` finds no hammer — plays nothing, so the
positive is the target-gated FX firing as authored, not a sound the command
would play regardless. The only other audio on either skin is the continuous
working loop (`Object PreciousExtractor Loop`, `Target = "ignore"`,
skin-independent).

⇒ **Cause MEASURED:** the shipped `UniversalExtractorHammer` `working`
animation draws its strikes but carries **zero `Hit` moments**, so
`BaseBuilding:TrackMultipleHitMoments` exits silently at 1.1.0 `:1046-1049`.
Everything downstream is proven sound by the hand-fired FX.

#### The chain (identical in 1.0.7.396349 and 1.1.0.403908 — PASSING, not diff-caused)

- Class: `PreciousMetalsExtractorBase` declares
  `track_multiple_hit_moments_in_work_state = {"hit-moment1", "hit-moment2",
  "hit-moment3"}` (`Lua/Buildings/MetalsExtractor.lua` 1.1.0 `:22-25`, 1.0.7 `:32-35`).
- `BaseBuilding:ChangeWorkingStateAnim` gives `working` and the tracker to the
  first object with that state — the hammer (1.1.0 `:889-952`, 1.0.7 `:581-644`).
- Authored FX, all `Target = "UniversalExtractorHammer"`: 8 `ActionFXSound`
  (`LoopPeaks` + `LoopSmoke`, hit-moment1..4, 1.1.0 `:17156-17248`, 1.0.7
  `:19034-19126`) and 3 `ActionFXParticles` (`UniversalExtractor_Steam`,
  hit-moment1..3, 1.1.0 `:860-932`). Presets resolve (`Data/SoundPreset.lua`
  1.1.0 `:13102`, `:13113`); samples ship (`Sounds.fpk`:
  `extractorUniversal_workpeak5.opus` 23,042 B, `_worksmoke1/2`).
- ⚠️ 1.0.7's ANIMATION asset is not archived (only Src is), so whether 1.0.7
  shipped the same untagged animation is not established; the reporter's
  original-game memory is unverified (the original is installed, `.hpk` packs
  our tools cannot open).
- ⛔ Instrument limit, stated: our tools cannot read moment tables — no
  readable `Hit` in any `.hgacl` or `BinAssets/entities.dat`, controls included.
  The cause rests on the console measurement alone.

**Our pack is not involved:** zero hits for the whole path in `Code/` and the
TestKit's `Code/`.

**Reach:** every hammer-skin Rare Metals Extractor — the default for every
sponsor NOT on the list above, plus anyone who switches skin. Base game, no DLC.
Cosmetic only: production, maintenance and dust are unaffected.

**Fix route — owner decision (checklist 139).** The FX work when driven, so a
pack module COULD drive them: when the hammer's `working` animation reports 0
`Hit` moments, fire the hit-moment FX at the strike phases of each loop.
TAKEABLE WHEN the strike phases are measured (unreadable from the asset; needs a
runtime timing readout an agent designs first). Save-safety per `FIX_POLICY`
§3a: vanilla already stores this tracker as a game-time thread
(`track_multiple_hit_thread`), and a mod-authored game-time thread persists into
saves (`EF-019`, `EF-023`) — the fix shape must stay inside that existing
thread or be provably uninstall-clean. The true repair (a `Hit`-tagged
animation) is the developers'.

**Falsifier:** a later build where the readout shows `UniversalExtractorHammer
working` with a count above 0 and strikes are heard — then vanilla fixed it.
