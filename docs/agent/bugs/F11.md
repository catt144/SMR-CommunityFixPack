### F11 — Train wedges at platform (`table.remove` misuse)  `[fixed: Code/Fix_TrainPlatformWedge.lua]`

`Lua\Units\ColonistTransport.lua:541-547` (`ExitVehicle` stale-passenger guard) —
`table.remove(vehicle.units, self)` needs an integer pos; intended API is
`table.remove_entry`. When the guard fires (dev comment: CargoTransporter abduction),
the error aborts before `DiscardTransportTicket`; `Train:UnloadTrain`
(`Units\Train.lua:443-453`) then spins forever → train permanently blocks platform.
**Fix:** PRE-wrapper on `Colonist.ExitVehicle` — repaired guard branch
(`table.remove_entry`), tail-call the captured original otherwise. Converted
2026-08-03 from a §1.5 full copy; see the conversion block below, including the
verification still owed.

### ⛔ Route error corrected 2026-08-03 — the old citation was the wrong class in the wrong file

The 2026-07-30 block cited `CargoTransporterNew.lua:221-234` at path
`Lua\Units\`. Both wrong. The file is `Lua/CargoTransporterNew.lua` (no `Units/`),
and **`CargoTransporterNew` is a separate class that expedition rockets never
touch**: `RocketExpeditionBase.__parents = { "SupplyRocketBase", "CargoTransporter" }`
(`RocketExpedition.lua:1-2`) and `RocketExpeditionBase:GatherAvailableColonists`
statically calls `CargoTransporter.GatherAvailableColonists` (`RocketExpedition.lua:493`).
The live busy-colonist fallback is **`Lua/Buildings/CargoTransporter.lua:272-285`**.
The two implementations differ (the `New` one lacks `transfer_available`, adds an
`IsDead()` check, and prefers `self.cargo_request_passengers`). The old block's
*conclusion* — that crew-gathering takes busy colonists including riders — survives
in the correct file; the route to it did not. This is the failure mode the project
already has a name for, and it is recorded rather than quietly fixed.

### Owner witness 2026-08-03 — why expeditions APPEAR never to take busy colonists

Owner, unprompted, from their own campaign: *"Expedition waiting rockets have
never gathered busy colonists. It will leave the rocket sitting forever until you
either import a colonist that it needs from earth or train one in the university.
I have ran into this multiple times."*

**The observation is correct; the mechanism is not busy-refusal.** The busy
fallback exists (`CargoTransporter.lua:272-285`), but it is filtered by
`FilterColonistsByTrait` (`Lua/CargoTransporterNew.lua:163-194`) FIRST. When the
expedition asks for a specialization nobody on the map has, the busy pool
contributes nothing either, `GatherAvailableColonists` returns nil, and
`colonist_summon_fail` goes true (`RocketExpedition.lua:493-495`) — the rocket
sits. Cured by importing or by university training, which is exactly the remedy
the owner names. So the stall is **trait scarcity**, not busy-refusal.

Discriminator, if it is ever worth confirming: a *generic*-crew expedition
(`crew_specialization` unset → `"Colonist"`, `RocketExpedition.lua:522`) requesting
more crew than there are idle colonists should take working colonists. A generic
expedition stalling with busy colonists available would overturn this reading.

### ⛔ Corrections 2026-08-03 (f11-f99-review second-opinion chain — sealed derivation `28c253f`, adjudicated by the terminal prompt)

**Route claim narrowed.** "The measurement shows it does not drop the holder
link" was an over-claim: a post-hoc read (`holder == rocket`, `find == nil`)
cannot distinguish WHICH call cleaned `train.units`. Two candidate routes exist
in the cross-map case and both end in `Holder:OnExitHolder` →
`table.remove_entry` (`Holder.lua:36-41`): (a) `Unit:OnTransferToMapDone`
(`Unit.lua:846-851`) does `SetHolder(false)` when the holder was left on another
map — fired from C via `OnMsg.TransferToMapDone` (`_cobject.lua:166-170`); or
(b) `EnterTransporter`'s own `SetHolder(transporter)` at `Unit.lua:1209`. Route
(a) is better supported — it is what the function exists for, and
`Unit:DisembarkElevator` (`Unit.lua:930-933`) deliberately sets the destination
holder BEFORE transferring so Done won't clear it — but the Msg raise point is
inside the C-side `TransferToMap` and is not readable from Lua. **Neither route
is provable from source; the shared, settled fact is that whichever ran first
cleaned the list via the correct API.** Consequence either way: the SAME-MAP
removal path (`SetHolder` at `:1209` doing the work) remains unmeasured.

**Index argument struck.** "Index 1513 in a 1543 pool can only have come from
the append" requires `#MainCity.labels.Colonist < 1513`, and that number was
never printed. The conclusion survives via step 4 of the same sitting:
`col.city == MainCity` → `false`, plus the label invariant — `CityObject:Init`
asserts `city:GetMap() == map` (`CityObject.lua:11-17`) and both transfer edges
move label membership (`:70-81`); `Colonist:AddToCityLabels`/`RemoveFromCityLabels`
(`Colonist.lua:272-311`) act only on `self.city`. So `col ∉
MainCity.labels.Colonist`, no index needed. Caveats that make it "does not,
unless a known-buggy state exists" rather than "cannot":
`SavegameFixups.FixCityLabels2` (`CityObject.lua:89-116`) exists because shipped
saves have violated the invariant, and `ManualCityLabels` (`:83-87`) opts
classes out (Colonist is not one).

**Pool-rebuild scope.** The console rebuild reproduced only the raw
concatenation (`CargoTransporter.lua:237-251`). The shipped function then
filters `thread_running_destructors` (`:252-260`), partitions idle-before-busy
(`:262-285`), and runs `FilterColonistsByTrait` + truncation (`:270-291`).
Membership in the raw pool is established; SELECTABILITY is not, and the index
is a position in an ordering the shipped code never uses.

**Counter limits (for future counters of this shape).** `nil 6 true` also
prints if the `units` table was replaced between steps (`KickUnitsFromHolder`
nils it, `OnEnterHolder` rebuilds — `Holder.lua:11-32`) or if the colonist was
aboard a different train by the final read; `6` is not an identifier. Cheap
prophylactic next time: also print the container's identity and `#units`
immediately before the operation.
