### F11 — Train wedges at platform (`table.remove` misuse)  `[fixed: Code/Fix_TrainPlatformWedge.lua]`

`Lua\Units\ColonistTransport.lua:541-547` (`ExitVehicle` stale-passenger guard) —
`table.remove(vehicle.units, self)` needs an integer pos; intended API is
`table.remove_entry`. When the guard fires (dev comment: CargoTransporter abduction),
the error aborts before `DiscardTransportTicket`; `Train:UnloadTrain`
(`Units\Train.lua:443-453`) then spins forever → train permanently blocks platform.
**Fix:** replace `Colonist.ExitVehicle` with one-line-corrected copy (`table.remove_entry`).

### ⚖️ Settling observation DELIVERED 2026-08-03 (attended) — the abduction route does NOT produce the stale state

**The audit's open question is answered and its hypothesis is refuted.** The
2026-07-30 reachability block said the stale-passenger state "bottoms out in
engine-side `TransferToMap`… which source alone cannot settle". It has now been
settled at the keyboard, on both maps, and the answer is that **crew-gathering
abduction keeps `train.units` synced — there is no stale entry to guard.**

**Measured (owner's live campaign, session ~1h, pack ON — the fix only replaces
`Colonist.ExitVehicle`, which runs later at unload, so it cannot contaminate the
counter):**

| reading | value |
|---|---|
| rider's command while aboard | `BoardVehicle` |
| `table.find(train.units, col)` BEFORE | `1` |
| rider's index in a surface rocket's gather pool | `1513` of `1513`-plus pool of `1543` |
| `col:GetMap() == MainMap` / `rocket:GetMap() == MainMap` / `col.city == MainCity` | `false` / `true` / `false` |
| `col.holder == rocket` AFTER | `true` |
| `#train.units` AFTER | `6` |
| **`table.find(train.units, col)` AFTER** | **`nil`** |

The abduction was driven by invoking the shipped call site directly —
`col:SetCommand("EnterTransporter", rocket)`, which is verbatim the body of
`CargoTransporter:ExpeditionLoadCrew` (`Lua/Buildings/CargoTransporter.lua:300-302`)
— on a chosen target rather than one the gatherer picked. That removes the
lottery; it does not change the mechanism.

**Why the counter is honest.** `#train.units` = **6** after the abduction, so the
nil lookup is not an empty-or-nil-list artifact: the list is live and populated
and our colonist is simply not in it. `col.holder == rocket` = `true` proves the
transfer actually executed, so `nil` cannot be read as "the call did nothing".
The counter could have failed in either direction and did not.

**The mechanism, re-derived (route, not just citations).**
`EnterTransporter` (`Lua/Units/Unit.lua:1198-1211`) → `self:SetHolder(transporter)`
→ `SetHolderOnMap` (`Unit.lua:709-711`) → `holder:OnExitHolder(self)` on the OLD
holder, the train → `Holder:OnExitHolder` (`Lua/Buildings/Holder.lua:36-37`) →
`table.remove_entry(self.units, unit)` — the correct API. Both ends are real
Holders (`Train.__parents` includes `Holder`, `Train.lua:10-16`; every Building is
one, `BaseBuilding.lua:10`), so `SetHolderOnMap`'s `IsKindOf("Holder")` guard never
early-returns. The cross-map case runs `self:TransferToMap(transporter)` FIRST
(`Unit.lua:1201-1203`) — that was the suspected hole, and the measurement shows it
does not drop the holder link.

⚖️ **What this does and does not establish.** It establishes that the ONE producer
the shipped dev comment names (`--abducted by CargoTransporter?`) does not produce
the state, same-map or cross-map. It does **not** establish that `train.units` can
never go stale by some other producer. The guard remains a correct repair of a
genuine `table.remove` misuse in reachable shipped code; what changed is that its
hypothesised trigger is now measured absent.

### ⛔ Route error corrected 2026-08-03 — the old citation was the wrong class in the wrong file

The 2026-07-30 block cited `CargoTransporterNew.lua:221-234` at path
`Lua\Units\`. Both wrong. The file is `Lua/CargoTransporterNew.lua` (no `Units/`),
and **`CargoTransporterNew` is a separate class that expedition rockets never
touch**: `RocketExpeditionBase.__parents = { "SupplyRocketBase", "CargoTransporter" }`
(`RocketExpedition.lua:1-2`) and `RocketExpeditionBase:GatherAvailableColonists`
statically calls `CargoTransporter.GatherAvailableColonists` (`RocketExpedition.lua:493`).
The live busy-colonist fallback is **`Lua/Buildings/CargoTransporter.lua:272-285`**.
The two implementations differ (the `New` one lacks `transfer_available`, adds an
`IsDead()` check, and prefers `self.cargo_request_passengers`). The old block's
*conclusion* — that crew-gathering takes busy colonists including riders — survives
in the correct file; the route to it did not. This is the failure mode the project
already has a name for, and it is recorded rather than quietly fixed.

### Owner witness 2026-08-03 — why expeditions APPEAR never to take busy colonists

Owner, unprompted, from their own campaign: *"Expedition waiting rockets have
never gathered busy colonists. It will leave the rocket sitting forever until you
either import a colonist that it needs from earth or train one in the university.
I have ran into this multiple times."*

**The observation is correct; the mechanism is not busy-refusal.** The busy
fallback exists (`CargoTransporter.lua:272-285`), but it is filtered by
`FilterColonistsByTrait` (`Lua/CargoTransporterNew.lua:163-194`) FIRST. When the
expedition asks for a specialization nobody on the map has, the busy pool
contributes nothing either, `GatherAvailableColonists` returns nil, and
`colonist_summon_fail` goes true (`RocketExpedition.lua:493-495`) — the rocket
sits. Cured by importing or by university training, which is exactly the remedy
the owner names. So the stall is **trait scarcity**, not busy-refusal.

Discriminator, if it is ever worth confirming: a *generic*-crew expedition
(`crew_specialization` unset → `"Colonist"`, `RocketExpedition.lua:522`) requesting
more crew than there are idle colonists should take working colonists. A generic
expedition stalling with busy colonists available would overturn this reading.

### The natural cross-map route is LIVE, and that half was settled by reading

An underground colonist cannot be in `MainCity.labels.Colonist`, so the rider's
index `1513` in a surface rocket's `1543`-entry pool can only have come from the
`GetConnectedCitiesForColonists` append (`CargoTransporter.lua:220-235`, `:244-251`),
which walks `city.labels.Elevator`. A surface rocket's crew gathering therefore
**does** see underground train riders and will take them as busy colonists once
idle ones run short. No expedition was consumed to establish this — it is a pool
reconstruction, not a launch.
