### C105 - Water Reclamation automation upgrade reportedly removes the water saving (P3) `[cand 2026-09-17: NOT reproduced; shipped-body desk control says the saving survives at 50%; no mechanism found]`

**VERDICT.** Not reproduced. On every shipped path read and executed, the "Exotic Mineral
Automation" upgrade **keeps** the spire's water saving and sets it to **50%**. A staffed spire
saves half its performance, e.g. 70% at 140 performance. The upgrade fixes performance at 100.
The reporter's "gone" may be that drop, or a state this entry did not reach. **One in-game read
settles it** (see *Settling read*). Do not build from this entry.

#### Field report

Steam discussion post, 2026-09-16: *"Water Reclamation Spire upgrade bugged. The normal mode is
fine. Once upgraded so you have no need of workers, the reclamation effect is gone."* No save, no
numbers.

#### How the saving works - game 1.1.0.403908

- **The saving is computed, not a property.** `WaterReclamationSpire:RecalcModifiers`
  (`Lua/Buildings/WaterReclamation.lua:22-61`) takes the **best** `performance` of every spire in
  the dome (`:25-40`) and applies `-performance/2` percent (`:18-20`) twice: as the dome label
  modifier `SupplyGridBuildings` (`:43-50`) and as an `ObjectModifier` on the dome's own
  `water_consumption` (`:52-60`).
- **It runs on two triggers:** a `performance` change (`:11-16`) and `OnSetWorking` (`:88-90`).
- **The upgrade** (`Data/BuildingTemplate/WaterReclamationSystem.lua:35-45`,
  id `WaterReclamationSystem_JumboCave`, unlocked through the Jumbo Cave buried-wonder scenario's
  `JumboCaveUpgrades` tech, `Lua/Scenario/BuriedWonder_Jumbo_Cave.generated.lua:147-151`) creates
  three `ObjectModifier`s in slot order via `Building:ApplyUpgrade` (`Lua/Buildings/Building.lua:1153-1210`):
  `automation` +1, `auto_performance` +100, `max_workers` -100%.
- **The modifier system that actually runs is `Lua/Modifiers.lua`**, which redefines `Modifiable`
  (`:3-4`). ⚠️ `CommonLua/Classes/Modifiers.lua` describes a deferred, coalesced change message.
  That is **not** the running implementation, and reading it first nearly produced a false
  mechanism. The game's `UpdateModifier` and `SetBase` call `OnModifiableValueChanged`
  **synchronously**, on any real value change (`:82-85`, `:123-127`).
- **The chain after install:**
  1. `max_workers` 2 → 0 enters the Workplace handler (`Workplace.lua:608-665`). It fires the
     workers, closes the workplaces, and calls `SetWorkshift` → `UpdatePerformance`.
  2. With `max_workers == 0`, performance = `auto_performance` = 100 (`:296-301`, `:279-281`).
  3. That performance change runs `RecalcModifiers`, which applies 50%.
  4. `ApplyUpgrade` then cycles `SetWorking(false)` and `SetWorking(true)` (`Building.lua:1225-1229`).
     That recalculates again, **independently** of step 3.

#### Refuted - recorded so nobody re-derives them

1. **"A de-duplicated value change skips the recalculation."** The running system fires on every
   real change. The upgrade changes both `max_workers` (2 → 0) and performance. The working-state
   refresh recalculates regardless, which scratch variant 1 below demonstrates.
2. **"The automation branch of the Workplace handler never updates performance."** True of that
   branch (`Workplace.lua:657-664`), but `Workplace:SetWorkshift` calls `UpdatePerformance`
   (`:211-217`) and the `max_workers` branch runs too. Even with no workers and no automation,
   `NoWorkersPerformance` is **100**, not 0 (`Lua/__const.lua:1927-1929`).
3. **"1.1.0 removed `Workplace.OnSetWorking(self, working)` from the spire."** It did (the only
   diff in the file), but as a **refactor**. 1.0.7 declared `AutoResolveMethods.OnSetWorking`
   (1.0.7 `Building.lua:8`). 1.1.0 declares `RecursiveCallMethods.OnSetWorking = "call"`
   (`Building.lua:3`), which chains ancestors itself.
4. **"An upgrade upkeep object switches the modifiers off."** `UpgradeConsumption:GameInit` does
   stop them (`Lua/HasConsumption.lua:728-729`), but no such object exists here. The type defaults
   to `no_consumption` (`Lua/Buildings/UpgradableBuilding.lua:39`), the early return is at `:173`,
   and the template sets none.
5. **"1.1.0's now-working `StopUpgradeModifiers` turns automation off."** Vanilla did fix that
   string-keyed `ipairs` no-op (our F03). But its callers are `Building:Done` (removal,
   `Building.lua:533`) and `SetDome`, filtered to that dome's label modifiers (`:698`, `:1303-1311`).
   Neither reaches the spire's own `ObjectModifier`s.
6. **"Old saves clamp `max_workers` at 1."** Both fixups (`WorkplaceWorkersModificationMin1_1`,
   `WorkplaceMaxWorkersUnclamp`, `Workplace.lua:1861-1897`) exist verbatim in 1.0.7. The property
   `min` is 0 in both trees. Clamped at 1, performance would still be `Max(workers, 100)` = 100
   (`:283-287`).
7. **"A throw aborts `ApplyUpgrade`."** The change callback is not `procall`-wrapped, so this was
   worth checking. The only arithmetic that can throw, `100 % max_workers` in
   `GetWorkersPerformance`, returns before it when a shift is empty (`:252-254`), and every
   non-UI caller is guarded by `max_workers == 0` (`:279`, `:329`).
8. **The Jumbo Cave scenario** only waits for `BuildingUpgraded` (`:152-158`). **`SpireBase`** is
   frame cosmetics. **`LabelContainer:SetLabelModifier`** removes the old modifier and applies the
   new one, unchanged since 1.0.7.
9. **No UI line shows the saving.** A grep of `Data/XDef`, `Lua/XDef` and `Lua/UI` for
   "reclamation" returns nothing, so a player sees it only as dome and building water consumption.

#### Desk control - `python tools/desk_c105_water_reclamation.py`

It executes 20 shipped bodies plus the whole spire file and `SetLabelModifier`. The class-chain
resolution, a colonist's firing route and working-state plumbing are retyped and named in the
header. Fixture: one dome (water 10000), one farm in `SupplyGridBuildings` (water 5000), one
spire, two workers at 140. **7 of 7 hold** at HEAD `105a666`.

| state | performance | dome water | farm water |
|---|---|---|---|
| staffed | 140 | 3000 (−70%) | 1500 |
| after `ApplyUpgrade` | 100 | 5000 (−50%) | 2500 |
| after 5 more working-state refresh cycles | 100 | 5000 | 2500 |
| two spires, one upgraded | 100 / 140 | 3000 (best wins) | 1500 |
| **negative control**: upgrade modifiers forced off | 0 | 10000 (no saving) | 5000 |

**Falsified by scratch variants** (patching the loader's read of the spire file):

- Neutering only the performance hook still passes the upgrade leg, because the working-state
  refresh recalculates independently; only the negative control fails. **The upgrade leg is
  over-determined.**
- Neutering both hooks fails 3 demands, with the saving stuck at a stale 70%.

The instrument can show a loss. The shipped path does not produce one.

#### Settling read (owner or TestKit, one sitting, cheats fine)

On any colony with a Water Reclamation spire staffed by at least one shift:

1. SMRTK-dump the spire and its dome.
2. Build the automation upgrade (`JumboCaveUpgrades` can be granted).
3. Dump both again.

Read the spire's `performance`, `automation`, `max_workers`, and the dome's
`SupplyGridBuildings` modifier `WaterReclamationSpireWaterConsumptionReduction`.

- **Not reproduced:** after the upgrade, `performance` is 100 and that modifier reads −50.
- **A mechanism outside this entry exists:** `performance` is 0, `automation` is 0 with the
  upgrade built, or the modifier is absent.
- **Vacuous if:**
  - a second staffed spire at 100 or more sits in the same dome (best performance wins, `:25-40`);
  - the staffed spire was already at 100 or less (the upgrade then raises the saving);
  - the upgrade is toggled off.

#### Side observation - benign, not filed

`WaterReclamation.lua:15` explicitly calls `Workplace.OnModifiableValueChanged(self, prop, ...)`.
But the callback is already `RecursiveCallMethods = "call"` (`Lua/Modifiers.lua:1`, identical in
1.0.7), so Workplace's handler runs **twice** per change. The second pass is idempotent: the
refresh legs above run it, with no drift. 1.1.0 removed the matching explicit call from
`OnSetWorking` but not this one.
