### C101 — Colonists set to REJECT in the rocket applicant filter are still seated (P3) `[wontfix 2026-10-02: recheck not-a-defect]`

⛔ **NOT REPRODUCED, and deliberately not investigated** — the owner asked for it noted, not
chased (2026-09-16, mid-release day: *"Don't got to deep on that, i have more important stuff
but I wanted to note it"*). Everything below is an owner observation plus a source read.

#### What was seen

One attended observation on the owner's live ESA/Wildfire colony, 1.1.0.403908, with an SMRTK
screenshot. Applicant filter set to **Tourist = disapprove**, **Botanist = musthave**. The
passenger list filled with Tourists anyway. The SPECIALIZATION panel read:

| row | selected/pool | filter state |
|---|---|---|
| Botanist | 38/38 | musthave |
| Tourist | **19/108** | **disapprove** |
| Geologist | 0/22 | disapprove |

⭐ **The asymmetry is the finding.** Two attributes in the same disapprove state produced
opposite outcomes. ⚠️ Botanist at 38/38 means the whole musthave pool was exhausted, so the
remaining seats had to be filled from somewhere — that is the pressure which makes this visible
and may be part of the mechanism.

#### Control — what would falsify the claim

⚠️ **RUN ONCE, SOFTLY — see the partial result below.** With Tourist still disapproved,
**clear the passenger list and press Fill Seats.**

- **No Tourists return** ⇒ mechanism 1 below. The reject works; it simply never evicts an
  already-seated colonist. Low severity, arguably intended.
- **Tourists return immediately** ⇒ mechanism 2 or similar. A real filter defect, and the
  observation becomes reproducible on demand.

Anything else refutes both mechanisms and the entry needs re-deriving from scratch.

⚠️ **PARTIAL RESULT 2026-09-16, owner, SOFT.** The owner ran the control and reported
*"seems to be fine but I didn't look into it to much deeper"* — i.e. no Tourists returned, which
points at **mechanism 1**. ⛔ This is NOT a verdict: the counts were not read back, the rejected
attribute was not re-confirmed as still set, and the owner explicitly deferred (*"we will look back
into it"*). Treat mechanism 1 as the leading hypothesis and mechanism 2 as open.

#### Why a reject should be absolute — SOURCE-VERIFIED on 1.1.0.403908

`FilterState.Negative = -1000` (`Lua/Filter.lua:6-11`); `FilterObjectAttributes` sums the
weights of every filter attribute the colonist carries (`Filter.lua:113-121`); both
`ResolveApplicantLists` and `RecalcApplicantLists` admit a colonist only on `eval >= 0`
(`Lua/Traits.lua:434-472`); `FillSeats` draws exclusively from the resulting
`matching_applicants` (`Traits.lua:485-500`). One disapproved attribute is therefore enough to
drop a colonist from every automatic seating path.

⛔ **The key matches — this is not a key-mismatch bug.** `Tourist` is an ordinary trait on the
colonist (`colonist.traits["Tourist"]`, `Traits.lua:423`, `:512`), exactly like `Geologist`.

#### Two candidate mechanisms — neither tested, ⛔ do not reason from either as settled

1. **Seated passengers are never re-filtered.** `ResolveApplicantLists` removes only the
   **unlocked** colonists from `approved_applicants` (`Traits.lua:455-460`), and the shipped
   rollover says so outright: *"Locked passengers will remain selected when the filter changes"*
   (`Traits.lua:539`). A colonist seated before the reject was set is never revisited.
2. **The panel edits a copy of the pool filter.** `TraitsObject` takes
   `self.filter = table.copy(context.filter)` (`Traits.lua:114`), while the pool filter lives in
   the globals `g_ApplicantPoolFilter` and `g_AsteroidLanderPassengerPoolFilter`
   (`Traits.lua:96`, `:118`) which are written back only at the end of a filter update
   (`:406-410`). A seat-filling path reading the global would ignore a panel-only edit and the
   UI would still draw the reject.

⚠️ Mechanism 1 predicts the Geologist row exactly — 0/22 because no Geologist had been seated
before the filter was set — which makes it the cheaper hypothesis. That is a reason to run the
control, not a reason to file it as the cause.

#### Not ours

`rg -l -F -- "ApplicantPoolFilter" Code/` returns nothing, and no pack module wraps the applicant
filter, `TraitsObject`, or seat filling. Vanilla behaviour on a colony with no relevant fix
active.
