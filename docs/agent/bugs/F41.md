### F41 — Gene Forging tech has no effect (P2, high)  `[tested: Code/Fix_GeneForging.lua — PT-29 PASS 2026-07-29: live console read on a colony with neither tech researched went nil → 50 (Gene Forging alone, was nil = the defect) → 150 (both), confirming the additive sum]`

#### 2026-09-12 - still-needed sweep: Current default rare-trait consumer

On **1.1.0.403908**, GetRandomTrait now reads GetRareTraitChance as its default (`Lua/Traits.lua:1049`); GenerateTraits also uses that helper (`Lua/Units/Colonist.lua:4419`, :4422). The helper still omits the GeneForging technology bonus (:4399). The older have-only consumer limit is not the current topology. The additive repair and public outcome remain supported at source; no fresh generated-colonist distribution was measured.

Current review: [one-module evidence](../reports/still-needed/Fix_GeneForging.md). Historical dates and status below remain unchanged. Owner decisions: checklist 156.

`Colonist:GetRareTraitChance` (`Colonist.lua:3541-3550`) reads only
`TechDef.GeneSelection.param1`; `GeneForging` (`TechPreset.lua:1556-1564`, param1=50)
referenced nowhere in gameplay code. **Fix:** wrap `GetRareTraitChance`: add GeneForging
param when researched (ChoGGi's original approach: bump GeneSelection.param1 to 150).
*Implemented as an additive sum, not the param1 bump:* bumping GeneSelection only pays out
when that OTHER tech is researched, so Gene Forging on its own would still do nothing.
The value is a percentage bonus on the rare traits' draw weight (`GetRandomTrait` does
`rare_weight_mod = 100 + (rare_weight_mod or 0)`, `Traits.lua:1001-1022`), which is why
GeneSelection's 100 reads as "double" — so the two techs add: Forging alone +50, both +150.
Note `GetRareTraitChance` is a global function, not a Colonist method as this entry said.
Scope: only the "have" half. Rare traits GAINED later (schools, sanity breakdowns) call
`GetRandomTrait` with no `rare_weight_mod` at all, so neither tech has ever affected them
— separate defect, not touched.

⭐ **CONVERTED TO A §1.4b CHAINED WRAPPER 2026-08-02** (chain prompt 8;
`SAVE_SAFETY_REDESIGN.md` §5.4 group A). The two techs are meant to ADD, so the
shipped body keeps owning the GeneSelection term and the module contributes only
its own: `local base = orig(unit)` … `return (base or 0) + GeneForging.param1`
when researched, `base` otherwise. The six-line copy is gone, and the global is
now installed through `SMRFixPack.SetGlobal` so the §1.4b read-back check applies
(the copy assigned it directly). All four states reproduce PT-29's ladder
exactly: neither → `nil`; GeneSelection only → its `param1`, passed through
untouched; GeneForging only → `50`; both → `150`. One documented delta: the copy
carried a `city.colony` nil-guard vanilla does not have, and delegating gives
vanilla's unguarded index back — defensive hardening with no defect claim behind
it, no producer in Src for a live city without a colony, and vanilla raises there
too.

## 2026-09-09 — augment A-1: the module was the last reader of an abandoned map

hotfix2 link 05, from the 1.1.0 re-verification §1c row A-1. ⛔ **Nothing was
run in a game and the status is unchanged** — this is a desk change with desk
controls.

The module WORKS on 1.1.0 (K-4 re-verified it) and this does not repair a
symptom anyone can see today. What it repairs is a latent one. 1.1.0 moved the
tech data: `Data/Tech.lua` now places `Tech` objects whose value lives in a
`Parameters` list and is read as `Techs.<id>:ResolveValue("param1")` — which is
exactly what the shipped body does for the GeneSelection term one line above
ours (`Colonist.lua:4399-4400`). The old `TechDef` map survives in
`Data/TechPreset.lua`, still carrying `GeneForging param1 = 50`, so our bonus
still pays. But **MEASURED 2026-09-09: `TechDef` has exactly one mention left in
the entire shipped tree — the `GlobalMap = "TechDef"` declaration itself**
(`ClassDef-PresetDefs.generated.lua:1730`). Zero readers. This module was the
last consumer of a map the game has abandoned, and R-32 shows one stub has
already been emptied.

**The failure it prevents is a player LOSS, and it was measured, not argued.** A
desk control simulating a patch that empties the stubs, with both techs
researched: the old module returns **100** — the whole Gene Forging bonus gone,
silently, with the module still logging `applied` and every self-check green —
and the new one returns 150.

Two reads changed, each now going through the running branch's own route:
* the VALUE: `Techs.GeneForging:ResolveValue("param1")`, falling back to
  `TechDef.GeneForging.param1`;
* the TECH TEST: the global `IsTechResearched("GeneForging")`, replacing our
  hand-rolled `(unit.city or MainCity).colony:IsTechResearched`. Both branches
  ship that global and each defines it in terms of its own researching party
  (1.0.7 `UIColony:IsTechResearched`, `Tech.lua:466`; 1.1.0
  `GetTechState(tech_id, UIPlayer)`, `Tech.lua:468`), and 1.1.0's shipped body
  uses it for the half of the sum vanilla still owns.

⛔ **No branch guard, deliberately, and that is ck118 applied rather than
skipped.** The guard is owed by a module that CARRIES a 1.1.0 body. This one
carries none — it delegates to `orig`, and the value read is dual-branch by
construction. Verified against the archived 1.0.7 tree: nothing in it places
class `Tech` anywhere, so `Techs` is empty there, the first read is nil, and the
fallback returns the same 50 from `Data/TechPreset.lua:1556-1564`. The fallback
is load-bearing, not decoration.

⚠️ **The wrapper keeps a vararg**, against an upstream note suggesting the
`unit` plumbing be dropped as "harmless, 1.1.0 ignores it". 1.1.0 does ignore
it — all three of its call sites pass nothing. 1.0.7's signature is
`GetRareTraitChance(unit)` and **two of its call sites do pass a colonist**
(`TraitPreset.lua:748`, `Colonist.lua:3559`), which `orig` uses to pick the
city; a wrapper declared `function()` would swallow that before `orig` saw it.
A red control confirms it: with the vararg dropped, the 1.0.7 leg returns nil
where it must return 100.

Controls (desk, `lupa`): the pack's real `Require`/`SetGlobal`/`Register` over
each branch's VERBATIM shipped `GetRareTraitChance` body and real data shape.
The full ladder reproduces on both branches — neither → nil, GeneSelection →
100, GeneForging → 50, both → 150 (PT-29's ladder, unchanged) — plus the 1.0.7
vararg leg. Both red controls fire.

No manifest re-stamp: the `SRC:` line hashes the SHIPPED body, which a
module-side edit does not touch (`bodycheck` OK on both rows before and after).
