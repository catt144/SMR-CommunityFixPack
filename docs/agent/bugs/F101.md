### F101 — Retail calls tooling-only globals (`TestMeteor`, `GetSpotNameColor`)  `[wontfix — OUT OF SCOPE (owner, 2026-08-10): both throws are impossible on a build where the panel belongs, and retail only reaches them with modding tools active. MEASURED, vanilla, no pack code, nothing built and nothing will be]`

## ⛔ Read this block before anything else

**This is closed. Do not re-open it, and do not re-derive the gate below.**
The defect is real and the two mechanisms are correctly described — but it can
only fire in a configuration the pack does not serve, and the owner has ruled it
out of scope (§ "Why `wontfix`", bottom). If a future session finds one of these
throws in a log, the answer is already here: **check whether a Ged mod-tool
window was open.** If it was, this row explains it and there is nothing to do.

**How it was found.** Not by looking for it. The owner was exploring F99's
trigger conditions with dev tools, clicked a track element's **Meteor Hit**
infopanel cheat button, and the sitting's error monitor fired. Reported here
rather than attributed away — "not caused by our leg" is an attribution verdict,
never a dismissal, and the owner's follow-up question (*"Many people use dev
cheats outside of dev mode via mods. If one can cause that, I am interested"*)
is what turned a one-off into a class.

Log: `docs/archive/cb1sitting_Mars.exe-20260805-14.28.49.log`, session uptime
`1:58:42`, 8 loads, build 1.0.7.396349 retail, pack 81/81 active.
**Session baseline before these: 0 `[LUA ERROR]` lines**, so attribution is
unambiguous. FORCED — every occurrence was an owner-initiated UI action, named
below in the owner's own account.

## (a) `TestMeteor` — a `Platform.cheats`-only global with three ungated callers

```
[LUA ERROR] Lua/Buildings/TrackElement.lua:441: attempt to call a nil value (global 'TestMeteor')
  Lua/Buildings/TrackElement.lua(441):  field ?
  CommonLua/Libs/Network/Network.lua(213):   <>
  [C](-1):  global procall
  CommonLua/_Network.lua(35):  global NetSyncEvent
  Lua/X/Infopanel.lua(49):  method OnAction
  CommonLua/X/XActions.lua(624):  method OnAction
  CommonLua/X/XButton.lua(90):  upvalue on_press
  CommonLua/X/XToolBar.lua(69):  method OnPress
  CommonLua/X/XButton.lua(70):  method Press
```
×3. Owner's account: *"Test meteor will not work, I was just going to ask you
about that"* — i.e. clicked from the infopanel, not the console.

**The definition is gated; the callers are not.** `Meteors.lua:1086-1088`:

```lua
if Platform.cheats then

function TestMeteor(obj)
```

Single definition in the whole tree (`grep -rn "function TestMeteor"` → one
hit), no `else` branch, so on a retail build the global simply does not exist.
**Three ungated call sites, all identical in shape:**

| site | method |
|---|---|
| `Lua/Buildings/Building.lua:1936` | `Building:CheatMeteorHit()` |
| `Lua/Buildings/TrackElement.lua:440` | `TrackGridElement:CheatMeteorHit()` |
| `Lua/Buildings/TrackElement.lua:672` | `TrackConstructionSite:CheatMeteorHit()` |

```lua
function Building:CheatMeteorHit()
	TestMeteor(self)
end
```

⭐ **The first is on `Building` itself** — the base class for effectively every
selectable structure — so this is not a track-piece quirk: **every building's
Meteor-Hit infopanel cheat throws on retail.** The one the owner clicked
happened to be a track element.

⚠️ **Contrast with the sibling that works.** `TrackElement.lua:436-438`:

```lua
function TrackGridElement:CheatBreakElement()
	BreakTracks({self})
end
```

`BreakTracks` (`Meteors.lua:599`) is a plain ungated global, so **Break Element
works on retail** while Meteor Hit, three lines below it, does not. That
asymmetry is what makes the defect legible as an oversight rather than a design
choice — and `SelectedObj:CheatBreakElement()` is the working instrument any
future track-damage fixture should use.

## (b) `GetSpotNameColor` — an optional LIBRARY, not a `Platform` gate

```
[LUA ERROR] CommonLua/GedGameObjectEditor.lua:104: attempt to call a nil value (global 'GetSpotNameColor')
Error calling Lua function "MouseEvent" from C: CommonLua/GedGameObjectEditor.lua:104: ...
```
×2. Owner's account, asked for attribution before anything was written down:
**"opened the inspector"** — then a mouse event fired it.

⛔ **CORRECTION 2026-08-05 (terminal audit, against the archived stacks) — the
witnessed trigger is NOT the inspector.** Both `[LUA ERROR]` blocks carry a
full stack in the archived log (throws at `1:44:57` and `1:45:06`):

```
XButton:Press → XToolBar:OnPress → Infopanel.lua(47): method OnAction
  → _cobject.lua(1576) → ToggleSpotVisibility (GedGameObjectEditor.lua:64)
  → EditorShowSpots (GedGameObjectEditor.lua:104) → GetSpotNameColor  [nil]
```

That is an **infopanel toolbar button** — the spot-visibility dev toggle — the
same surface class as mechanism (a). The paired `Error calling Lua function
"MouseEvent" from C` lines re-enter the same `:104`. And the session's one
actual inspector open was **clean**: `Opened GedInspector` at `1:45:12`,
`Closed GedInspector` at `1:45:32`, no error between — and it came AFTER both
throws, so the owner's recollection ("opened the inspector") named the nearest
salient action, not the throwing one. The stack is the authority.

**What stands and what moves:** the defect stands MEASURED — retail core code
calls the `DevToolsPublic`-only `GetSpotNameColor` at
`GedGameObjectEditor.lua:104`, witnessed 2×. What moves is the reachable
surface: *"opening the object inspector `~<expr>` throws"* is **UNWITNESSED**
and joins the `!`/`ShowMe` instance in the static-lead bin (`:104` is in the
inspector's own file, so the risk is plausible — but nobody has measured it).
Both *witnessed* mechanisms are now infopanel dev-toolbar buttons.
`PLAYTEST_HELP.md` corrected in the same commit; the paragraph below predates
this correction and keeps its HELP-history point only.

`CommonLua/GedGameObjectEditor.lua:104`:
```lua
local spot_name, spot_color = GetSpotNameColor(obj, i)
```

Single definition: `CommonLua/Libs/DevToolsPublic/debug.lua:359`. **It is not
behind a `Platform.*` gate at all** — the entire `DevToolsPublic` library is
absent from this build. (`Libs.DevToolsPublic` appears as a live condition in
`CommonShortcuts.lua:173`: `AreCheatsEnabled() or ConsoleEnabled or
Libs.DevToolsPublic`.)

⚠️ **This mechanism is worse than (a) for us specifically**, because
`PLAYTEST_HELP.md`'s console table documents `~<expr>` as "opens the object
inspector on `<expr>`" — **we recommend the action that throws.** HELP corrected
in the same commit.

A third instance of the same mechanism was found statically and is **NOT yet
witnessed**: `CommonLua/UI/Dev/uiConsole.lua:357` maps the console's `!` prefix
to `ShowMe(...)`, and `ShowMe` lives only at `DevToolsPublic/debug.lua:184`.
Recorded as a lead, not a finding — nobody has typed `!` on this build.

## ⭐ The reachability gate — derived 2026-08-10, and it is what closed the row

*(The severity paragraph this replaces asked whether a player who never touches
dev tools can reach these. The answer below is sharper than "unproven": the
engine's own cheat gate has to say yes first, and on retail only a modding-tools
session makes it say yes.)*

**SOURCE — neither throw can happen where the panel belongs.** (a) `TestMeteor`
is nil *because* `Platform.cheats` is false (`Meteors.lua:1086`); (b)
`GetSpotNameColor` is nil *because* the `DevToolsPublic` library is absent. On a
cheats/dev build both symbols exist and both buttons work. **There is nothing to
reproduce in dev mode** — the defect *is* "this panel pressed on a build it was
not shipped for".

**MEASURED — the engine authorised the call before it broke.** In the sitting
log, each throw is preceded by the dispatcher's own print:

```
1062  ObjCheat CheatMeteorHit
1063  [LUA ERROR] Lua/Buildings/TrackElement.lua:441: attempt to call a nil value (global 'TestMeteor')
```

`print("ObjCheat", method)` is `Network.lua:220` — **one line after**
`if not AreCheatsEnabled() then return end` (`:219`). So the gate passed, the
sync event dispatched, and only then did shipped code call a symbol its own
build does not ship. That is the defect in one sentence: the button hangs off
`AreCheatsEnabled()`, the function hangs off `Platform.cheats`, and they are
different gates.

**SOURCE — which gate was open, and therefore who is exposed.**
`AreCheatsEnabled() = Platform.cheats or AreModdingToolsActive()`
(`gamelib.lua:1035`). `Platform.cheats` was false — that is *why* `TestMeteor`
was nil — so `AreModdingToolsActive()` was true:
`IsModEditorOpened() or IsModManagerOpened() or IsModEditorMap() or Game.testModGame`
(`Mod.lua:145`), the first two being Ged tool windows (`GedModEditor.lua:1-7`).
⇒ **The exposed population is "retail build with the modding tools attached"** —
the same state that blocks achievements (`GedModEditor.lua:23-25`). ROUTE claim,
tagged separately from its citations: `Platform.cheats` false is *inferred from*
`TestMeteor` being nil, which is sound because `Meteors.lua:1086-1088` is the
symbol's only definition in the tree.

⚠️ **Which of the four predicates was true was NOT sampled** and does not need
to be for the disposition. If anyone ever wants it, it is one console line while
the buttons are visible:
`print(Platform.cheats, AreModdingToolsActive(), IsModEditorOpened(), IsModManagerOpened(), Game and Game.testModGame)`.

**⛔ NOT forced by our own tooling — checked rather than assumed.** The TestKit
enables the *console* (`ConsoleEnabled`, `00_TestCore.lua:315`), and
`ConsoleEnabled` is **not** a term in `AreCheatsEnabled`. A grep of `Code/` in
both repos for `config.BuildingInfopanelCheats`, `Platform.cheats`,
`AreCheatsEnabled` and `testModGame` returns **zero writes** — only comments. We
supplied a console; vanilla supplied the cheat authorisation.

## Damage from pressing them — measured, because "harmless" was an assumption

- **(a) None.** The nil call is the first statement of `CheatMeteorHit`, so
  nothing ran — no meteor, no partial state — and it is inside `procall`
  (`Network.lua:223`), so `Msg("ObjCheatStart")` / `Msg("ObjCheatEnd")` still
  pair. ⚠️ Explicitly **unlike F99**, where an escaping throw skipped
  `ResumeTerrainInvalidations` seven times.
- **(b) Dev-tool UI state only.** `EditorShowSpots` destroys the previous
  renderables first (`DoneObjects(shown_spots[obj])`, `GedGameObjectEditor.lua:92`)
  but assigns `shown_spots[obj] = objs` only at `:138`. The `:104` throw lands on
  the first matching spot before any renderable is created, so nothing leaks —
  but the stale (destroyed) table stays under the key, so the next click takes
  the `EditorHideSpots` branch and merely clears it. Net on retail: the toggle
  can never show spots and sits one click out of phase. Runtime table, no
  persistence, no colony state, nothing reaches a save.

## Fixability — recorded for the record only; nothing will be built

Both were wrappable and cheap, which is why the disposition is a scope call
rather than a capability one. (a) A §1.4 pre-wrapper on `Building:CheatMeteorHit`
plus the two track variants, returning early when `rawget(_G, "TestMeteor")` is
nil — or, barely harder, doing `TestMeteor`'s own six lines inline, every symbol
of which is ungated (`MapSettings_Meteor` `Meteors.lua:1`, `MeteorsDisaster`
`:131`), which needs **no new global** and therefore avoids C43's
strict-global-guard problem. (b) A §1.4b replacement of the existing global
`EditorShowSpots` that returns early when `GetSpotNameColor` is nil — best
possible outcome a silent no-op, since restoring the function itself means
creating a new global (C43) or copying ~40 lines of renderable code.

## Why `wontfix` — owner scope decision, 2026-08-10

**The owner's words:** *"If it works fine from what we can tell in dev mode then
its not in this mods scope. If a modder wants to build out a toolkit for users
then that should be something they fix."*

This lands exactly on FIX_POLICY §4's tier rule — **R4-class: the defective path
needs a configuration only a modding tool produces, so the beneficiary is a
modder, not a player** — and §4a's test ("could a PLAYER be harmed by this?")
answers no for anyone not running Ged tools. R4 does not ship; it is recorded
`wontfix` with the enumeration that proved it, which is the gate section above.

⚠️ **What this does NOT say:** it does not say the code is correct. Vanilla
authorises a call it cannot serve, and if a future patch ever made
`AreCheatsEnabled()` true in ordinary play, or a mod exposed these buttons
directly, the defect would become live — at which point this row already holds
the diagnosis and both fixes.

**The user-facing idea is parked, the defect is not.** A separate mod that
exposes dev tooling to players would have to repair these before it could use
them; that idea is filed in `docs/FUTURE_IDEAS.md` (post-launch, separate mod,
never this pack). Per FUTURE_IDEAS' own hard rule, the *defect* stays here with
this status — only the enhancement is parked there.

## ⛔ What a future session must not conclude

- **Not** that infopanel cheat buttons "silently no-op on retail." They execute:
  the `NetSyncEvent` delivered, `procall` ran it, and it reached line 441 before
  throwing. `AreCheatsEnabled()` and `Platform.cheats` are different things.
- **Not** that the static audits behind this entry are a findings list. Two
  scripted sweeps produced four distinct false-positive classes (`else`-branch
  definitions, `end -- comment` closers, `local` with a dev-only override, and
  call sites that are themselves in unshipped editor code). **Only the two
  instances above were verified by reading source, and only they are claimed.**
