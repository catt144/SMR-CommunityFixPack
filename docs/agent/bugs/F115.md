### F115 — `Fix_LandscapeUnitFilter` throws on every landscaping site: 1.1.0 changed the signature of the global it replaces (our own defect, patch-induced) (P1, measured — filed)  `[filed 2026-09-08: REPRODUCED LIVE by the owner]`

- ⭐ **MEASURED, NOT SOURCE-READ.** Owner triggered it on demand with "flatten
  landscaping" on a fresh 1.1.0 colony, 2026-09-08, unforced/shipped
  configuration (log `archive/logs/*15.57.09*`, throw at `:247` and `:262`).
  The engine's own mod-error dialog fired naming **Relaunched Fix Pack**:

      [LUA ERROR] Mod/SMR_CommunityFixPack/Code/Fix_LandscapeUnitFilter.lua:63:
        attempt to index a nil value (global 'Landscapes')
        Fix_LandscapeUnitFilter.lua(63): global LandscapeForEachUnit
        Lua/Landscape/ClearWasteRockConstructionSite.lua(81): GetUnitsUnderneath
        Lua/Buildings/ConstructionSite.lua(1915): ScatterUnitsUnderneath
        Lua/Landscape/ClearWasteRockConstructionSite.lua(75): InitBlockPass
      Locals:  mark | object Map      callback | number 51
      [mod] Error in mod Relaunched Fix Pack (id SMR_CommunityFixPack, v1.00-005)

  A second throw the same instant comes via `ConstructionSite:Initialize`
  (`:1146`) rather than `InitBlockPass`, so BOTH entry points are live.
- ⭐ **THE CAUSE, PINNED, WITH THE CONTROL IN THE LOG ITSELF.** 1.1.0 changed
  the signature of the global we replace:

      1.0.7:  function LandscapeForEachUnit(mark, callback, ...)
      1.1.0:  function LandscapeForEachUnit(map, mark, callback, ...)
              -- Lua/Landscape/Landscaping.lua:509

  Our replacement (`Code/Fix_LandscapeUnitFilter.lua:62`) kept the 1.0.7 arity,
  so the caller's `map` binds to our `mark` and the caller's `mark` binds to our
  `callback`. ⛔ **That is not an inference — the `Locals` block proves it**:
  `mark | object Map`, `callback | number 51`. The whole family moved the same
  way (`LandscapeForEachObstructor`, `…ForEachStockpile`, `…ForEachHex`,
  `LandscapeChangeTerrain`, `LandscapeFinish` all gained a leading `map`).
- The second half: `Landscapes` moved from a `GameVar` to
  `MapVar("Landscapes", {})` (`Landscaping.lua:21`) and 1.1.0 reads it as
  `map.Landscapes[mark]`. Our body reads the bare global ⇒ nil ⇒ the throw.
- ⛔ **WHY EVERY EXISTING INSTRUMENT MISSED IT, AND THIS IS THE PART TO KEEP.**
  The module's `Require` spec checks `{ global = "LandscapeForEachUnit" }` and
  `{ global = "Landscape_ForEachObject" }` — both still EXIST, so the module
  applies. The 1.1.0 call-site sweep behind `F113` checked 106 global
  call-names and 174 method names. **Names.** A name sweep cannot see an arity
  change; the name is precisely what survived. ⇒ Same failure shape as
  `EF-078`'s finding that path specs were verified by their last segment's NAME
  instead of as a path, which made the desk audit wrong by 5. **Check the
  thing, not its label.**
- ⚠️ **BLAST RADIUS IS LARGER THAN THE POPUP.** `ScatterUnitsUnderneath` is
  called from `ConstructionSite:Initialize` (`ConstructionSite.lua:1146`)
  BEFORE the rest of that method, so the throw aborts `Initialize` and
  **`CreateResourceStockpile()` never runs**, as does the
  `can_complete_during_init` → `Complete()` path. It also aborts
  `ClearWasteRockConstructionSite:GameInit` via `InitBlockPass`. So a
  landscaping site can be left un-stockpiled and half-initialised, not merely
  noisy. ⛔ UNMEASURED how far that goes in play — do not state a gameplay
  outcome without a control.
- ⚠️ **DO NOT CONFLATE WITH THE RC DOZER RULE.** 1.1.0 requires an RC Dozer (or
  the `LandscapingNanites` tech) to service a landscaping job —
  `LandscapeConstructionSiteBase.lua:159`, and the dedicated status
  `ConstructionStatus.LandscapeNoDozer` "You need an RC Dozer for Landscaping"
  (`LandscapeConstructionController.lua:300`). **Drones ignoring a landscaping
  job is expected vanilla behaviour without a dozer** and is NOT this defect.
  ⛔ Whether that requirement is NEW in 1.1.0 is UNVERIFIABLE from disk — the
  1.0.7 tree is gone (`EF-075`). The separating control is to put an RC Dozer
  on the job: if it then progresses, the dozer rule was the symptom the owner
  saw and this defect is the popup plus the aborted `Initialize`.
- ⭐ **THE FIX IS STILL WANTED — 1.1.0 DID NOT REPAIR F34(d).** The shipped
  1.1.0 body still ends `Landscape_ForEachObject(..., foreach_params_unit,
  callback, ...)` — passing `callback`, not the `filter_embark` it just built
  (`Landscaping.lua:520`), exactly the defect this module exists to correct. So
  this is not an obsolete fix to retire; it is a live fix with a broken body.
- **TWO ROUTES, OWNER'S CALL (checklist).** (a) **GATE** it to self-disable on
  1.1.0 — the `F113` shape, smallest possible change, restores vanilla's
  working-but-buggy function, costs players the F34(d) correction. (b)
  **REPAIR** the body to 1.1.0's shape — `(map, mark, callback, ...)` reading
  `map.Landscapes[mark]` and passing `filter_embark` — which also fixes
  F34(d) again. ⛔ A repair pins us to 1.1.0's signature and re-breaks on the
  next signature change unless the gate goes in TOO. Recommend **(a) now**, (b)
  considered separately with a control; a safety-first patch should not carry
  an unverified new body.
- ✅ **BOUNDED BY A SWEEP, NOT BY HOPE.** `tools/sigcheck.py` (written for this)
  compares every replacement's parameter list against the shipped tree: **54
  sites, 1 MISMATCH (this one), 1 ABSENT (`TouristSatisfaction`, already
  self-disabled), 52 OK.** ⛔ Coverage limits, stated: it reads
  `function Name(...)` / `function Class:Method(...)` definitions only — NOT the
  15 `SetGlobal` sites nor 5 anonymous `X = function(...)` literals — and an
  `OK` never clears a same-name, same-arity BODY change. Bounded, not cleared.
