### F107 — `Fix_LandscapeCostRefresh` captures a nil `prev`, so its delegation is dead code that raises if reached (P2, high)  `[built 2026-08-24: Code/Fix_LandscapeCostRefresh.lua — one wrap on ConstructionSite (checklist 74(a)); MEASURED on the F106 leg, repair NOT yet boot-verified]`

## The measurement (MEASURED — one unattended leg, 2026-08-24)

```
[SMRTest] SMRTEST-F105GUARD LandscapeConstructionSite: unguarded-state call ok=true
[SMRTest] SMRTEST-F105GUARD ClearWasteRockConstructionSite: unguarded-state call ok=true
[SMRTest] SMRTEST-F105GUARD TerrainPaintConstructionSite: unguarded-state call ok=true
[SMRTest] FAIL  LandscapeCostGuard  [behavior] the guard no longer delegates on
  LandscapeConstructionSite (raised with a valid cost table:
  Mod/SMR_CommunityFixPack/Code/Fix_LandscapeCostRefresh.lua:81: attempt to call a
  nil value (upvalue 'prev')); ClearWasteRockConstructionSite (…same…);
  TerrainPaintConstructionSite (…same…) — a site WITH a start-cost record must
  still be refreshed
```
— `docs/archive/f106_Mars.exe-20260824-02.32.27.log`

Read the two halves together. **Clause 1 passed on all three leaves**: with the
field state (a live `construction_resources.WasteRock` request and
`construction_costs_at_start == false`) the wrapper is reached and returns
without raising — F105's reported crash is genuinely repaired, and that half of
F105's claim stands. **Clause 2 failed on all three**: given a real
`construction_costs_at_start` table the wrapper reaches `return prev(self)` and
`prev` is nil.

⭐ Clause 2 exists only because a probe that checks a guard must also check that
the guard is not swallowing everything — the same failure family as the two
false-greens this chain was launched over. It is the clause that found this.

## The mechanism (SOURCE, re-derived 2026-08-24)

`Code/Fix_LandscapeCostRefresh.lua:70-83`:

```lua
for _, cls in ipairs({ "LandscapeConstructionSite",
                       "ClearWasteRockConstructionSite",
                       "TerrainPaintConstructionSite" }) do
    local C = rawget(_G, cls)
    local prev = C.RefreshConstructionResources   -- <- nil
    C.RefreshConstructionResources = function(self)
        if not self.construction_costs_at_start then return end
        return prev(self)                          -- <- :81
    end
end
```

1. `SMRFixPack.Register` runs `run_apply` **inline** (`Code/00_Core.lua:452`), so
   every module's `apply` executes while its file loads — during
   `ModsLoadCode()` (`CommonLua/Core/autorun.lua:423`).
2. `Msg("Autorun")`, which `CommonLua/Core/classes.lua:980` builds the classes
   on, is raised later at `CommonLua/Core/lib.lua:371` — the line after the
   `dofile("CommonLua/Core/autorun.lua")` at `:370` returns (audit correction
   2026-08-24: `autorun.lua:556-557` is the `OnMsg.Autorun` handler, not the
   raise; the correction strengthens the ordering, since the dofile completes —
   `ModsLoadCode()` included — before the message fires).
3. ⇒ At apply time `rawget(_G, "LandscapeConstructionSite")` is the raw
   **classdef**. `classes.lua`'s `define` does `rawset(_G, class, class_def)`
   and sets **no metatable**, so a classdef holds only the members its own
   `DefineClass` block and `function Class:Method` definitions put there.
4. `RefreshConstructionResources` is declared on **`ConstructionSite`**
   (`Lua/Buildings/ConstructionSite.lua:665`) and on nothing else in the tree
   (F105's whole-tree grep: a single definition). None of the three leaves
   declares it.
5. ⇒ `prev == nil`, in every leaf, on every boot.

⚠️ **The module's own `Require` block could not catch this.** It self-checks
`{ class = "ConstructionSite", method = "RefreshConstructionResources" }` — which
passes, because `ConstructionSite` really does declare it — and
`{ class = <each leaf>, method = "GatherConstructionResources" }`, which the
leaves really do declare. **The one pair it never checked is the pair it
installs on.** That is the authoring trap, and `00_Core`'s
`find_declaring_ancestor` warning (`:133-137`) fires only when a Require check
FAILS, so it never spoke.

## Reachability, stated honestly

⛔ **Not reachable on shipped data**, by F105's own reader sweep: the only writer
that can touch a LANDSCAPE site's `construction_costs_at_start` is
`ConstructionSite:GatherConstructionResources` (`:639-640`), and all three
leaves override the gatherer without ever creating it. A landscape site's cost
table is `false` for its whole life, so the guard always returns and `:81` is
never executed. ⚠️ Audit precision 2026-08-24: "only writer" tree-wide was too
strong — `Track.lua:651` also assigns the field, on a TRACK construction-group
leader in the SafeTransport branch (the same lines as F49's recorded
`DivRound(cost, res)` latent, `:648`); that path cannot reach a landscape
class, so the latency verdict stands on the narrower, correct ground.

⚠️ **That is a latency argument, not an absolution**, and three things follow:

1. **The module does not do what its entry and its own comments say.** F105
   describes "pre-guard, then delegate". On these three classes it cannot
   delegate; it is an unconditional early return wearing a delegation's clothes.
2. **It is NEW HARM in waiting.** Any other mod, or any game patch, that
   initialises the pair on a landscape site turns a silent no-op into a raise
   **inside our file** — and `EF-065`(a) means the resulting popup names this
   pack. That is precisely the shape F104 and F105 were mis-blamed for.
3. **A vanilla behaviour has been removed with nothing put back.** If a site of
   these classes ever did carry a cost record, vanilla would refresh it; the
   pack now raises instead.

⚖️ **Why this is fixed while F49's latent was deliberately NOT (audit
2026-08-24, reconciling the precedent).** F49 records a real typo
(`DivRound(cost, res)`, `Track.lua:648`) in genuinely unreachable code and
declines to fix it — "writing a fix for it would be the F10 mistake." F107 is
also unreachable on shipped data, so the two calls look opposite on the same
shape. The distinction that decides it: **F49's dead code is VANILLA's; F107's
is OURS.** A raise inside our own file names this pack in the player's popup
(`EF-065`(a)) — the exact misattribution F104 and F105 were both about — and a
pack whose posture is repairing errors must not ship a latent one under its own
name. Repairing F107 is removing OUR defect, not fixing vanilla's dead code.

## What the fix shape should be — ⛔ RECOMMENDED, NOT BUILT

Chain rule 9 forbids the chain that found this from writing fix code. The
recommendation, for checklist 74:

**One chained wrap on `ConstructionSite.RefreshConstructionResources`** —
checklist 72's original picture, which was abandoned on the strength of `F106`
and is now vindicated by `F106`'s refutation.

* `ConstructionSite` **declares** the method, so `prev` is real.
* Reach is **measured, not assumed**: the same leg's sweep line reads
  `Fix_LandscapeCostRefresh ConstructionSite.RefreshConstructionResources
  link=copy desc=13 reach=5 UNREACHED=3 (own-copy 3)
  [ClearWasteRockConstructionSite, LandscapeConstructionSite,
  TerrainPaintConstructionSite] MULTI=5 (unreached 0)`. The three UNREACHED are
  the classes **this module itself overwrote**; with the per-leaf installs gone,
  a classdef-time wrap on `ConstructionSite` is copied into all 13.
* No shipped subclass re-declares the method (F105's grep), so one install is
  exhaustive for shipped reality.
* ⚠️ It widens the guard to ordinary construction sites too. That is harmless by
  construction — they always have a cost table, so the guard falls straight
  through to `prev` — but it is a behaviour-surface change and belongs in the
  owner's decision, not in an agent's. ⭐ Audit-verified at Src 2026-08-24
  (`ConstructionSite.lua:636-684`): the widening is if anything a small
  robustness GAIN — `GatherConstructionResources` creates
  `construction_resources` and `construction_costs_at_start` together
  (`:639-640`, gated at `:637`), so the only ordinary-site state where the
  widened guard fires is the ungathered one, where vanilla's own body would
  index `construction_resources == false` at `:670` and raise. Behaviour where
  vanilla succeeds is unchanged. Put this derivation in the repair's header.
* ⚠️ The repair must also REWRITE the module's header comment
  (`Fix_LandscapeCostRefresh.lua:42-51`): it still asserts the refuted
  post-`ClassesBuilt` premise and cites `classes.lua:986-988` as stating the
  split — the comment F106 rules must never be cited (it is inverted). Line 6's
  "the ONLY writer" also needs the Track.lua:651 precision above. Left in place
  by the audit deliberately: this chain writes no `Code/*.lua` change (chain
  rule 9), and the header travels with the repair the owner picks.

Minimal alternative, if the per-leaf shape is preferred for any reason: capture
`prev` from the **declaring** class (`ConstructionSite.RefreshConstructionResources`)
instead of from each leaf. Same three installs, a real `prev`.

## The repair — BUILT 2026-08-24 (checklist 74(a))

`Code/Fix_LandscapeCostRefresh.lua`: the `for` loop over the three leaf
classdefs is gone. One chained wrap installs on `ConstructionSite`, the class
that declares the method, so `prev` is the real function:

```lua
local C = rawget(_G, "ConstructionSite")
local prev = C.RefreshConstructionResources -- real: ConstructionSite declares it (:665)
C.RefreshConstructionResources = function(self)
    if not self.construction_costs_at_start then return end
    return prev(self)
end
```

* **The pair is Require-declared already** — `{ class = "ConstructionSite",
  method = "RefreshConstructionResources" }` was in the block from the start;
  it is now the pair the module actually installs on, which is what
  `FIX_POLICY` §2 demands. The three leaves' `GatherConstructionResources`
  entries stay: they are the defect PREMISE, not install sites.
* **The three F107 allowlist rows are REMOVED** from
  `tools/harvest_wrap_targets.py`, as that comment instructed. `WRAP CHECK: 0
  wrap site(s) outside Require, 5 allowlisted` — the module no longer needs an
  exemption, which is the check confirming the repair rather than tolerating it.
* **The header comment was rewritten**, as this entry required: the refuted
  post-`ClassesBuilt` premise and the banned `classes.lua:986-988` citation are
  gone, replaced by the measured file-load ordering; line 6's "the ONLY writer"
  carries the `Track.lua:651` precision; the widening derivation
  (`ConstructionSite.lua:636-684`) is in the file, per the recommendation.
* **§2's "inert for a foreign object" clause is answered in the header, not
  waived.** The wrapper reads one field of `self` before delegating, which that
  clause discourages. It is unavoidable and correct here: the defect is a state,
  not a class, so no class predicate separates a broken landscape site from a
  healthy one — and the widening bound below says what that read can change.

⭐ **Widening, re-verified at Src by this session (2026-08-24).** The wrap now
runs for every `ConstructionSite` descendant, not just the three leaves.
`GatherConstructionResources` creates `construction_resources` and
`construction_costs_at_start` together (`:639-640`, gated at `:637`), and both
class defaults are `false` (`:13`, `:32`), so on an ordinary site the guard can
only fire in the ungathered state — where vanilla's own body indexes
`construction_resources == false` at `:670` and raises. Wherever vanilla
succeeds, the cost table is a table and the guard falls straight through.
⇒ the widening can only ever PREVENT an error. Independent re-derivation, same
verdict as the 08-24 audit.

⛔ **What is NOT done, and why the status word is `built` and not `fixed`.**
No boot since the repair: there is no `[CommunityFixPack] LandscapeCostRefresh:
applied` line for this revision, and TestKit's `LandscapeCostGuard` probe —
which is what FAILED and found this — has not been re-run. Its clause 2 should
flip to PASS and clause 1 must stay PASS; a run where clause 1 broke would mean
the repair traded one defect for another. ⚠️ The probe asserts per-leaf
behaviour and still should: the leaves are where the field defect lives, and
the wrap now reaches them by inheritance rather than by installation — which is
exactly the claim a probe should be made to prove. One rig boot closes this.
