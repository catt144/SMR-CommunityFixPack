### C54 — 1.1.0's leaked-upgrade-modifier fixup may abort on its own success path (vanilla defect, candidate)  `[filed 2026-09-08 — SOURCE-READ ONLY, ⛔ not reproduced, ⛔ the deciding question is unanswered, ⛔ no fix proposed]`

## What was read

1.1.0 ships a new savegame fixup that cleans the residue our F03 pass used to
clean (`Lua/Buildings/Building.lua:1313-1345`). Its shape:

```lua
function SavegameFixups.RemoveLeakedUpgradeModifiers()
	...
	for _, container in ipairs(containers) do
		local leaked                              -- nil until something is found
		for label, modifiers in pairs(container.label_modifiers) do
			for id in pairs(modifiers) do
				if type(id) == "string" and not owned[id] and id:match("^%d+_upgrade%d+_mod_%d+$") then
					leaked = leaked or {}
					leaked[#leaked + 1] = { label = label, id = id }
				end
			end
		end
		for _, entry in ipairs(leaked) do          -- ⛔ leaked is nil if this container was clean
			container:SetLabelModifier(entry.label, entry.id, nil)
		end
	end
end
```

`leaked` is only ever assigned inside the match. A container carrying no leaked
modifiers therefore reaches `ipairs(leaked)` with `leaked == nil`.

## Why it would matter, IF `ipairs(nil)` raises here

The container list is built in order — `UIColony` first, then every `City`, then
every `Dome`. The loop has no per-container protection, so the **first clean
container ends the whole sweep**, and every container after it is never visited.
On a typical save `UIColony` itself is likely to be clean, which would mean the
fixup does nothing at all on most saves.

It would also be silent. `FixupSavegame` calls each fixup through
`procall(func, metadata, lua_revision, data)` and marks it applied regardless
(`CommonLua/SavegameFixup.lua:34-38`), so the fixup is recorded as done, will
never run again on that save, and nothing surfaces to the player.

## ⛔ What is NOT established

- **Whether `ipairs(nil)` raises in this engine.** Not tested. No Lua binary on
  this rig and the question was not put to a running game. The only evidence is
  stylistic: vanilla writes `ipairs(<expr> or empty_table)` in 36 places under
  `Lua/` and this site is unguarded — which is suggestive and nothing more.
  ⚠️ This engine is known to deviate from stock Lua semantics elsewhere
  (`#elements == 0` is true for `nil`, read at `Tracks.lua:808`), so stock
  behaviour must not be assumed in either direction.
- **Whether any player is affected.** The fixup only runs on a pre-1.1.0 save,
  which on Steam cannot be loaded at all (`config.OldSavegameBehavior` is
  `Platform.steam and "block" or "warn"`, `Lua/Config/config.lua:175`). The
  reachable population is the same narrow one as `90_SaveSanitizer`'s remaining
  passes: a non-Steam build, an old save, and the player clicking "Load anyway".
- **Whether it is worth fixing even if real.** A leaked upgrade modifier is a
  lingering *bonus*. Under the owner's 2026-09-08 rule — *"we fix anything
  negatives, a small positive I am not as concerned about"* — that is explicitly
  the class not worth chasing. ⇒ This entry is a record, not a proposal.

## What would settle it

One line on a loaded save that has been through the migration, checking whether
the fixup completed or died on its first clean container. Cheap, but it needs a
1.0.7-era save loaded on a non-Steam build, which this rig cannot currently
produce (`EF-075`, `EF-079`; and Steam allows only one branch selected at a
time, so the rig cannot hold 1.0.7 and 1.1.0 simultaneously).
