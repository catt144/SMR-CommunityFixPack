### C54 — ⛔ REFUTED: the "unguarded `ipairs(leaked)`" in 1.1.0's leaked-modifier fixup is a house idiom, not a defect  `[closed 2026-09-08 — filed and refuted the same day; kept for the reasoning error, not the finding]`

## What I filed, and why it looked real

While re-deriving row `R-5`, I read 1.1.0's new fixup
(`Lua/Buildings/Building.lua:1313-1345`) and saw this tail:

```lua
	for _, container in ipairs(containers) do
		local leaked                              -- nil until something is found
		for label, modifiers in pairs(container.label_modifiers) do
			...
					leaked = leaked or {}
					leaked[#leaked + 1] = { label = label, id = id }
			...
		end
		for _, entry in ipairs(leaked) do          -- leaked is nil if this container was clean
			container:SetLabelModifier(entry.label, entry.id, nil)
		end
	end
```

The reading was correct as far as it went: `leaked` really is `nil` for a
container with no leaked modifiers. The **inference** was wrong.

## Why it is not a defect

**The engine tolerates nil-iteration, and vanilla relies on it constantly.**

* **The identical shape appears at 18 sites** in shipped `Lua/` and `CommonLua/`.
  Two read in full as controls, both in code that runs for every player:
  * `CommonLua/Cooldown.lua:239-252` — `local removed` … `removed = removed or {}`
    … `for _, id in ipairs(removed)`. The ordinary case is that nothing matched
    the filter, so `removed` is `nil` at the loop.
  * `CommonLua/Libs/Notifications/Notifications.lua:430-437` — `local to_remove`
    … `for _, id in ipairs(to_remove)`. The ordinary case is that every
    notification preset exists, so `to_remove` is `nil` at the loop.
* **`ipairs(self.<field>)` on a field whose class default is `false`** appears at
  28+ distinct sites, including `SupplyGrid.lua` (×5), `ElectricityGrid.lua:67`
  and `LifeSupportGrid.lua:67` — grid code, the most-executed in the game.
* **105 archived logs contain zero `ipairs` errors**, while carrying other
  `bad argument #N to '<fn>'` lines, so such an error would have been visible.

⇒ If nil-iteration raised, this game would not boot, let alone run.

## ⛔ The reasoning error, which is the only reason this entry is kept

I wrote that vanilla "guards `ipairs(x or empty_table)` in 36 other places under
`Lua/`, and this one site is unguarded", and treated that asymmetry as evidence.
**It was a one-sided count.** I counted the guarded sites and never counted the
unguarded ones. Counting both sides takes one more command and inverts the
conclusion: the guard is a style preference in some files, not a necessity, and
the unguarded form is the house idiom.

⚠️ Worse, the answer was already recorded and I did not look. **`EF-005`**
(2026-07-29) states: *"Engine Lua tolerates `#nil`/`next(nil)`/`ipairs(false)`
(verified from working code paths) … **don't report/fix nil-iteration as
crashes**."* The facts index exists precisely so this question is asked once.
⇒ Consult `agent/facts/INDEX.md` before filing an engine-semantics claim.

✅ One thing this exercise did produce, and it is worth keeping: `EF-005`'s
`ipairs(false)` half and a separate `ipairs(nil)` half are now **re-derived by
route** from 18 + 28 shipped sites, rather than carried on the original entry's
unattributed "verified from working code paths". The fact is stronger than it
was, and its `verified:` field is still empty.

## What this does NOT disturb

`R-5`'s REMOVE verdict never rested on this. `Fix_UpgradeModifierLeak` was
retired because vanilla fixed the leak at source (`StopUpgradeModifiers` now
iterates with `pairs`, `Building.lua:1303-1311`) **and** cleans existing residue
with this fixup — which, on the evidence above, works fine.
