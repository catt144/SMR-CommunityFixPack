### F109 — A meteor-destroyed Atomic Accumulator, then rebuilt, left ~50 stacked objects on one hex (unconfirmed field report)  `[parked 2026-08-30 by owner — nowhere to go until more information arrives; no cause claimed]`

**Provenance, and its weight.** A public Reddit thread, supplied by the owner as
screenshots on 2026-08-30 (post ~22 days old). ⛔ **This is not a report to our
tracker, it is not reproduced, and the evidence is gone** — the reporter rolled
back ~5 Sols to an earlier save. There is no log, no savegame, and **no
statement of what other mods were loaded.** `F104` was this same shape — a
plausible-sounding field report that turned out to be Passage Network and not us
at all — and that precedent is the reason this entry claims nothing.

**Reported symptoms, in the reporter's own words.** A meteor strike destroyed an
Atomic Accumulator, and *"the glitch seemed to have been triggered by rebuilding
it"* (they did not know whether the rebuild was auto-queued). Then: the roof
*"keeps jumping up and down"*; it could not be demolished, because *"infinite
accumulators are appearing as soon as they are demolished"*; it could not be
repaired, because it *"requires infinite polymers"*, with the colony's Polymer
pool visibly draining; power on it *"jumped from positive to negative"*; and it
*"appeared to have sent like 50 'building has malfunctioned' messages, which is
how I saw it."* The cheat/debug menu did not help and the ground could not be
flattened under it.

## What is source-verified

1. **The building is vanilla.** Template `AtomicBattery`
   (`Lua/BuildingTemplate/AtomicBattery.generated.lua`), `display_name` "Atomic
   Accumulator", `__parents = { "ElectricityStorage" }`. Not a modded building.
2. **The Polymer cost is NOT an outlier.** `maintenance_resource_type =
   "Polymers"`, `maintenance_resource_amount = 2000`. A ranking of every
   `BuildingTemplate` puts 2000 at **32 templates**, with two higher at 10000.
   ⇒ **the "infinite polymers" is repetition, not a bad constant** — and that
   kills the most obvious cheap theory before anyone writes it down.
3. **The visuals are state-driven.** `charge_animation = "charge"`, `empty_state
   = "idle"`, `full_state = "full"`. A building whose power flips sign every tick
   re-applies its state every tick, which is what a "roof jumping up and down"
   looks like. (Consistent with the report; not evidence of a cause.)

## ⭐ The one real derivation — the message count is an arithmetic tell

`RequiresMaintenance:SetMalfunction` (`Lua/RequiresMaintenance.lua:247-261`)
latches:

```lua
function RequiresMaintenance:SetMalfunction()
    self.is_need_maintenance = false
    if not self:DoesRequireMaintenance() then return end
    if not self.is_malfunctioned then
        self.is_malfunctioned = true
        ...
```

It cannot fire again until `Repair()` (`:265-299`) clears `is_malfunctioned`.
⇒ **one object cannot produce ~50 malfunction messages.** Either the object was
repaired and re-broken ~50 times — which contradicts the report that it could
never be repaired for want of Polymers — or **there were ~50 objects.**

⇒ The reporter's *"infinite accumulators appearing as soon as they are
demolished"* is most likely **literally true**: demolish one, the next is
underneath. That single reading also explains the Polymer drain (N buildings ×
2000 each, no loop required) and the un-demolishable hex, without needing any
looping behaviour at all.

## ⚠️ The mechanism is LOCATED, NOT PROVEN

The rebuild path is `Building:DestroyedRebuild` → `Building:Rebuild` →
`PlaceConstructionSite` (`Lua/Buildings/Building.lua:1656-1694`). Its **only**
re-entrancy protection is a rendering flag:

```lua
if not self.destroyed or self.bulldozed
    or self:GetEnumFlags(const.efVisible) == 0 then --already rebuilding...
    return
end
```

`efVisible` is cleared by `Building:RebuildStart` (`:1630-1632`) and restored by
`Building:RebuildCancel` (`:1635`). So **"am I already rebuilding?" is answered
by "am I invisible?"** — a state machine keyed on a render flag. Every pass that
gets through calls `PlaceConstructionSite` again at the same position; the only
other guard in `Rebuild` is `assert(self.destroyed)`, and asserts do not run in
the retail build.

⛔ **What this entry does NOT have: any route that actually restores `efVisible`
on a destroyed accumulator mid-rebuild.** That was searched for and not found.
The single candidate in the tree — `ConstructionSite.lua:2610-2625`, which does
`ClearEnumFlags`/`SetEnumFlags` on the same flag — is
`GridSwitchConstructionSite`, for pillars and grid switches, and has nothing to
do with an accumulator. ⇒ **a fragile guard plus a consistent symptom set, with
no demonstrated path between them.** That is a lead, not a diagnosis, and the
project's own rule is to challenge the cause before filing one.

Noted and not implicated: `DestroyedRebuild` takes a `broadcast` argument that
runs `BroadcastAction(self, "DestroyedRebuild")` across every building of the
class (`:1681-1684`).

## ⛔ What would move this, and what would not

**The one cheap observation that settles it** was asked for in the thread by a
commenter — *"see if there's hundreds of atomic accumulators listed, check if
it's just laying them all in the same spot"* — and **the reporter never answered
it.** The Command Center buildings list at that hex separates ~50 stacked
objects from one glitching object outright, and it costs a player ten seconds.

⇒ **If a second report ever arrives, ask for exactly that, plus the mod list and
a save.** Until then this entry is dormant on purpose.

⛔ **Do not** open a fix on this. Do not "harden" `DestroyedRebuild`'s guard on
the strength of this entry: the guard is ugly, but ugly is not broken, and
nothing here shows it failing. A fix written now would be guessing at a defect
we have not seen, in a path every destroyed building in the game goes through —
which is precisely the class of change `FIX_POLICY` §4a exists to refuse.
