### F118 — `Fix_LayoutTechLock` clears the delete-on-load registration 1.1.0 gives the layout controller (P3, source-read — filed)  `[filed 2026-09-09: source-derived, NOT reproduced]`

- ⛔ **STATUS: SOURCE-DERIVED, NEVER REPRODUCED.** Effect on a player unmeasured.

#### The mechanism

- `GameVar("s_ConstructionControllerDeleteOnLoad", false)` (`Lua/Construction/Construction.lua:1018`);
  `OnMsg.PersistPostLoad` `DoneObject`s whatever it holds and resets it (`:1052-1056`).
- `ConstructionController:Activate` sets it to `self` (`:1065-1066`, both branches);
  `ConstructionController:Deactivate` opens with `s_ConstructionControllerDeleteOnLoad = false`
  (`:1226-1227`, both branches; 1.0.7 `:1154`).
- **New in 1.1.0:** `LayoutConstructionController:Activate` ends with
  `s_ConstructionControllerDeleteOnLoad = self` (`Lua/Construction/LayoutConstruction.lua:385`;
  0 hits in the 1.0.7 file), and its own `Deactivate` resets it first (`:411-412`).
- Our post-wrapper (`Code/Fix_LayoutTechLock.lua:90-121`) runs AFTER `:385`, and for
  each tech-locked entry calls `controller:Deactivate()` (`:112-114`) on the
  sub-controller → `ConstructionController:Deactivate` → the GameVar is `false`
  → the layout controller is unregistered while its dialog is still open.

On 1.0.7 the same teardown cleared the LAST sub-controller's registration (the
var pointed at the last `ConstructionController:Activate`), a smaller divergence
nobody had named; vanilla's own `LayoutConstructionController:Deactivate`
leaves the var `false` too, so the post-teardown value matches the
"dialog closed" state rather than the "dialog open" one.

#### Consequence (predicted)

Open a layout whose entries include a tech-locked building; save while the
layout dialog is open; load. Vanilla 1.1.0 deletes the layout controller at
`PersistPostLoad`; with the pack it survives the load. Whether that is a stuck
cursor/ghost or nothing visible needs a runtime read. Reachability: both branches
ship two layouts (`Data/LayoutConstruction.lua`: `SelfSufficientDome`,
`testing`); only the former is referenced.

#### Repair (one line, dual-branch safe)

Read `local before = s_ConstructionControllerDeleteOnLoad` before the teardown
loop; after it, `if before == self then s_ConstructionControllerDeleteOnLoad = self end`.
On 1.0.7 `before` is a sub-controller, never `self`, so nothing is re-asserted
there. Water markers are unaffected: the sub-controllers' `DestroyWaterMarkers`
is `empty_func` (`LayoutConstruction.lua:357-359`).

#### Control

The save/load above, pack on vs off, on a 1.1.0 colony with one un-researched
building in `SelfSufficientDome`. `reports/HOTFIX_2_AUDIT.md` §1 F-2.
