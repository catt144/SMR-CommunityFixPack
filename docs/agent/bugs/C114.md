### C114 — access to a large dome is measured from its centre, so hub and passage colonists get rescue rides home (P1) `[cand 2026-09-24: source-verified; measured on a reporter's save; one watched death]`

#### Must_Read_Header

Candidate, not built. Hub audit S1, cleared by the Codex
[resweep](../reports/MIGRATION_CROSSCHECK_HUB_RESWEEP_2026-09-24.md). It ships only as part of the
hub release set below. The build waits for the hub-footprint measurement.

#### Report

Steam, 2026-09-24 (TheGodUncle): colonists stuck outside near passages, and rides to "a new dome"
that is their own. The owner loaded the reporter's save twice
([HUB_FIELD_FINDINGS_2026-09-24.md](../reports/HUB_FIELD_FINDINGS_2026-09-24.md)): home Brussels is a
radius-19 Geoscape dome, and its hub sits 24-28 hexes from the centre.

#### Source (archived 1.1.1.405907)

- `IsUnitInDomeRange` (`Lua/Units/ColonistTransport.lua:19-28`) returns true on the dome's own hexes,
  otherwise `HexAxialDistance(unit, dome) <= dome:GetOutsideWorkplacesDist()`, measured to the centre.
- `HasLocalAccess` (:270-300) keeps same-map and in-dome access, then tries the community route
  (`HasAccessViaCommunity` :262-268, centre range again), then the fallback at :293-299:
  `g_Consts.DefaultOutsideWorkplacesRadius >= HexAxialDistance(self.holder or self, destination)`.
  A hub or passage is never recognised as a connected access point.
- The constant's help text reads "Colonists search this far (in hexes) outside their Dome"
  (`Lua/__const.lua:1944-1949`, value 20). For a radius-19 dome the "outside" band is about one hex.
  Intent tell (FIX_POLICY §4, tell 6): the code contradicts its own documented meaning.
- The Idle wrapper books an own-home rescue when access fails (:461-474).
  `HasAccessViaCommunity` and `IsDestinationInCommunityRange` are file-local, so a fix wraps
  `Colonist:HasLocalAccess`.

#### Harm

A colonist interrupted on a hub or in a passage beside a large dome waits outside for a shuttle, up
to a sol (`Colonist.lua:4000-4006`), instead of walking the passage it is standing in. With S2
([C115](C115.md)) that wait ends in death. Priced in the mid game, when Geoscape and Mega domes and
hubs appear. Every crossing interrupted by a job change or a dome shutdown is exposed.

#### Reach

R1 on large domes with hubs: the ordinary triggers are work reassignment and switching a dome off
(`Colonist.lua:1755-1758`, `Buildings/Dome.lua:1905-1935`). A nearer small community can make the
test pass, so not every interruption fails. Passage Network 1.38 adds crossings (exposure) and can
make some access checks pass (wider cluster); it is not required.

#### Control

- **Supports (measured):** on Brussels' hub, `c:HasLocalAccess(c.dome)` is false and
  `c.transport_task.dest_dome == c.dome` (field findings, both runs).
- **Refutes:** the same interruption on a hub at the shell of a small dome books a ride.
- **Build control (not run):** the resweep's large-dome interrupted crossing, with and without the
  fallback, with Passage Network off first. Success is safe entry with no rescue loop, not merely
  `access == true`. Controls: a small dome, an unrelated destination, a stale marker or holder off
  the hub, a removed last connection, a cross-map destination, an outdoor workplace, and a station
  commute.

#### Fix shape (owner approved the direction in principle, 2026-09-24)

A synchronous result-widening wrapper on `Colonist:HasLocalAccess` (FIX_POLICY §1.4, layer 3). Call
the original and keep a true result. Add true only when all four hold:
1. The destination is a Dome or has a valid Dome `parent_dome`.
2. It is the current-position query. The home-relative call at :447 keeps its meaning.
3. The colonist is physically on a live hub or passage. Neither `passage_hub` nor `holder == hub`
   proves this alone.
4. A still-connected endpoint dome's `dome_network` contains the destination dome. A hub has
   `hub_domes`, not `dome_network`, so derive the network through an attached dome.

It does not widen work assignment, service capacity or the train graph. Do not raise the global
radius. **Hub-footprint measurement done** (handoff item 6, the S4 test — see the 2026-09-24
sitting section below): condition 3's physical discriminator is hex ownership (the hub's own hex
or a connected passage/PassageRamp hex) OR standing elevated above terrain (`dz > 0`). A
marker-only version (`passage_hub` or `holder == hub` alone) remains ruled out; neither was shown
sufficient or necessary by the measurement.

## 2026-09-24 — hubset 04 sitting: hub-footprint measurement (S4)

- **MEASURED, TheGodUncle's save (`New Horizons 2 83`), game `1.1.1.405907`, junction on `main`
  (unfixed code), Passage Network off.** Two console passes roughly eleven real minutes apart
  (unpaused at normal speed between them), archived at
  [`docs/archive/logs/hubset04_footprint_Mars.exe-20260924-15.34.30-6aad2d75.log`](../../archive/logs/hubset04_footprint_Mars.exe-20260924-15.34.30-6aad2d75.log).
  Per-hub held units, classified by the hex under each unit (own hub hex, a connected
  passage/PassageRamp hex, a dome hex, or bare ground) and by height above terrain (`dz`):
  - Pass 1 (`SMRFOOT` lines 385, 397-398, 405 of the archived log): hub 2692 held 54
    (1 DomeInterior, 5 dome, 4 own-hex, 44 passage), hub 4113 held 14 (2 PassageRamp, 1 dome, 3
    own-hex, 8 passage), hub 1908 held 2 (2 own-hex), hub 2026 held 10 (1 dome, 4 own-hex, 5
    passage). Two more hubs (11985, 11714) held 0.
  - Pass 2 (lines 592, 604, 618, 643): hub 2692 held 86 (1/6/6/73 in the same order), hub 4113 held
    13 (3/1/2/7), hub 1908 held 14 (1 DomeInterior/1 own-hex/12 passage), hub 2026 held 27
    (1 DomeInterior/2 PassageRamp/1 dome/3 own-hex/20 passage).
  - Reconciliation (prediction 4): every `SMRFOOT` line's category counts sum to its `held` figure
    in both passes; no mismatch.
  - **Zero** held units, in either pass, were classified `none` (bare ground, no structure) with
    `dz 0`. Every off-hex unit was either on a passage/PassageRamp hex, or on a dome/DomeInterior
    hex while still elevated (`dz` 3 to 185, never 0) — the hub's ramps reaching over the dome hex,
    matching the reach hypothesis in this entry's Report section.
- **Verdict: S4 refuted, both passes.** The hub's walkable footprint is its own hexes plus its
  connected passages plus the elevated ramp/deck geometry that overlaps dome hexes. A hex-ownership
  test alone (own hex or passage hex) is necessary but not sufficient, since some legitimately
  on-ramp units sit over dome-owned hexes; the sound "on the hub" discriminator for 05's shared
  physical test (condition 3) is **hex ownership (hub or connected passage) OR `dz > 0`**.
  `holder == hub` was not directly exercised by this reading (all `SMRFOOTU` rows come from
  `hub.units`, not the `holder` field); 05 should not treat this as validating `holder == hub` on
  its own.
- **Drift instance (routed to 99):** the three per-hub console lines this link shipped with called
  a bare global `MapGet(...)`, which does not exist — `MapGet` is a method mixed onto map objects
  only (`CommonLua/Core/map.lua:14`, `MapInterface.MapGet`), called everywhere in the archived tree
  as `<map>:MapGet(...)` and aggregated over the global `LoadedMaps` array when a query must span
  every loaded map. The prepared lines' desk "smoke-run" did not catch this since it never
  exercised a live map instance. Corrected live with the owner at the keyboard (loop over
  `LoadedMaps`, call `MapGet` on each map); the corrected lines are the ones cited above. The
  retired prompt file was not edited in place since it is removed at this link's close-out; see
  99's inbox for the corrected text kept for the record.
