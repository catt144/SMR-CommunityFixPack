### C43 — **OUR OWN DEFECT:** the TestKit's `set_global` raises the engine's strict-global error on two Wave-5 probes  `[fixed 2026-08-11: TestKit 00_TestCore.lua — suite run carries ZERO TestKit [LUA ERROR] lines, both refusals print by name, and exactly one probe verdict moved (the declared AnomalyCaveInMap PASS→SKIP)]`

**How it was found.** Not by looking for it. The chain's F99 work swept the
archived logs for every `[LUA ERROR]` kind, on the standing rule that *"not
caused by our leg" is an attribution verdict, never a dismissal*. Two of the
seven distinct error kinds in the three archived logs are **ours**.

**The log, verbatim** (`docs/archive/logs/MarsDebug.exe-20260803-23.14.05-6a22b8b3.log:489-503`):

```
[LUA ERROR] Attempt to create a new global 'IsNearDome'
  Mod/SMR_CommunityFixPackTestKit/Code/00_TestCore.lua(172):  upvalue set_global
  Mod/SMR_CommunityFixPackTestKit/Code/00_TestCore.lua(192):   <>
  Mod/SMR_CommunityFixPackTestKit/Code/50_Probes_Wave5.lua(415):   <>
  [C](-1):  global pcall
  Mod/SMR_CommunityFixPackTestKit/Code/00_TestCore.lua(251):  field Run
  Mod/SMR_CommunityFixPackTestKit/Code/00_TestCore.lua(293):  field RunAll
Locals:
	                   k |   string IsNearDome
	                   v | function 0x0000024D736BF098
	        ENV_SPECIALS |    table 0x0000024D77E36A70 #0
	               defer | function 0x0000024D77E31CD8
```

and the identical shape at `:504-517` for `'AddAreaRubble'`.

**What it is.** The engine installs a strict-global guard that raises when
previously-undeclared name is assigned in `_G`. `00_TestCore.lua:172`'s
`set_global` helper installs temporary stubs for a probe and hits that guard for
any name the game has not already declared. `IsNearDome` and `AddAreaRubble` are
two such names.

**Why it matters even though nothing breaks.** The very next lines are

```
[SMRTest] PASS  AnomalyCaveInMap  [behavior] a false map is declined; a real map still reaches the shipped cave-in
```

so the probes work and the stubs are installed regardless — the guard reports and
does not unwind (`agent/facts/EF-008`). **The cost is entirely in the log.** Two
`[LUA ERROR]` lines with our mod's path in the stack, in a log a player or a
bug-reporter may read, sitting beside genuine engine errors and
indistinguishable from them at a glance. The pack's whole posture is that it
repairs errors rather than adding them.

⚠️ **Second instance in one day.** [F100](F100.md) is the pack printing a false
`inactive` line into every boot log for a module that is actually active. This is
the same shape — our own authoring noise in the owner's log, found only because
someone read the log rather than the summary.

**Repair options, none chosen — the call is the owner's:**

1. **Declare the names before assigning** — whatever the engine's own
   declaration path is (`rawset(_G, k, v)` sidesteps the metatable guard
   entirely, at the cost of bypassing a guard that exists for a reason).
2. **Restrict `set_global` to names that already exist**, and have the probe
   skip with a stated reason when its stub target is undeclared — the probes
   would then be honest about what they did and did not exercise.
3. **Leave it**, and add a line to the log-reading guidance saying these two are
   expected. Cheapest, and the worst of the three: it trains readers to skip
   `[LUA ERROR]` lines.

**Scope.** `Mod/SMR_CommunityFixPackTestKit/Code/00_TestCore.lua:172` and
whatever else routes through `set_global`; the two observed callers are both at
`50_Probes_Wave5.lua:415`. **Nothing built and nothing measured beyond the log
lines quoted above** — in particular, how many probes use `set_global` with an
undeclared name was not counted.

## ⚖️ 2026-08-10 — OWNER DECISION: option 2. `set_global` gets restricted; probes with undeclared stub targets SKIP honestly

Chosen over the `rawset` bypass (option 1 — silences a guard that exists for
a reason) and over documenting the noise (option 3 — trains readers to skip
`[LUA ERROR]` lines). **The work, queued into the next unattended chain**
(which launches the game anyway and verifies against a live suite run):

1. `00_TestCore.lua` `set_global` refuses to CREATE a global — it may only
   replace one that already exists (awget-style existence check against the
   real environment, not the mod env).
2. The two Wave-5 probes stubbing `IsNearDome` / `AddAreaRubble`
   (`50_Probes_Wave5.lua:415` callers) print
   `SKIP <stub target undeclared on this build>` instead of passing over a
   stub the engine rejected — honest about what was and was not exercised.
3. Suite run before/after; the acceptance reading is ZERO `[LUA ERROR]`
   lines from TestKit code in a full `RunAll()` log, with both probes
   reporting SKIP (not PASS) wherever the target is genuinely undeclared.

⚠️ Un-counted and now in scope for the same leg: how many OTHER probes call
`set_global` with undeclared names (the entry's own noted gap).

## 🔨 2026-08-11 — BUILT (TestKit commit `d8e1fbf`)

`unattended-2` prompt 1. ⚖️ **This section first read "the suite reading is
BLOCKED, so the status stays `filed`"** — the night's first launch found the
pack disabled in the Mod Manager. The owner re-enabled it and the run was
redone; **the acceptance readings are in the section below, and the status moved
to `fixed` on them.** The correction is left visible.

**What shipped.** `set_global` refuses to CREATE a global and returns
`false, <reason>`; existence is read against the REAL `_G` by clearing the env
shadow and reading back, which is what `safe_rawget`'s fall-through makes
possible (`Mod.lua:1577-1583`, installed at `:1606` — Src-verified today, not
carried). A refusal does **not** abort the call: the other stubs still install
and the probe body still runs, because a probe reporting FAIL for work it never
attempted is worse than the noise. The refused names come back as a **third
result** so a caller can report the honest verdict, and `WithGlobals` defers a
SKIP that `SMRTest.Run` applies **only** when the probe came back nil or FAIL —
so the mechanism cannot silently flip an existing PASS anywhere in the suite.
Each refusal also logs itself by name, which is how the un-counted gap gets
enumerated by execution rather than by grep.

⚠️ **Deliberately narrower than the engine's own guard.** `ModEnvMeta.__newindex`
(`Mod.lua:1556-1562`) also permits creating a name listed in
`PersistableGlobals`; we do not. "May only replace" is the decided semantics.

⭐⭐ **THE ENTRY IS WRONG ABOUT WHAT THESE TWO STUBS WERE DOING, and the
correction matters more than the noise.** Both names are **`local function`s in
the shipped source** — `AddAreaRubble` at `Lua\Buildings\CaveInRubble.lua:38`
and `IsNearDome` at `:79` (Src-verified 2026-08-11). A file local cannot be
reached through `_G` at all, so **those two stubs never took effect, before or
after this change** — the shipped `TriggerCaveIn` body has always called the
real helpers. The `[LUA ERROR]` pair was the *only* thing they ever produced.
⚖️ Two consequences, and the second is the owner's call:
1. `AnomalyCaveInMap` now returns **SKIP** naming what was and was not
   exercised (steps 1-3 held; the cave-in ran against the shipped helpers). That
   is the decision applied literally — and it is a real demotion, since the
   probe's discriminating half still passes.
2. **The two stub entries are dead code.** Deleting them would restore the PASS
   honestly and remove the SKIP entirely. That is a *different* repair from the
   one decided, so nothing was deleted; they stay put and stay visible.

⚖️ **Also a correction to this entry's own wording, and to the chain prompt
that inherited it:** there are not "two Wave-5 probes". There is **one probe**
with **two undeclared stub names in a single `TryWithGlobals` call** — which is
