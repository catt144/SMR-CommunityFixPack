### C110 — passage reach in the 1.1.1 route planner is one hop (P2) `[cand 2026-10-02: recheck possible-unconfirmed]`

#### Must_Read_Header

The independent [cross-check](../reports/MIGRATION_CROSSCHECK_2026-09-24.md) recommends dropping
the build proposal pending measured reach and an intent ruling. Status remains `cand`.

#### Report

Filed from the migration audit ([MIGRATION_AUDIT_2026-09-24.md](../reports/MIGRATION_AUDIT_2026-09-24.md), N2).
Field shape: Steam, 2026-09-24 (TheGodUncle): "other colonists don't use passages when moving from
one dome to another". Not a confirmed instance; the audit names this as the highest-reach native
explanation.

#### Source (archived 1.1.1.405907)

- `BuildReachableGraph` (`Lua/Units/Colonist.lua:3609-3662`) is a breadth-first search with a
  write-once predecessor map. A Dome node adds its cluster as `walk` nodes only when the Dome
  itself did not arrive by `walk` (`:3590-3596`, cleared):
  `if arrived_by ~= "walk" then for _, dome in ipairs(node:GetClusterDomes()) do AddReachableNode(reachable, dome, "walk", node)`.
- `Dome:GetClusterDomes()` returns `self.connected_domes` (`Lua/Buildings/Dome.lua:745-747`,
  cleared), declared as the array `{self, neighbour1, neighbour2, …}` of **direct** passage
  neighbours (`:534`). The transitive network is `dome_network` (`:535`, maintained by
  `Dome:UpdateConnectedNetwork :688-706`), which no graph function reads.
- The other admission is the walk scan `AddNodesInWalkDist` (`:3488-3532`), which uses
  `CheckWalkableDistanceCached` (`Dome.lua:244-251`) and so a pathfinder path length under
  `ColonistMaxDomeWalkDist` (400 m; `_GameConst.lua:149`). Passages are pathfinder tunnels, so a
  path under the cap may run through one; a longer path is not admitted.
- Net effect: from a start dome A with passages A–P–B, B enters the graph only if its path length
  is under the cap, or by train, elevator or shuttle. With a hub available it becomes a direct
  shuttle leg (`GetNextLegToward :3667-3706`); with none it is not a candidate at all
  (`GetBestReachableCommunities :3719-3789` scores only graph nodes).
- The legacy test the fallback still uses, `IsInWalkingDistDome` (`Dome.lua:299-319`), treats any
  pair in the same `dome_network` as walkable (`:315-316`), and `GetDomesPassagePath`
  (`Lua/Passage.lua:1300-1330`) computes multi-hop passage paths for exactly that case, with a
  passthrough cap of 8 domes read in `TryToEmigrateToDome :1922`.

History (seat B): 1.0.7 reached the whole network through city-level `dome_networks`; 1.1.0 removed
`Dome:GetConnectedDomes` and `CreateDomeNetworks`, added `GetClusterDomes`, and introduced the
graph. 1.1.1 kept the one-hop expansion unchanged.

Intent tell (FIX_POLICY §4): sibling contradiction, tell 3. The same file keeps a multi-hop
passage path function and an 8-dome passthrough cap, and the legacy walkability test honours the
whole network. Against it: the 1.1.0 rename to "cluster" and the deliberate `arrived_by ~= "walk"`
gate read as a design choice. **This entry does not rule intent**; that is the open question.

#### Harm

When the far dome fails the independent walk scan and no other route admits it, automatic
migration cannot select it through passage expansion alone. This is narrower than all two-hop
layouts. A shuttle can admit it; an explicit forced destination can use legacy fallback.

#### Reach

Conditional source reach: a serial A–P–B chain, with P a dome, whose endpoints fail the cached
walk scan. A single Passage Hub pairs all its attached domes directly (`Passage.lua:1593-1600`,
archived 1.1.1.405907), so a multi-spoke hub is not this trigger. Likelihood judged uncommon;
ordinary geometry is unobserved. Adding a third dome to phase 2b is not by itself sufficient.

#### Control — not yet run

Build A–P–B with A→B over the cap by path, no hubs. From a colonist in A, print the graph and the
leg toward B:

- **Supports:** B is absent from the graph, or present only as `shuttle` when a hub is on; the
  leg toward B is `false` without hubs.
- **Refutes:** B appears as `walk` with predecessor P.
- **Vacuous if:** A→B path length is under the cap (the walk scan admits B on its own).

A desk check needs no game: load the archived `BuildReachableGraph` with a stub city of three
domes whose `connected_domes` chain A–P–B and whose `g_DomeToDomeDist` marks A–B over the cap.

#### Fix shape (owner decides, after intent is settled)

The graph helpers are file-local. Hookable planner entrances include:
`Colonist:GetBestReachableCommunities` (a pre-wrapper could add the current dome's `dome_network`
members as `walk` nodes with the current dome as predecessor) and `Colonist:GetNextMigrationLeg`
(a post-wrapper could turn a `false` leg for a network dome into `{walk, dome, final = true}`).
A final walk leg takes `TryToEmigrate`'s direct path (:2071-2074) to `TryToEmigrateToDome`, whose
native passage lookup, passthrough cap and shuttle preference still apply; it does not guarantee
a passage walk. A leg-picker-only wrapper cannot add an absent automatic-choice candidate, and
a false-only wrapper misses an already-shuttle leg. `TryToMigrateHome` and `CanReachDomeForBuilding` also call
the leg picker, and every added node changes what the chooser scores. Not to be built before the
intent question is put to the developers or settled by an owner ruling.

#### Not opened

`PathLenCached` delegates to engine ConnectivityCheck; the Colonists tunnel mask includes passages
(`Config/_pfclasses.lua:48-50`, `Passage.lua:1736-1739`, archived 1.1.1.405907), but actual choice
and length remain unmeasured. The cross-check read both patch notes and all literal cluster
readers: work, service, security, faction, station, arrival, rescue and UI effects make global
cluster widening a design change. The notes do not settle migration-only intent. The report
also covers scoped cluster interception, data surgery, paired wrappers, per-leg replanning and
the temporary distance-cache window before `Dome:BuildingDailyUpdate` (:1225-1228).
