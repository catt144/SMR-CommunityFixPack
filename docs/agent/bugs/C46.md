### C46 — St. Elmo's Fire's `"destroy"` branch empties the trap but leaves its power modifier standing, so the trap produces phantom power forever  `[filed 2026-08-11 by the corun-pt15 sitting's F15 rider — OBSERVED on retail 1.0.7.396349; NOTHING BUILT, owner decision]`

**How it was found.** Not by looking for it. The `corun-pt15` sitting took the
F15 rider (research points from the destroy branch) after PT-15 was banked, and
the `CP15.TrapRead` taken afterwards showed a trap holding **zero** wisps while
still reporting its full pre-destroy production.

**The omission, in the shipped function.** `SetLightTrapMode(mode)`
(`Lua\Mysteries\Fireflies.lua:674-701`), `"destroy"` branch (`:676-688`):

```lua
for _, trap in ipairs(MainCity.labels.LightTrap) do
    reward = reward + #trap.fireflies * 100
    for i = #trap.fireflies, 1, -1 do
        trap.fireflies[i]:SetCommand("Die")
    end
    trap:SetWorkState("work_empty")      -- <- the ONLY state it clears
end
```

There is no `trap.el_prod_modifier:Change(0)`. Compare the sibling `"free"`
branch at `:689-699`, which *does* re-`Change` the modifier on every trap.

**Why it never heals.** `Change` **sets absolutely**
(`Lua\Modifiers.lua:321-331` — the game `UndefineClass`es CommonLua's additive
`ObjectModifier` at `:288`), so the stale value persists until something writes
a new one. The only writers are `:346` (release), `:479` (catch) and `:692`
(the free branch) — **all three require wisps**, and the same destroy branch
permanently stops wisp spawning (`SinkholeBase:BuildingUpdate` gates on
`lighttrap_mode ~= "destroy"`, `:248-250`). ⇒ nothing can ever clear it.

### The measurement (retail 1.0.7.396349, pack 81/81 active, game PAUSED)

Log `docs/archive/cp15sitting_Mars.exe-20260811-15.09.30.log`, L1592-L1601,
`LightTrap#1631`, ~7 game hours after the destroy (well past every wisp's
`Die` destructor):

| field | before destroy | **after destroy** |
|---|---|---|
| `#trap.fireflies` | 15 | **0** |
| `el_prod_modifier.amount` | 15000 | **15000** |
| `electricity_production` own / resolved | 15000 / 15000 | **15000 / 15000** |
| `GetUIPowerProduction()` | 15000 | **15000** |
| grid element `production` | 15000 | **15000** |
| `work_state` | `contain_fireflies` | `work_empty` |
| `working` | true | **true** |
| `mystery.fireflies_destroyed` | 0 | 15 |

⇒ **15,000 internal units = 15 displayed power, produced by a trap holding
nothing.** `work_state` went to `work_empty` and `working` stayed **true**, so
the grid keeps counting it — `ElectricityProducer:OnModifiableValueChanged`
publishes `self.working and self:GetPerformanceModifiedElectricityProduction()`
(`Lua\ElectricityProducer.lua:68-73`), and `working` is what gates the grid
figure, not `work_state`.

**Scale:** a Solar Panel is 2000 internal units, so the phantom output is worth
~7 Solar Panels on the observed 15-wisp trapful — and it scales with whatever
the trap happened to hold at the moment of the choice. On the same save an hour
earlier the trap held **95** wisps; answering then would have left **95,000**
(≈47 Solar Panels) standing permanently.
