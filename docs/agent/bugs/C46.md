### C46 — St. Elmo's Fire's `"destroy"` branch empties the trap but leaves its power modifier standing, so the trap produces phantom power forever  `[wontfix — owner ruling 2026-08-12 ("Lets just write that one off since its not a true bug"), on the same day's re-grade: the harm is forced-only, no organic route to a nonzero modifier at destroy time exists in current source (once-only choice, two callers, all writers free-mode-gated); the code omission is real but unreachable, so nothing is built. Filed 2026-08-11 by the corun-pt15 F15 rider; re-opens if any route to free→destroy or a "none"-mode modifier write ever surfaces]`

**How it was found.** Not by looking for it. The `corun-pt15` sitting took the
F15 rider (research points from the destroy branch) after PT-15 was banked, and
the `CP15.TrapRead` taken afterwards showed a trap holding **zero** wisps while
still reporting its full pre-destroy production.

**The omission, in the shipped function.** `SetLightTrapMode(mode)`
(`Lua\Mysteries\Fireflies.lua:674-701`), `"destroy"` branch (`:676-688`):

```lua
for _, trap in ipairs(MainCity.labels.LightTrap) do
    reward = reward + #trap.fireflies * 100
    for i = #trap.fireflies, 1, -1 do
        trap.fireflies[i]:SetCommand("Die")
    end
    trap:SetWorkState("work_empty")      -- <- the ONLY state it clears
end
```

There is no `trap.el_prod_modifier:Change(0)`. Compare the sibling `"free"`
branch at `:689-699`, which *does* re-`Change` the modifier on every trap.

**Why it never heals.** `Change` **sets absolutely**
(`Lua\Modifiers.lua:321-331` — the game `UndefineClass`es CommonLua's additive
`ObjectModifier` at `:288`), so the stale value persists until something writes
a new one. The only writers are `:346` (release), `:479` (catch) and `:692`
(the free branch) — **all three require wisps**, and the same destroy branch
permanently stops wisp spawning (`SinkholeBase:BuildingUpdate` gates on
`lighttrap_mode ~= "destroy"`, `:248-250`). ⇒ nothing can ever clear it.

### The measurement (retail 1.0.7.396349, pack 81/81 active, game PAUSED)

Log `docs/archive/cp15sitting_Mars.exe-20260811-15.09.30.log`, L1592-L1601,
`LightTrap#1631`, ~7 game hours after the destroy (well past every wisp's
`Die` destructor):

| field | before destroy | **after destroy** |
|---|---|---|
| `#trap.fireflies` | 15 | **0** |
| `el_prod_modifier.amount` | 15000 | **15000** |
| `electricity_production` own / resolved | 15000 / 15000 | **15000 / 15000** |
| `GetUIPowerProduction()` | 15000 | **15000** |
| grid element `production` | 15000 | **15000** |
| `work_state` | `contain_fireflies` | `work_empty` |
| `working` | true | **true** |
| `mystery.fireflies_destroyed` | 0 | 15 |

⇒ **15,000 internal units = 15 displayed power, produced by a trap holding
nothing.** `work_state` went to `work_empty` and `working` stayed **true**, so
the grid keeps counting it — `ElectricityProducer:OnModifiableValueChanged`
publishes `self.working and self:GetPerformanceModifiedElectricityProduction()`
(`Lua\ElectricityProducer.lua:68-73`), and `working` is what gates the grid
figure, not `work_state`.

**Scale:** a Solar Panel is 2000 internal units, so the phantom output is worth
~7 Solar Panels on the observed 15-wisp trapful — and it scales with whatever
the trap happened to hold at the moment of the choice. On the same save an hour
earlier the trap held **95** wisps; answering then would have left **95,000**
(≈47 Solar Panels) standing permanently.

## ⚖️⚖️ 2026-08-12 — OWNER CHALLENGE RE-GRADES THIS ENTRY: the measured harm is FORCED-ONLY; no organic route exists in current source

The owner asked the control question this entry should have asked itself:
*"We destroyed the wisps via a command no normal play could reach. Could our
way of destroying the wisps be why we observed a defect?"* Re-derived from Src
the same day. The answer splits cleanly in two:

**The omission is real, and the forcing did not create it.** The command the
rig called is not exotic — `SetLightTrapMode("destroy")` is verbatim the
payload of the player's own *Experiment upon them* click
(`Mystery 11.generated.lua:470-471`, re-read; the scenario runs that one call
and nothing else that touches a trap). The branch really does kill every wisp,
set `work_empty`, and skip the modifier (`Fireflies.lua:676-688`, re-read),
and the wisps' own death path never compensates — `Firefly:Die` (`:533-545`)
and `Firefly:Done` (`:313-321`) remove the wisp from `trap.fireflies` without
any `Change`. Whatever the modifier holds at destroy time stands forever.

**But what the modifier holds at an ORGANIC destroy click is ZERO — so the
harm we measured cannot happen in normal play.** Three source facts, each
re-read 2026-08-12:

1. **Every writer of `trap.el_prod_modifier` is gated on mode `"free"`:** the
   4 AM release (`:341-346`), the catch (`:474-479`), and the choice's own
   free branch (`:692`). In the pre-choice mode `"none"` a catch inserts the
   wisp and sets `work_state` but writes **no** modifier — a pre-choice trap
   produces 0 power while holding wisps (the sitting's own daytime read
   confirms the shape: `amount=0` on a trap that had caught 33).
2. **`SetLightTrapMode` has exactly two callers in the entire tree** — the
   once-only choice's branches (`Mystery 11.generated.lua:440` free, `:471`
   destroy; the `SA_WaitChoice` fires once per game). There is no organic
   path that sets mode `"free"` and later `"destroy"`.
3. ⇒ An organic *Experiment* click transitions **none→destroy** with the
   modifier never written: wisps die, `amount` stays 0, **no phantom power**.
   The 15,000 this entry measured stood only because the rig performed a
   **free→destroy** flip on a save whose choice was already consumed — the
   exact sequence normal play cannot produce. The rig's forcing did not cause
   the omission, but it DID manufacture the only state in which the omission
   is visible. (The earlier "answering at 95 wisps would have left 95,000
   standing" scaling sentence is part of the withdrawn framing — an organic
   destroy answer at that moment would have arrived with `amount=0` too.)

**Provenance, stated precisely:** this is a SOURCE derivation, not a play
sample — no organic destroy-first playthrough has been run (that costs a full
mystery). It re-opens if anyone finds a route to free→destroy, a `"none"`-mode
modifier write, or a wisp killed in free mode outside `DetachFromWaterSource`
(none found: the `:239` sinkhole cull and both `SetCommand("Die")` sites are
destroy-gated). Fourth challenge-driven correction in the project's record,
and the second overturned by re-deriving the ROUTE while every cited line
stayed right.

**Consequences.** The player-visible defect claim is WITHDRAWN; what remains
is a latent correctness omission in shipped code (and verbatim in our
`Fix_WispRewards` copy). The owner decision shrinks accordingly: wontfix/
document is the natural default; a defensive `trap.el_prod_modifier:Change(0)`
in our own replacement's destroy branch is available as belt-and-braces if
ever wanted. `CP15F15.savegame.sav` still answers the forced state's R4
question if anyone cares to load it.
