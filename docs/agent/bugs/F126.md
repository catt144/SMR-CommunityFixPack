### F126 — the F23 additive handler outlives the feature it completed `[fixed 2026-09-23: desk controls; owner play pending]`

#### 2026-09-23 build response

**Fixed by retirement:** `Fix_FounderTraitNotification` and its registrations/probe requirements are removed. **desk-MEASURED:** `python tools/desk_gamepatch_retirements.py` runs the focused old-pack/native controls. The actual pre-retirement additive handler from `16ff1aa` reaches archived
1.1.1.405907 `AddNotification` (`CommonLua/Libs/Notifications/Notifications.lua:25-89`)
and `PropertyObject:CreateInstance` (`CommonLua/PropertyObject.lua:1472-1489`): an
unknown-id assertion precedes the base fallback, whose instance has an empty id.
With the old handler absent it emits none. A valid-id control exercises the same
constructor and a weakened-assert scratch variant loses the diagnostic. EF008's
report-and-continue assert is explicitly modeled; class/UI services are stubs.
Rendering and retail assertion behavior have not been watched in this build.

No new state or migration; deletion introduces no executable removal residue. Retail display/trait-generation checks remain owner-only.

See [build report](../reports/GAMEPATCH_1.1.1_BUILD_2026-09-23.md) for commands, controls, claim limits and owner play.

#### Historical filing and evidence


F23 was a dead shipped handler: `OnMsg.ColonistAddTrait` in `Lua/ColonyViability.lua:306-314`
(1.1.0.403908) indexed an array by a group name and never fired. `Fix_FounderTraitNotification`
added a second handler with the same conditions and a real set, and left the vendor's in place
(`Code/Fix_FounderTraitNotification.lua:49-59`).

Game 1.1.1 removed the feature rather than repairing it. The handler is gone from
`ColonyViability.lua` (the only `OnMsg.ColonistAddTrait` in the 1.1.1 tree is the unrelated
Dictatorship check at `Lua/Factions/Factions.lua:1466-1473`), and the `FounderGainsTrait`
`NotificationPreset` is gone from `Data/NotificationPreset.lua`: a whole-tree grep for the id
finds no file on 1.1.1 and two (the handler and the preset) on 1.1.0. The 1.1.1 triage read the
first half and filed KEEP ("no working Founder notification replaced it"); it did not read the
second.

Our handler still fires on 1.1.1 (its `Require` asks only for the two globals, `:37-40`) and
calls `AddNotification("FounderGainsTrait", …)` (`:56`). `AddNotification` looks the id up in
`NotificationPresets`, asserts on a miss, and then builds the instance from the base
`NotificationPreset` class (`CommonLua/Libs/Notifications/Notifications.lua:32-48`); this
engine's `assert` reports and continues. So a Founder gaining a Positive, Negative or
Specialization trait now produces a notification with the base class's defaults, for a
feature the vendor deleted.

**Repair contract.** Remove the module and all registrations, and retire its TestKit probe.
No saved state is written, so no cleanup or migration is needed. F23 is closed by the
vendor's deletion, not by a repair.

**Falsifier.** On 1.1.1 with the pack on, read `NotificationPresets.FounderGainsTrait` from
the console: if it is a preset, or if a retail `AddNotification` rejects an unknown id instead
of building the base instance, this defect is absent. The TestKit probe cannot settle it: it
stubs both `FindNotification` and `AddNotification`
(`SMR-BugFixPack-TestKit/Code/40_Probes_Wave4.lua:985-1012`), so its retail PASS on the
2026-09-23 on-leg (`docs/archive/logs/ck208on_…:421`) shows only that our handler still fires.
What the player sees has not been observed.

**Harm.** During ordinary play, whenever a Founder gains a qualifying trait: a notification
with no title or text of its own, or an assert line, for a feature the game no longer has.
Misleading rather than destructive; Founders are present from sol 1, so an early colony sees
it first.
