### C52 — three defects on the Mod Manager detail path: screenshots can never download, description hyperlinks are disabled, thumbnails never refresh  `[parked 2026-08-20 on the owner's ruling — FROZEN, may be revisited; filed 2026-08-16 by the smr-community-fixes coverage sweep — SOURCE-VERIFIED ×3; ⭐ their stated mechanism REFUTED by our own EF-008 and the real one found; ⚠️⚠️ CORRECTED same day on the owner's challenge — the hyperlink half was wrongly closed as a design choice and is a DISABLED path with two hard tells; ⛔ no fix proposed, ⛔ not a release gate, ⚠️ release-relevant awareness. Prior art: fredware's *Repair Mod Manager Browser*]`

## The claim, and what happened to it

`fredware`'s **SMR Community Fixes** #4 says mod thumbnails and screenshots do not display
in the in-game Mod Manager and that descriptions are mangled. The symptom is real. Their
account of *why* does not survive our own facts shelf, and the actual cause turns out to be
simpler and better evidenced.

## Their mechanism — REFUTED, and by our own record

The premise, all of it verified here by symbol:

- `ModUI_Entry` derives from `ProtectedPropertyObject` (`CommonLua/UI/ModManager.lua:1207-1208`).
- The class declares `ScreenshotPaths = false` (`:1229`) and **never** `ScreenshotUrls`.
- `ModsUIRetrieveModDetails` assigns `mod.ScreenshotUrls = table.keys(unique_images)` (`:797`),
  sorts it (`:798`), then calls `ModsUIDownloadScreenshots(mod)` (`:799`).
- `ProtectedPropertyObject.__newindex` asserts on a key the class never declared
  (`CommonLua/PropertyObject.lua:1819-1823`).

The conclusion — *"a mod that has screenshots therefore asserts on that assignment, and
where asserts halt, the `ModsUIDownloadScreenshots` call on line 799 is never reached"* —
fails on two independent grounds:

```lua
	__newindex = function (table, key, value)
		local class = getmetatable(table)
		local old_value = rawget(class, key)
		assert(old_value ~= nil, string.format("Creating a new key '%s' in a protected object '%s'.", key, class.class))
		rawset(table, key, value)          -- :1823 — runs regardless
	end
```

1. **`rawset` is on the line after the assert.** Even in a build where the assert reported,
   the write still lands.
2. **`EF-008` (ours, 2026-07-29): `error()` and `assert()` do NOT unwind — they report and
   execution continues** with the next statement. There is no halt to hide behind.

⇒ In retail the assignment succeeds, `:798-799` run, and the missing `ScreenshotUrls`
declaration is a tidiness issue with no behavioural consequence. **This is what the house
rule about challenging a stated cause is for**: the citations were all correct and the
mechanism was still wrong.

## The real cause — one local read outside its block

`CommonLua/Libs/Paradox/ParadoxMods.lua:213-276`, `WaitDownloadModScreenshots(mod)`:

```lua
	local thumbnailUrl = mod.DisplayImagePath
	if thumbnailUrl then
		local path, file, ext = SplitPath(thumbnailUrl)          -- :220
		local version = …                                        -- :221
		local mod_prefix = PdxModsScreenshotsPath .. mod.Pdx.ModID .. version   -- :222
		local file_path = mod_prefix .. ext                      -- :223
		local err, temp                                          -- :224
		…
	end                                                          -- :245  ← scope ends here

	-- todo: this is not working                                 -- :247   ← shipped comment
	--download screenshots
	local urls = mod.ScreenshotUrls                              -- :249
	if urls then
		mod.ScreenshotPaths = {}
		temp = PdxModsScreenshotsPath .. "screenshot.temp"        -- :252  ← global write
		…
		for i = 1, #urls do
			local url = urls[i]
			local path, file, ext = SplitPath(url)                -- :256  (ext is re-declared, fine)
			local file_path = mod_prefix .. "_" .. i .. ext       -- :257  ← mod_prefix is NIL
```

`mod_prefix` is local to the `if thumbnailUrl` block and dies at `:245`. At `:257` it is a
global read, therefore `nil`, therefore **"attempt to concatenate a nil value" on the first
screenshot of every mod that has any**. `temp` (`:252`) and `err` (`:258`) leak out of the
same dead scope and are created as globals.

**The developers labelled it.** `-- todo: this is not working` sits immediately above the
loop (`:247`) and again above the `ScreenshotUrls` block that feeds it
(`ModManager.lua:786`). Under `FIX_POLICY` §4 this is not an interpretation of intent — it
is the shipped source stating that the branch does not work.

⛔ **A second question, deliberately left open:** `AsyncPopsDownloadFile` (`:260`) has **zero
definitions in all of `ModTools\Src`**. It is either a native engine export Lua cannot see or
genuinely missing. It does not matter for the diagnosis — `:257` raises before `:260` is
reached — and we do not claim it is absent, only that Lua cannot see it.

## The second defect — a thumbnail cache that never invalidates

Same function, `:218-240`:

```lua
		local version = mod.Pdx.PreferredVersion and mod.Pdx.PreferredVersion ~= "" and ("_" .. mod.Pdx.PreferredVersion) or "_1"
		local mod_prefix = PdxModsScreenshotsPath .. mod.Pdx.ModID .. version
		local file_path = mod_prefix .. ext
		local err, temp
		if not io.exists(file_path) then
			…download…
		end
```

The cache key is **mod id + preferred version, and nothing else** — no timestamp, no ETag,
no revalidation. `if not io.exists(file_path)` skips the fetch outright. ⇒ **a mod author who
replaces the preview image without publishing a new version leaves every player who already
saw the mod looking at the old thumbnail, in Browse All, in Installed Mods and on the detail
page, indefinitely.**

⚠️ **This one is relevant to our own step ④.** Three mods are queued for upload with preview
art (`reports/preview_art/FINAL_*.png`). The practical consequence: *if a preview image is
ever changed after publication, the change reaches only players who have not cached it,
unless the mod version also moves.* Recorded as awareness on the checklist; nothing to decide.

## Defect 3 — description hyperlinks are a DISABLED path, not a design choice

⚠️⚠️ **CORRECTED 2026-08-16, same day, on the owner's challenge.** This section first read
*"NOT a defect by our bar — code a developer commented out is a decision, not a slip."*
**That was wrong, and the owner's distinction is what exposed it:** *a design choice and a
planned-but-deferred fix are two different things*, and commented-out working code is
evidence of the second. The corrected reading carries **two independent hard tells**, which
is more than most entries in this tracker are filed on.

`ModsUIRetrieveModDetails` runs mod descriptions through
`ParseDescriptionAsHTML` → `ParseHTML` (`ModManager.lua:740-743, :761-762`). The shipped
`HTMLParser` turns anchors into inert `label [URL]` text
(`CommonLua/X/HTMLParser.lua:108-119`):

```lua
	if tag == "A" then
		local r, g, b, a = GetRGBA(self.HyperlinkColor)     -- :109  ← computed, never used
		local link_ref = attributes.href
		if not link_ref then return "" end
		link_ref = link_ref:gsub(" ", "+")
		if (processed_html or "") ~= "" then
			return string.format("%s [%s]", processed_html, link_ref)
		else
			return link_ref
		end
		--return string.format("<color %s %s %s><h OpenUrl %s %s %s %s underline>", r, g, b, link_ref, r, g, b) .. processed_html .. "</h></color>"
	end                                                     -- :118  ← the clickable form, disabled
```

**Tell #3 — sibling contradiction, and it is exact.** The commented line is **live and
working in the sibling parser**, `CommonLua/X/MarkdownParser.lua:49`:

```lua
	return string.format("<color %s %s %s><h OpenUrl %s %s %s %s underline>", r, g, b, link_ref:gsub(" ", "+"), r, g, b) .. link_text .. "</h></color>"
```

Same markup, same `<h OpenUrl …>` handler, same colour treatment, same `gsub(" ", "+")`.
One parser ships it enabled; the other ships the identical line commented out. `FIX_POLICY`
§4 tell (3) is *"the same author wrote it correctly elsewhere"* — this is that, verbatim.

**Tell #2 — dead code / a computed value discarded.** `local r, g, b, a =
GetRGBA(self.HyperlinkColor)` at `:109` is consumed by **nothing** once `:118` is commented
out. The parser class therefore carries a live `HyperlinkColor` property that cannot affect
any pixel. A discarded computed value is `FIX_POLICY` §4 tell (2) on its own.

**The consuming end is wired.** `ModsUIModDetails.lua:683` handles `OpenUrl(argument)`, so
the details UI already knows how to open a hyperlink. The receiver is built and the producer
is switched off upstream of it.

⇒ **The intended behaviour is the clickable link.** The shipped behaviour is a temporary
disablement that reached retail. That is a defect, not a decision, and `C47`'s "an unset
field is not a self-contradiction" reasoning does **not** transfer — an unset field is an
absence, a commented-out working line is a removal.

⛔⛔ **BUT: deferred does not mean safe to re-enable, and this is the caution that survives
the correction.** A line may have been commented out *because it misbehaved*. This is exactly
the area where fredware hit real trouble — his own §5N carries a whole clause about XText's
`<fallback_font>` mode selecting a face that returns font id `-1` after a successful
preflight at otherwise valid UI scales. If `<h OpenUrl …>` markup destabilised XText in some
state, the comment IS the workaround and uncommenting it reinstates the original fault.
⇒ **the repair shape here is "re-enable and observe", not "uncomment it"** — and observing
means the mod browser on screen, which is `FIX_POLICY` §4's UI/affordance class where source
reading has no validity. No fix is proposed on this record.

## Scope note on their remedy

Their §5N asks one module to declare a class field, wrap four functions, run its own
HTML/BBCode formatter at a fixed point size, download and cache images itself, and build a
**private font cascade discovered at runtime from loaded text styles** to place non-ASCII
glyphs. That is a feature reimplementation of the mod browser, not a minimal repair of a
located defect, and it is out of scope for this pack on that ground independently of whether
the underlying defects are real. The two defects above are real; the remedy shape is theirs.

## Player route

Open the in-game Mod Manager and view any Paradox-hosted mod that has screenshots. Both
symptoms are on the default path; neither needs a cheat, a console or an unusual save.
⚠️ **Not observed by us** — no leg has opened the browser with instrumentation, and this
entry claims source, not a screen.
