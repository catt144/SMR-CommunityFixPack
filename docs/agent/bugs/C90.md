### C90 — a declined `DataPatch` self-check still patches the presets (P3) `[cand 2026-09-12: source-read + desk-reproduced; OUR defect, not the game's]`

⚠️ **This is a defect in the fix pack's own core, not in the game.** Found 2026-09-12 while building C89
(`prompts/C85_C88_BUILD.md`), by a desk leg that asked what happens when the module's `Require` fails.
**Filed, not fixed** — the build prompt's standing rule is *anything else interesting, file it, do not fix it*.

#### The mechanism (SOURCE, `Code/00_Core.lua`)

`SMRFixPack.DataPatch(id, opts)` returns `run`, and installs `OnMsg.ClassesBuilt` / `ModsReloaded` /
`DataLoaded` / `DataChanged` handlers that call it. Those handlers are installed **at file scope,
unconditionally** — that is the documented F87 design, because `OnMsg.DataLoaded` alone does not fire on the
enable path. `run()` then checks, in order:

1. `ctx.classes_built`
2. `ctx.patched`
3. `SMRFixPack_Disabled[id]` — the user veto, re-read before every pass (the A1 lesson)

and then calls `opts.pass(ctx)`. **It never reads `SMRFixPack.fixes[id].status`, and it never learns whether
`apply()` succeeded.**

So for a module shaped

```lua
apply = function()
    local err = SMRFixPack.Require(FIX_ID, { ... })
    if err then return err end     -- entry -> "inactive", logged "inactive (<reason>)"
    patch()
end
```

a failing self-check makes `run_apply` latch the entry `inactive` and log it — and then the very next
`ClassesBuilt` fires the pass anyway and **patches the shipped presets**. The player-visible result is the
inverse of F87: the log and `ListFixes` say the module switched itself off for safety, while it has in fact
edited shipped data.

⚠️ **The obvious guard is the wrong one.** `run_apply` writes `entry.status` only *after* `apply` returns
(`00_Core.lua`, the `run_apply` branches), and `apply` is where `patch()` is called — so on a **live re-apply**
(the Mod Options reconciliation path, which 00_Core's own comment says must do the work) the pass legitimately
runs while `status` still holds its previous value. A pass that gated on `status == "active"` would break that
path. What works is a module-local flag set in `apply()` after the self-check passes, and read by the pass;
`Code/Fix_FactionDomeSizeGate.lua` uses exactly that (`self_check_passed`).

#### How bad is it, per site (INFERRED from the bodies; not observed in play)

⚠️ Reachability is **U — unknown**, and that is the honest tier: the trigger is a self-check FAILING, which
needs a game update that removes one of those targets. It has not happened to either module. ⛔ So this is not
a live harm today; it is a latent one that arrives on the update that trips a self-check, which is precisely
when the safe-disable is supposed to protect the player.

- `Fix_SaintBlessing` — the pass would run with one of the three targets missing. Its own body calls what it
  needs, so the likely outcome is a throw caught by `run()`'s `pcall`, which sets status `error`. **Partially
  self-limiting, but the pass may have edited presets before the throw**, and which edits landed is not stated
  anywhere. NOT traced line by line here.
- `Fix_SinkholeIndestructible` — the `Require` is for a classdef and a global the *pass* checks again, so the
  overlap may make it benign. NOT traced.

⭐ Both need the same read before anyone calls them safe, and neither read was done here: *list what the pass
writes before its first use of the missing target.*

#### Fix sketch (NOT built; the shape is the owner's call)

Two candidates, and they are not equivalent:

1. **Per module**, the `self_check_passed` flag — three lines each, no core change, no risk to the other 45
   modules. What C89 does.
2. **In the core**, have `DataPatch` capture the apply verdict itself — e.g. `run()` refuses until the module
   has recorded a successful apply, with the live-re-apply ordering handled explicitly. One place instead of
   three, but it changes a seam every `DataPatch` module sits on, so it is a §3a/§1 decision and wants its own
   desk control and a re-run of every DataPatch module's legs.

⛔ **Do not "fix" this by gating the pass on `entry.status == "active"`** — see the ⚠️ above; that breaks the
live re-apply path 00_Core deliberately supports.

#### Control — what would prove it, cheaply

Desk, no game: `tools/desk_c89_faction_gate.py` leg **(k2)** already does it for the guarded module — it removes
`FactionLikeDomes.CountDome` so `Require` fails, fires the pass, and demands that nothing is patched. Point the
same leg at `Fix_SaintBlessing` or `Fix_SinkholeIndestructible` with one of their `Require` targets removed and
it should show the presets edited while the entry reads `inactive`. That harness is the template.

#### Not opened
