#### Mechanism and correction to the initial filing

`Code/00_Core.lua:315-420` installs DataPatch handlers unconditionally. The runner checks classes built,
already patched, and veto (`:364-367`), then calls the pass (`:373`) without learning the result of
`apply()`. Register's `run_apply` sets inactive on a returned reason (`:456-459`).

**The prediction "data edited while the entry stays inactive" was too narrow.** Both measured bypasses
call `ctx.heal()` (`:345-356`), restoring active and clearing detail and update_suspect. The initial
inactive log survives, but ListFixes now says active and UpdateSuspects no longer lists the failed target.
No outer runner exception occurs in these cases.

#### Reach and recommendation — still an owner decision

**INFERRED route: U — unknown** remains the reachability tier. Target-loss injections prove the mechanism, not a game
update or ordinary player route that actually removed a target. No field harm is claimed. Settling
observation: a naturally failing self-check plus actual post-pass status/data on a changed game build.

**INFERRED recommendation:** prefer **per-module apply-success guards for Saint and Sinkhole** as the bounded repair: the census
does not justify expanding to OnDataReady. A future implementation must define reset/retry behavior,
rather than treating a once-true flag as an everlasting successful verdict. Alternative: a core
apply-verdict contract with explicit ordering and controls for all four DataPatch callers; that changes
shared code and remains the owner's §1/§3a call. **Neither is built here.**

Do not gate the pass on `entry.status == "active"`. run_apply updates status only after apply returns;
a legitimate live re-apply can call the pass while previous status is inactive. Generic optional
reconciliation supports that ordering even though these four modules are not optional today.
