### F104 — NOT OURS: Passage Network's `CreateDomeNetworks` returns nothing, vanilla indexes the nil, and the engine flags us for it (?, high)  `[filed 2026-08-23 — NOT OUR DEFECT; cause derived AND confirmed live on the rig; nothing to build; pending closure on a reply + reporter confirmation]`

## Where this came from

The **first field reports against the published listings.** Two GitHub issues,
same reporter (Keelai), 2026-08-23, running six mods: Passage Network, Flexible
Passages, Geyser Removal, No Passage Penalty, Start with all Breakthroughs, and
this pack.

> "removing a home in order to move to a larger dome … colonists wont automove
> as they did, also when manually moving the game triggered mod error … they
> seem to expect there to be a shuttle and thus dont use passages" — and, as a
> follow-up, "Also appears when changing workplace."

The reporter's own hypothesis (passages being skipped in favour of shuttles)
turned out to be the right neighbourhood and the wrong mechanism.

## The mechanism (SOURCE-derived, then MEASURED)

1. Passage Network replaces the global `CreateDomeNetworks`:
   ```lua
   function CreateDomeNetworks()      -- no city parameter, no return value
       LH_ClearConnections()
       LH_AddAllConnections()
   end
   ```
   Vanilla's takes `city`, sets `city.dome_networks`, and **returns** the table
   (`Lua/Passage.lua:1096-1107`).
2. All three vanilla call sites use the same idiom and then index the result:
   `AreDomesConnectedWithPassage` (`Passage.lua:1116` → `networks[d1]` at `:1117`),
   `RecalcWorkingMediaCentersCheck` (`Dome.lua:1642` → `pairs(networks)` at `:1645`),
   `DbgShowDomeNetworks` (`Passage.lua:2135`).
3. `city.dome_networks` is `false` by default (`City.lua:11`) and is reset to
   `false` on every passage connect/disconnect (`Passage.lua:1244`, `:1361`).
4. ⇒ The first reader after any passage change gets `nil` and throws.
5. `AreDomesConnectedWithPassage` sits directly under `IsInWalkingDistDome`
   (`Dome.lua:256-259`), which is the colonist emigration AND workplace-selection
   path — hence "won't automove" and "also when changing workplace".

**Self-healing, one abort per passage change.** PN's own `LH_AddAllConnections`
calls the captured vanilla `CreateDomeNetworks(UICity)`, which repopulates
`city.dome_networks` as a side effect — too late for the call in flight, but
every later reader succeeds. So the blast radius is ONE aborted operation per
passage connect/disconnect, not a persistent breakage. ⚠️ Not true for non-main
cities (underground/asteroid): the side effect only ever covers `UICity`, so
`RecalcWorkingMediaCentersCheck`'s `for _, city in ipairs(Cities)` loop would
throw every time on those. Untested — no multi-city capture exists.

## Why WE are named and Passage Network never can be

`OnMsg.OnLuaError` (`Mod.lua:3001-3013`) is a blind substring test — for each
loaded mod, *does your `content_path` appear anywhere in `err` or `stack`?* The
shipped comment says "rough estimation based on call stack". Ours
(`Mod/SMR_CommunityFixPack/`) is there because we replaced a global and our file
now labels a frame vanilla used to label. PN's is not, because a Lua traceback
lists only LIVE frames and its function returned at `:1116`, one line before the
throw at `:1117`. ⇒ **The mod that produced the nil is structurally invisible to
the check; a pass-through is named instead.** This is `EF-065`(a) firing for the
first time in the field.

⚖️ **We are not a contributing cause, and vanilla's own code proves it.**
`OnMsg.DomesConnected` / `OnMsg.DomesDisconnected` set
`g_TransportationModeToCommunityCache = false` (`Colonist.lua:2483-2488`) — the
transport cache is wiped at exactly the moment `dome_networks` is invalidated, so
the next `FindTransportationModeToCommunity` MUST recompute and MUST reach
`AreDomesConnectedWithPassage` in vanilla too, with an identical stack minus our
line. ⚠️ Honest caveat: `Fix_ShuttleTransportCache` also recomputes when shuttle
availability flips, so it adds calls into that path at other moments — it widens
the window, it does not create it, and it did not create this one.

## Both portals carry the same code

Steam `3607071753` and Paradox `pdx_124952_5` extract to a **byte-identical**
`Code/PassageNetwork.lua` (md5 `f9c0e49b9c5233b809a4095742482855`) and an
identical `metadata.lua`. The `_5` in the Paradox folder name is that store's
file-revision index, not a mod version — `metadata.lua` still reads `version 14`,
`pdx_version "4"`, `saved_with_revision 384011`. There is no fixed build to point
a reporter at.

**Also dead on this game version, same mod:** it wraps `ConnectDomesWithPassage`
and `DisconnectDomesConnectedWithPassage`, and **neither global exists** in the
shipped Lua (zero hits across `Src/Lua`), so those two wrappers capture `nil` as
"vanilla" and define globals nothing calls.

## Screened and NOT the cause (recorded so it is not re-derived)

* **A second candidate, withdrawn.** `IsInWalkingDistDome`'s
  `dist[2] <= const.ColonistMinDistToIgnorePassage` clause (1200 m) means that
  with a working Shuttle Hub, passage-connected domes beyond 1200 m stop being
  walkable — which PN never overrides, defeating its own headline promise. Real
  property of the code, but the live capture explains the report without it, so
  it is NOT carried as a cause here. Left recorded because it may be degrading
  their passage travel independently.
* **`Fix_VacuumWalks` diverting colonists to shuttles** — refuted. PN marks every
  dome in a network as a direct neighbour, so `GetDomesPassagePath` always returns
  a 2-element path and `passage_path_domes` is always 0; the `>= 8` branch cannot
  fire.
* **Load order** — not a factor, and the opposite of a problem. `ModsLoaded` order
  in both logs is `SMR_CommunityFixPack` FIRST (`Mod.lua:2162` prints it), i.e.
  the position `EF-054` argues for. No other mod in the set — nor this pack —
  references `CreateDomeNetworks`, `dome_networks` or `connected_domes`.
* **Flexible Passages** — patches the passage *construction* cursor only
  (`fp_construction_rules`, `fp_lifecycle`); no routing code; and it was NOT in
  the reporter's log's loaded-mod list at all.
* **No Passage Penalty** — a pure data rule on the `Consts` label, which does not
  match `_Construction$` and cannot reach any of this.
