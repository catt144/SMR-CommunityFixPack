### F117 — `Fix_ArrivalDeaths`'s re-choose branch throws on 1.1.0: `ChooseDome` now takes the colonist, we still pass the traits table (P1, source-read — filed)  `[filed 2026-09-09: source-derived, NOT reproduced, shipped in v5]`

- ⛔ **STATUS: SOURCE-DERIVED on both trees, NEVER REPRODUCED.** The repair
  LANDED 2026-09-09 (99a, "What was BUILT" below) and has never been seen
  working or failing in play. ⛔ Do not move status without the control below.
- **Owner decision:** `PLAYTEST_CHECKLIST.md` item 127 — fix before the hotfix-2
  upload (recommended) or ship and fix in hotfix 3.

#### The defect

`Code/Fix_ArrivalDeaths.lua:197-206` (half (b), the F53 re-choose): when an
arriving colonist's assigned dome is not in walking distance of the landing spot
and no elevator provides the route, the pre-wrapper on `Colonist:Idle` re-picks
among the walkable candidates:

```lua
local new_dome, new_elevator = ChooseDome(self.traits, domes, false, dome_elevators)   -- :201
```

That is the 1.0.7 contract — `function ChooseDome(traits, domes, safety_dome, dome_elevators)`
(1.0.7 `Lua/_GameUtils.lua:426`), whose callees took a traits table
(`Community:GetScoreFor(traits)`, 1.0.7 `Community.lua:367`).

1.1.0 changed the contract: `function ChooseDome(colonist, domes, safety_dome, dome_elevators)`
(`Lua/_GameUtils.lua:486-500`), and every callee now reads `.traits` off the
argument:

- `Community:GetScoreFor(colonist)` → `TraitFilterColonist(self.traits_filter, colonist.traits)`
  (`Lua/Buildings/Community.lua:442-445`) → `FilterObjectAttributes(filter, obj_attributes)`
  does `obj_attributes[attrib]` for every key of the filter (`Lua/Filter.lua:113-121`);
- the same body then calls `residence:IsSuitable(colonist)` for every filtered
  residence with free space (`:449-456`), and `GetResidenceComfort(residence, colonist)`
  reads `colonist.traits["Tourist"]` (`Residence.lua:424-432`);
- `Community:HasFreeLivingSpaceFor(colonist)` calls `residence:IsSuitable(colonist)`
  for every working residence with free space (`:402-418`);
- `Residence:IsSuitable(colonist)` is `not pred or pred(colonist.traits)`
  (`Residence.lua:198-200`), and the preds index their argument
  (`ColonistFilterFunc`, `Lua/Stats.lua:192-197`: `traits.Child`, `traits.Senior`, …).

With `colonist` = our `self.traits` table, `colonist.traits` is `nil`. So:

| candidate dome has … | what runs | result |
|---|---|---|
| a non-empty `traits_filter` | `FilterObjectAttributes(filter, nil)` → `nil[attrib]` | **throws** |
| a residence with `filter_residents ~= "Everyone"` and free space (nursery, retirement home, hotel) | `pred(nil)` → `nil.Child` | **throws** |
| only "Everyone" residences and an empty filter | `pred` is nil, filter loop empty | no throw; scores computed with trait filtering silently disabled |

All nine 1.1.0 callers of `ChooseDome` pass a colonist/unit (`RocketBase.lua:1978`,
`:2064`, `:2103`; `CargoTransporterNew.lua:996`, `:1045`, `:1088`; `Colonist.lua:1452`;
`ColonistTransport.lua:870`; `DroneFactory.lua:230`). We are the only caller
passing a traits table.

#### Why no instrument saw it

Class (c) of the 1.1.0 re-verification's table — semantics moving under a
wrapper. `Require` checks that `Colonist.Idle`, `ChooseDome` and friends EXIST
(they do). `sigcheck` bounds arity of REPLACEMENT sites (this is a wrapper).
`bodycheck` pins `Colonist:Arrive` (byte-identical across branches). The
`Colonist:Idle` branch diff (58 lines) shows nothing in the arriving branch —
the change is in a callee two calls away.

#### What a player would see (predicted, not measured)

The throw is inside the colonist's `Idle` command thread. What the engine does
with an erroring command thread is NOT established here (a restarted command? a
colonist stuck "arriving"?). What IS on record: a Lua error in a mod frame
raises the once-per-session mod-error dialog naming the pack (`EF-065`; F115's
shape). Frequency: **NOT ESTABLISHED.** The line that stood here until
2026-09-09 — *"ordinary mid-game"* — is withdrawn (99b): it was an inference from
the F53(b) trigger alone, and the desk trace in §Control shows the ordinary far
landing does NOT reach the throw. What does is a specific layout: the arrivals'
only link to a welcoming dome is a passenger train station by the pad, AND one of
those domes carries a trait filter or a filtered residence with free space. No
field report and no log line has matched it.

#### Repair sketch (the fixing link designs it; this is the shape, not the code)

Pass the colonist on the 1.1.0 body. ⛔ ck118 binds: `self` on both branches
unguarded would hand 1.0.7's `GetScoreFor(traits)` a colonist object and
mis-score every dome (`colonist[attrib]` is nil for every trait) — wrong, not a
throw, but wrong. The discriminator must be read from a callee BODY, not a
label. The shape change is only visible at CALL time (the callers changed, not
`ChooseDome`'s own body), and `Community:GetScoreFor` needs `g_Consts` (a
per-game GameVar), so an apply-time probe cannot run it. Candidate: a one-shot
probe inside the wrapper, on first use, of `Community.GetScoreFor` on a stub
community (`HasLifeSupport`, a one-key `traits_filter`, empty residences) with a
stub argument whose `traits` field is a capture table — 1.1.0 indexes the
capture (`colonist.traits[attrib]`), 1.0.7 indexes the stub itself
(`traits[attrib]`); cache the verdict; UNKNOWN ⇒ fall back to the shipped
behaviour (skip the re-choose) rather than guess. Rider: a Test Kit probe that
drives the re-choose branch on a stub with a filtered residence and expects no
throw.

#### What was BUILT (link 99a, 2026-09-09 — `777249d`, `cb6415f`)

The repair is **not** one token. The argument is decided at runtime, per
FIX_POLICY §2a, because passing `self` on both branches would have been the
*worse* defect: on a 1.0.7 body `GetScoreFor(traits)` reads `colonist[attrib]`,
nil for every trait, and every dome is **silently mis-scored** — measured below
as 110 → 100, no throw, invisible to every instrument. Decision 118 forbids
exactly that.

- **The discriminator** (`Code/Fix_ArrivalDeaths.lua`, between the
  `F117-PROBE-BEGIN/END` markers). One stub community, **two** calls to the
  shipped `Community:GetScoreFor`, differing only in where a probe trait is
  hung — on the argument itself, and on the argument's `.traits`. The
  life-support term (the one value that differs between branches) **cancels in
  the difference**, and the surviving `1` names which table the shipped body
  indexed. No constant's value is read anywhere in the decision.
- **Why that body**: `ChooseDome` walks the list from
  `GetDomesReachableByColonists`, which inserts only `Dome`s
  (`_GameUtils.lua:449-478`; the `Station` sweep contributes their `.labels.Dome`,
  never a station), and **no `Dome` declares `GetScoreFor` on either tree**, so
  `dome:GetScoreFor` resolves to the `Community` body the probe reads.
- **When**: first use, not apply time — the 1.1.0 body opens on
  `g_Consts.CommunityEval*`, a per-game GameVar. Cached for the session.
- **Fail-closed**: neither shape, both shapes, a non-number, or a throw ⇒
  UNKNOWN ⇒ the re-choose **stands down** and vanilla's own destination
  survives, with the decline named once in the log. Routed through
  `SMRFixPack.Require`'s `probe` form so the pcall trap, the strict-`true` rule
  and the decline logging are the shared ones.
- **Published for the kit**: `SMRFixPack.ArrivalDeaths.ReadArgShape()` (pure,
  caches nothing) and `.CachedArgShape()`, the way
  `SMRFixPack.LayoutTechLock.IsLockedOut` already is — so the kit probe asserts
  *this module's* verdict rather than a second copy of the rule that could drift
  from it and still pass.
- **Kit probe** `ArrivalDeathsChooseDomeArg` (`20_Probes_Wave2.lua`, kit
  `c1114ed`). It does **not** call `Colonist:Idle` — that body blocks, and the
  kit's 2026-07-25 wedge lesson forbids faking a yielding body into a busy loop
  — so it drives the shipped `ChooseDome` over a stub dome with a trait filter
  and a filtered residence. It **refuses to pass vacuously**: it first shows the
  other argument is really worse on this branch (throw on 1.1.0, mis-score on
  1.0.7) and returns SKIP, never PASS, if it cannot tell them apart.
