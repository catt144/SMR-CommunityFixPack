### F103 — `Fix_CrystalMysteryHang`'s save-restored repeater duplicates hourly `CrystalFlyAway` broadcasts after a mid-mystery load (?, cand)  `[filed 2026-08-13 — our own defect-candidate, source-derived, unmeasured, harm nil; post-release WATCH; remedy sketch below, not built (ship line frozen)]`

## Where this came from

Prompt 2b of the `d13-rescue` chain inserted the F86/§3a orphan gate into this
module's repeater body (commit `91fc5d0`) and, while there, saw and DISCLOSED a
second, separate behaviour it deliberately did not repair — the disclosure
lives in the shipped header (`Code/Fix_CrystalMysteryHang.lua:44-52`, "Disclosed,
NOT repaired here"). Prompt 4's notes flagged that the finding had then
"passed three prompts without a home — please either file it or kill it."
The terminal audit re-read the module (2026-08-13) and files it: the mechanism
is real as written. Killing it was considered and rejected — "no harm found"
is a verdict this project records, never a reason to un-record a defect.

## The mechanism (SOURCE tier — never measured)

1. `start_repeater()` (`:66-86`) creates a game-time thread whose loop guard is
   `my_gen == repeater_gen` — both **module-chunk locals** captured as upvalues.
2. A save taken while that thread is blocked in `Sleep(const.HourDuration)`
   captures the thread **with by-value copies of its upvalues** (`EF-023`).
3. On the next load *with the pack installed*, `OnMsg.LoadGame` (`:109-118`)
   calls `stop_repeater()` — which bumps the **fresh chunk's** `repeater_gen`.
   The restored thread never sees that: it compares its own restored copies,
   which still match each other. If the mystery is still active and the crystal
   gone, LoadGame then starts a NEW repeater from the fresh chunk.
4. Result: two lineages posting `Msg("CrystalFlyAway")` on their own hourly
   clocks. A further save/load inside the window can add a third, and so on.

## Why the harm is nil (and what would change that verdict)

* The message has **exactly one consumer** in shipped content — the Mystery 10
  scenario's `WaitMsg("CrystalFlyAway")` — and the whole point of this module
  is that the consumer *wants* the message. It completes on the first receipt;
  subsequent broadcasts land with no listener registered.
* Our own `OnMsg.CrystalFlyAway` handler (`:101-103`) re-enters
  `start_repeater()`, which no-ops while `repeater_running` is true.
* Every lineage self-limits: the `crystals_mystery_active()` check ends it when
  the mystery ends or changes; its own frozen 10-sol deadline ends it
  regardless; and the §3a orphan gate (`:78`, since `91fc5d0`) ends any lineage
  whose pack is gone.
* **What would change the verdict:** a game update adding a second
  `CrystalFlyAway` consumer with non-idempotent behaviour, or a measurement
  showing the duplicate broadcasts doing anything at all. Either reopens this
  as work.

## Remedy sketch (recorded, NOT built — ship line frozen, harm nil)

The loop guard reads upvalue copies; a restored lineage can never see a fresh
generation through them. But `SMRFixPack` inside the closure is a **global**
lookup, resolved live at each wake — that is exactly why the orphan gate works
on restored lineages. The same route fixes this: keep the generation on the
registry table (e.g. `SMRFixPack.crystal_repeater_gen`, a plain in-memory field
on a mod global — NOT persisted state) and have the loop compare `my_gen`
against that instead of the `repeater_gen` upvalue. A restored thread then
reads the fresh session's counter on its first wake and exits. One small
behaviour change to a shipped module ⇒ belongs to a post-release build window,
not to an audit; priced at roughly one line plus a parse sweep plus the
standing baseline.

## What a measurement would look like (if ever wanted)

Save mid-mystery with the repeater running (crystal composed, Epilogue popup
open), load, and count `CrystalFlyAway` posts per game hour — a probe can
register a counting handler. >1 per hour confirms; 1 refutes (and would mean
the persist model is wrong somewhere more interesting than here).
