### F48 — Station-connector savegame fixup no-op (P3, high defect / low impact)  `[fixed 2026-08-11: Code/90_SaveSanitizer.lua — 7 tracks repaired to the clean-chain value on the fixture, held across two save+reload round trips, zero on the already-clean save]`
`Station.lua:1346`: `ProcessTrackElements(ResolveMap(track, track.elements))` — paren
misplaced, should be `ProcessTrackElements(ResolveMap(track), track.elements)`; migration
no-ops (may contribute to "tracks won't connect" on old saves). **Fix:** re-run corrected
pass in one-shot LoadGame sweep.
*Blocked 2026-07-25 (wave 3), during the sanitizer build.* The defect is confirmed exactly
as written — `ResolveMap(track, track.elements)` returns one value, `elements` arrives nil,
`#elements == 0` is true for nil in this engine (`Tracks.lua:808`) and the function returns
immediately, so `SavegameFixups.A_StationConnectorElements3` (`Station.lua:1341-1354`)
re-orders nothing. What blocks the repair is what the corrected call actually does:
`ProcessTrackElements` → `OrderTrackElements` (`Tracks.lua:520-624`) **clears and rebuilds
`el.connections` and rewrites `node_idx` on every element**, then the caller repositions
every element in Z and recomputes pillars and sections (`:840-900`). Its only failure
handling is `assert(false, "unable to find the expected number of track elements")`, and
assert does not unwind in this engine — so a track it cannot walk (a broken element, a
repair site — i.e. exactly F45's situation) has its connections half-rewritten and
execution continues. Running that over every track of every save on load, with no way to
test it in-game from this seat, risks more than the P3 it repairs.
**To unblock:** an in-game test on a save with (a) a healthy multi-station network and
(b) a meteor-damaged track, comparing `track.start_el`/`end_el` and route formation before
and after. If it holds up, the pass belongs in `90_SaveSanitizer.lua` behind a one-shot
`SMRFixPack_*` flag on `UIColony` so it cannot re-run every load.
*2026-07-26: that test is now written up as **PT-37** in `docs/PLAYTEST_CHECKLIST.md`
(exact console commands for both cases) and sits on the user's in-person list. PASS on
both cases → implement in the sanitizer, skipping tracks that carry repair sites; a dirty
FAIL on the damaged-track case → close `wontfix — repair riskier than the defect`.*

⭐ **2026-08-04 — the instrument was Src-verified before the sitting leans on it**
(`corun-batch-1` prompt 1). Three corrections, all visible per chain rule 5; the
procedure above is left standing so the changes are legible.

**Reachability: fine.** `ProcessTrackElements(map, elements, start_element,
adjust_iter)` (`Tracks.lua:807`) is a plain file-scope global and is not in
`ModEnvBlacklist` — callable from the console and the mod env. The corrected
call's first argument is a **map**, which is what `ResolveMap(qa_t)` returns;
`ResolveMap` is a C global taking **one** argument
(`CommonLua/LuaExportedDocs/Game/realm.lua:92`), which is exactly why the shipped
`ResolveMap(track, track.elements)` silently drops `elements`.

**(a) The failure path is NARROWER than this entry says.** `OrderTrackElements`'
failure branch (`Tracks.lua:614-620`) is `assert(false, "unable to find the
expected number of track elements")` → (EF-008, it does not unwind) → **it
restores the original element order** from the `table.copy` taken at `:569` →
`return` nil. `ProcessTrackElements` then hits `if not OrderTrackElements(...)
then return end` (`:818`) and returns **before any Z-repositioning, section
building or pillar work**. The blocking sentence above — *"the caller
repositions every element in Z and recomputes pillars and sections"* — describes
the SUCCESS path only, and overstates the failure case.

**(b) But the residue is real, and this entry UNDER-states it.** The restore
fixes the array order and nothing else. Left behind permanently, and saved:
`start_el.connections = {}` plus a rewritten `connections` on every element the
walk reached (`:578-580`, `:606-617`); a forced `start_el.node_idx = 1` (`:579`)
while the success-path renumbering (`:632-635`) never runs — **a duplicate
`node_idx` is the signature to look for**; and leftover hash keys
`elements[<el>] = true` that are never cleared.

**(c) ⛔ A meteor-damaged track may not sample the failure path at all, and the
source cannot settle it.** `BreakTrackElement` (`Track.lua:618-659`) does **not**
remove the element from `track.elements` — it sets `element.broken = <site>`,
hides it, and places a `TrackConstructionSite`, whose `__parents` are
`{ "ConstructionSite", "TrackGridElement" }` (`TrackElement.lua:580-583`). Two
`TrackGridElement`s therefore occupy the broken hex, while the walk's
`HexGetTrackGridElement` is `hex_grid:GetObject(q, r, "TrackGridElement")`
(`TrackElement.lua:1-3`) and returns exactly one of them. If it hands back the
hidden original the walk **succeeds** and case B is case A again — **the decider
is UNSAMPLED, and a clean result there is not a pass.** ⇒ **Case B must be gated
on a pre-mutation read** that asks the live `object_hex_grid` for each element's
own hex and compares identity; run the corrected call only when that read
predicts a failing walk.

**(d) Do NOT hand-assign `start_el`/`end_el`.** `ProcessTrackElements` sets both
itself on the success path (`:820-822`), so the procedure's assignment line is
redundant there — and on the FAILURE path it writes endpoints the shipped repair
would never write, making case B look more destructive than the repair is.
