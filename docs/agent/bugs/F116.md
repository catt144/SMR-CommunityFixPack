The entry as filed made four claims and its author flagged two as unsound. A
second session re-extracted both bodies (ours, `Code/Fix_TrackSalvageWipe.lua`;
shipped, `Lua/Buildings/TrackElement.lua:467-618`) and diffed them
structurally — comments stripped, not by keyword count.

1. ✅ **PRE-SORT revalidation is genuinely absent — CONFIRMED, and it is the
   crux.** 1.1.0 runs `if not skip_track_process then track_obj:ProcessAllElements() end`
   at `:473-476`, *before* `all_elements` is built (`:480`) and *before* the sort
   (`:487`), with the comment *"make sure elements' node_idx is actually valid,
   since we're assuming it represents the distance from the start."*
   ⛔ **The correction note's suspicion was right and the rescue does not
   work:** our four `ProcessTrackElements(map, ...)` tail calls are the
   **POST-split** step — they are 1.1.0's own `:609-613` in the 1.0.7 four-call
   form. They run *after* the sort, on the *resulting* tracks, and **only inside
   the split branch**. A call after the sort cannot validate the sort's input,
   and the two trim branches (`last <= 1`, `first >= n`) plus the
   `mass_delete or not idx` early return get no processing at all where 1.1.0
   revalidates before every one of them.
2. ⚠️ **Orphan policy — REAL, but a divergence, not a "stripped guard", and it

   have saved.** ⛔ The filing's "STING" (that we strip the guard against the
   corruption we exist to repair) is **WRONG as written** — we do not remove a
   guard, we substitute a harsher policy. ⛔ **NOT repaired** — see below.
3. ✅ **`skip_track_process` is not forwarded — CONFIRMED.** Ours called

   the flag — `Construction.lua:1692`, `el:DemolishAndSplitTrack(false, "skip process")`
   during a station build — and it does the element processing itself afterwards
   (`:1696-1704`). Ours therefore re-entered with the flag nil and ran the

4. ❌ **Empty-track `DoneObject` cleanup — DROPPED as a defect.** 1.1.0's

5. ⭐ **NEW — a fifth divergence the entry never listed.** 1.1.0 post-processes

   `ProcessTrackElements(map, elements .. elements_under_construction)`,

   other is empty** — so a track holding BOTH completed and under-construction
   elements gets **no post-split processing at all**. ⛔ **NOT repaired.**

#### Why the missing revalidation actually bites (the route, not the citation)

`node_idx` is **not** maintained as distance-from-start:

- stamped at build time from a monotonic per-track counter,
  `track_obj.last_node_idx + 1` (`Tracks.lua:370-371`, `:393-401`) — build order,
  which need not be physical order if a track is extended from its start;
- ⭐ **on a track MERGE it is restamped from two independent array positions** —
  completed elements get `el.node_idx = #track.elements`, under-construction ones
  get `el.node_idx = #track.elements_under_construction`
  (`TrackElement.lua:415-425`). **Those two sequences collide**, and the merge
  only repairs them via `ProcessTrackElements` when
  `#track.elements_under_construction == 0` (`:430-432`) — i.e. **not** in the
  mixed case that produced the collision;
- default is `node_idx = false` (`TrackElement.lua:173`).

`all_elements` in this function is exactly those two arrays concatenated. So
after a merge that left work under construction, the sort key is stale and
duplicated while the zone math — the `first`/`last` outward walk and the
`last+1 .. first-1` deletion range — assumes array order == physical order. The
deletion set is then **physically scattered**, which also manufactures the
disconnected fragments that become orphans (claim 2). ⇒ **the two findings are
one mechanism.** `ProcessAllElements` → `ProcessTrackElements` →
`OrderTrackElements` restamps `el.node_idx = i` in walked physical order
(`Tracks.lua:632-633`); that is precisely what 1.1.0 added and what our copy
lacks.

⭐ **This is not speculation about a state nobody has seen: our own PT-03
playtest reported exactly this outcome on 1.0.7** — the F44/F45 header says the
old comparator "sorted a never-stamped `node_idx` as -1 and CARRIED ON", the
zone math "deletes a physically scattered zone and strands fragments no seed can
reach". We treated the SYMPTOM (guard the non-numeric case, delete the stranded
debris). 1.1.0 fixed the CAUSE. Our copy keeps the 1.0.7 shape, so on 1.1.0 the
module is **strictly worse than vanilla on this axis** — the
`FIX_POLICY` §1.4b hazard ("a copy silently reinstates the old body's shape and
can undo the official fix"), realised.

#### What landed (2026-09-08, in-body, marked `-- FIX (F116)`)

- **the pre-sort revalidation**, at 1.1.0's own position (after the repair-site
  delegation, before `all_elements` is built). ⚠️ **Guarded, not assumed:**
  `if not skip_track_process and IsValid(track_obj) and type(track_obj.ProcessAllElements) == "function"`.
  ⛔ Deliberately **not** added to the `Require` block: a Require spec would make
  the module DECLINE where the method is absent, costing players `F44` and `F91`
  for nothing. The guard falls through to existing behaviour instead. ⛔ We
  cannot show 1.1.0 *added* `ProcessAllElements` — the 1.0.7 tree is gone
  (`EF-075`) — so the guard is a capability test, not a version test.
- **`skip_track_process` forwarded** to `self.broken:Demolish`.

⭐ **`F45` is NOT retirable** (the route note suspected it might be). It stops
being the primary defence — the revalidation now handles the common case — but
`ProcessTrackElements` bails **without restamping** when `OrderTrackElements`
cannot walk the track (`Tracks.lua:615-620`, `:818-819`), i.e. exactly when the
track is physically disconnected. F45's non-numeric guard stays as the backstop
for that case, and the module now says so at the guard.
