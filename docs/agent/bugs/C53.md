### C53 — the client hard-locked on the launch that downloaded our own published mod beside the identical dev junction  `[filed 2026-10-02: recheck possible-unconfirmed]`

## Why this is filed at all

It would have been easy to close this as "the log is clean, so nothing happened."
⛔ **The log being clean is not evidence the client is fine** — it is evidence that
*Lua did not error*. The owner's screen is the primary surface here and it said
hard lock; this project's own rule is that an unexplained observation gets
attributed, not discounted.

## What was measured, from outside the frozen client

| reading | value | what it rules out |
|---|---|---|
| `Responding` | **True** | not a classic Win32 message-pump hang |
| CPU delta | **0.16 s/sec** over a 6-second sample | ⛔ not a busy spin; ⛔ not fully idle — consistent with a render loop still drawing |
| threads / working set | 73 / 951 MB | nothing obviously exhausted |
| log growth | **zero bytes in ~7 minutes**, last line = TestKit load | the state machine stopped advancing *after* mod load completed |
| `PdxMods/pdx_156049_1/` | created **22:43**, session started **22:42:41** | the download landed **during** the locked session |

## What the log does say — the pack is not implicated by anything in it

`77 applied`, zero `[LUA ERROR]`, all three mods `Loaded mod def … unpacked from
appdata`, the fix pack at `v1.00-002` (the dev tree), and both 08-20 fixes
reporting normally (`LocalizedUIText: Back to Earth rollover wrapped on 1 rocket
class(es)`, `SpaceYDroneCapBullet: applied`). ⛔ **That exonerates the pack only
as far as a log can** — a lock that never reaches Lua would look exactly like
this too.

## ⭐⭐ THE SCREEN — supplied by the owner after the lock, and it changes this entry

*"the screen flicked and the menu was replaced with this, and stayed that way
till I alt F4'd."* What was on screen: **the pre-game menu's BACKDROP ART alone —
the Mars landscape with the rover — and no menu on top of it.** Not a crash, not
a black screen, not a frozen dialog: **the menu was torn down and nothing
replaced it.**

⇒ That is consistent with every outside measurement and explains all three at
once: the render loop keeps drawing a static backdrop (`Responding = True`,
0.16 s/sec), and nothing writes to the log because nothing errored — there was
simply no UI left to drive.

### The vanilla path that produces exactly this, read at Src

```lua
local function ModsUIDialogClose(dialog)
	if dialog.window_state == "destroying" then
		OpenPreGameMainMenu()
	else
		dialog:SetMode("")
	end
	g_InitialMods = false
end
```
`CommonLua/UI/ModManager.lua:59-66`

⛔ **The call that puts the main menu back is CONDITIONAL.** Only the
`"destroying"` branch reopens it; the other branch merely blanks the dialog's
mode. A mods-changed flow that reaches this function with the dialog in any other
state leaves the player looking at the backdrop with no menu — which is the
screenshot. The caller, `ModsUIDialogEnd` (`:124-166`), runs
`ModsReloadDefs()`, and on a real change does `LoadingScreenOpen` →
`ModsReloadItems()` → `ModsUIDialogClose` → `LoadingScreenClose` **inside a
created thread**, so a stall in that thread has no error path to the log either.

### ⭐ And the log carries a second, independent clue: our code never re-ran

`ModsReloadItems()` re-executes mod code, which in this repo's logs always
produces a **second block of `applied` lines** (the 08-19 Ged reload logged
150 = 2 × 75). ⛔ **There is no second block** — the archived log has exactly
**one** set of 77. ⇒ Whatever stalled, it stalled **before mod code re-ran**,
which places the failure upstream of every line this pack ships.

⚠️ **Still not derived.** Two things are unproven and must stay that way until
someone measures them: **which** branch of `ModsUIDialogClose` ran, and whether
the owner's session was in the mods dialog at all when the download landed.
⛔ Do not promote the paragraph above from *mechanism that fits* to *cause*.

## The one thing that was different about that launch

A **second copy of the same mod id** arrived on disk: the published Paradox
archive (`version 0`) downloading into `PdxMods/` while the dev junction
(`version 2`) was live. Every clean launch that day had exactly one copy.

⛔ **This is correlation and nothing more.** `H-09` documents the same
configuration but answers a different question (which copy loads), so it is a
neighbour, not a cause.

## What would actually settle it

1. ⭐ **The screen.** What was displayed when it froze — a mod-manager page, a
   download progress element, the main menu — is the single missing piece and it
   costs one screenshot next time.
2. **A deliberate repeat**, once, with the download present and the junction
   pulled — ⚠️ but pulling the junction costs the enable (`H-08`, `EF-055`) and
   is owner-only, so this is not free and is not owed.
3. If it never recurs, this entry stays filed and unreproduced, which is an
   honest resting place.

## Disposition

⛔ **No fix proposed and none should be.** Nothing here is known to be ours; the
pack's code is not implicated by any evidence collected. **The rig was restored
by deleting the downloaded copy** (`PdxMods/pdx_156049_1`, removed 2026-08-20
after the process was killed) — the junction was untouched, so no enable was
spent. ⚠️ Re-subscribing on Paradox re-downloads it and re-enters the
configuration; there is no reason to, because the delivered-bytes check that the
subscription existed for is **complete and passed on both portals**
(`reports/RELEASE_PORTAL_PREP.md` §0.5(f)).
