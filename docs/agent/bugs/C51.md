### C51 — three UI strings can never be translated while their translations sit in the shipped language packs  `[tested-attended 2026-08-20: BOTH HALVES WATCHED IN GERMAN by the owner at link 4's sitting — the terraforming heading renders TERRAFORMING-GESAMTFORTSCHRITT and the rocket rollover Zurück zur Erde / Schicke die Rakete ohne Ressourcen direkt zurück zur Erde., log '2 of 2 strings'; English shows no visible change on either, which is the entry's own promise. ⛔ THE ROCKET HALF WAS A NO-OP AS FIRST BUILT and was repaired mid-sitting: the button is NOT a direct child of the panel (measured live, kids=5, all InfopanelSection) and is now found with XWindow:ResolveId. Evidence docs/archive/link4en_*, link4de_*; report reports/04_ATTENDED_SITTING.md. Suite 74/0/24/0 of 98. Prior art: fredware's *Restore Localized UI Text*]`

## The claim, and whose reading this is

`fredware`'s **SMR Community Fixes** #13 says the terraforming heading and the Universal
Rocket *Back to Earth* action have official translations the game does not use. Below is our
own derivation — at `ModTools\Src` by symbol, and then against the **shipped binary language
data**, which is a stronger surface than either of us had cited.

## Miss 1 — a heading with no translation id at all

`Lua/XDef/TerraformingOverall.generated.lua:49-58` builds the panel title as an `XText`
whose `Text` property is a **plain Lua string**:

```lua
			XText:new({
				…
				TextStyle = "GreenSubTitle",
				Text = "OVERALL TERRAFORMING PROGRESS",
				TextVAlign = "center",
			}, _XWindow1, context)
```

(mirrored in the editor source, `Data/XDef/TerraformingOverall.lua:51`.)

A plain string carries no id, so the localization system never sees it. Meanwhile the same
English text **is** an enrolled record — `T(914616772802, "OVERALL TERRAFORMING PROGRESS")`,
`Lua/LocalizationTexts.lua:246`.

## Miss 2 — a button using two ids no language pack knows

`Lua/XDef/customUniversalRocket.generated.lua:22-29`:

```lua
			InfopanelButton:new({
				RolloverText  = T(807999655245, --[[XDef customUniversalRocket RolloverText]]  "Send the rocket directly to Earth without any resources."),
				RolloverTitle = T(885571832096, --[[XDef customUniversalRocket RolloverTitle]] "Back to Earth"),
				Id = "idBackToEarth",
				…
```

Both ids are syntactically fine. Neither is enrolled. The identical English text ships under
two different, enrolled ids — `T(407456913268, "Back to Earth")` and
`T(316233855405, "Send the rocket directly to Earth without any resources.")`,
`LocalizationTexts.lua:357-358`.

## ⭐⭐ The measurement — shipped German data, read directly

The install ships nine language packs under `Local\`. `German.fpk` was extracted with **our
own** `tools/flpk_extract.py`; it contains exactly one file, `CurrentLanguage/Game.csv`
(43,110 rows, columns `ID,Text,Translation,…,Status,…,Location,Context,…`).

| id | used by | in German pack? | German text | Status |
|---|---|---|---|---|
| `914616772802` | *nothing* — orphan record | ✅ | **TERRAFORMING-GESAMTFORTSCHRITT** | OK |
| — | `TerraformingOverall.generated.lua:56` | **n/a — raw literal, no id** | — | — |
| `407456913268` | *nothing* — orphan record | ✅ | **Zurück zur Erde** | OK |
| `885571832096` | `customUniversalRocket.generated.lua:24` | ❌ **ABSENT** | — | — |
| `316233855405` | *nothing* — orphan record | ✅ | German sentence | OK |

⇒ **The German translation of all three strings shipped with the game, and the UI that
displays them cannot reach any of it.** Note the `Location` column on the enrolled rows
points at `Trunk\Mars/Lua/LocalizationTexts.lua(00246)` and `(00357)` — the export knows
exactly where those records came from, and it is not the UI that renders them.

⚠️ **One number above is a physical line count, not a record count** (noted 2026-08-20 so a
later leg does not mis-derive from it): `Game.csv` is 43,110 **lines** but **23,090 CSV
records** — quoted fields carry embedded newlines. Both readings are of the same file.

## ⭐⭐ RE-DERIVED 2026-08-20 — all nine packs, and the English case is not a gap

The build link re-ran the extraction rather than inheriting the row above (`recorded facts
are claims too`), and widened it from one pack to all nine:

| pack | `914616772802` | `407456913268` | `316233855405` | `885571832096` | `807999655245` |
|---|---|---|---|---|---|
| Brazilian, French, German, Polish, Russian, Schinese, Spanish, Turkish | ✅ translated | ✅ translated | ✅ translated | ❌ **absent** | ❌ **absent** |
| English | ✅ (see below) | ✅ | ✅ | ❌ **absent** | ❌ **absent** |

⭐ **And the English row is the part worth keeping.** In `English.fpk` those three records
carry an **empty `Translation` column** — as do **22,266 of the 23,090 rows**. That is not a
missing translation and it must not be read as one: `csv_load_fields` maps CSV column 2 →
`text` and column 3 → `translated_new` (`CommonLua/Core/localization.lua:920`), and
`ProcessLoadedTables` (`:938-960`) resolves **English** in the order
`{ translated_new, TEXT, translated }`. So every row in a pack lands in `TranslationTable`,
and for English it lands as the English source string itself.

⇒ **`TranslationTable[914616772802]` is populated in all nine languages.** Re-pointing the
UI at it is therefore loss-free in the strong sense: an English player sees exactly the words
they see today, and the other eight see their own. The claim did not need this to be true —
an unenrolled `T(id, text)` falls back to its embedded literal anyway — but it removes the
one way the repair could have gone wrong, and it was not on record.

## Two controls — why this is not "just how XDefs work"

**Control A — same file, same class of string.** Every other id in
`customUniversalRocket.generated.lua` is enrolled: `468405949295` *Select a destination for
this Rocket*, `495831114406` *Destination*, `481209999840` *Cancels the current destination…*,
`477383533670` *Cancel the Flight*, `233352161688` *Launch Rocket*, `151505399245` *Launch*,
`880609979454` *Launch Issue*. **7 of 7**, one of them carrying the literal source location
`.../customUniversalRocket.generated.lua(00015)` and the context `XDef customUniversalRocket
RolloverTitle`. Absence is therefore specific to the *Back to Earth* button, not systemic to
XDef-generated ids.

**Control B — raw literals are the exception, by two orders of magnitude.** Across every
`*.generated.lua` under `Lua/XDef/`: **9** occurrences of `Text = "…"` against **633** of
`Text = T(…)`.

## The player route — REAL

`IsLocalizationLanguageAvailable(language)` resolves to `"Local/" .. language .. ".fpk"` in a
non-developer build and `OptionsData.Options.Language` is built only from the packs that
exist (`CommonLua/Core/localization.lua:1209-1227`). This install carries nine:
Brazilian, English, French, German, Polish, Russian, Schinese, Spanish, Turkish.

**ROUTE SENTENCE (tagged separately from its citations, R3):** *therefore any player who
picks a non-English language in Options sees these three strings in English inside an
otherwise translated interface.* The citations are each verified and the German data is
read; the "therefore" is our inference and has not been watched on a screen by us.

⚠️ **Not observed by us.** Confirming it costs one language switch in Options and two
screenshots — the terraforming overview panel and a Universal Rocket's infopanel — with the
game's language set to anything but English.

| `HUDIndicatorSpeed.generated.lua` | `"SOL"` | n/a — a unit token |

Only the first can be repaired by pointing at an existing id. The other three English
sentences have **no record in the English export and none in the German pack**, so they would
need a mod-supplied `ModItemLocTable` per language — `EF-039` route 4, explicitly
post-release work, and a route that overrides the shared table for vanilla and every other
mod. fredware's spec reaches the same conclusion about *COLONY DATA* and does not attempt
it; it does not mention the two Options strings, which are ours.

## Why the repair shape here is loss-free — unlike C50

`C50`'s remedy would replace a shipped, translated string with a new literal and regress
eight languages under `EF-039`. **This one is the opposite case.** Nothing here is a text
edit: it is pointing a UI at the id whose translation already ships. Under `EF-039` a `T()`
on an enrolled id returns the light userdata and rendering reads `TranslationTable[id]` — so
routing the heading through `914616772802` and the button through
`407456913268`/`316233855405` yields the shipped German (French, Polish, …) text with **no
English literal anywhere in the path**. That is `EF-039`'s mechanism working for us.

## ⭐ What was built — `Code/Fix_LocalizedUIText.lua` (2026-08-20, close-out chain link 1)

Owner ruling 2026-08-20 (checklist 58): `C50` + `C51` ship **in** 1.0.0. One module, Register
id `LocalizedUIText`, 76th registered module / 77th `Code/*.lua` file.

**Technique — chain, never replace** (`FIX_POLICY` §1.4). Both targets are XDef-generated
`Init` methods declared on their own class: `TerraformingOverall:Init`
(`TerraformingOverall.generated.lua:18`) and `customUniversalRocket:Init`
(`customUniversalRocket.generated.lua:11`). The module captures whatever `Init` is installed
when it loads — **if another mod replaced one first, that version is the original and their
work stays in the chain** — calls it, then corrects the controls it built. Mod code loads
before class flattening (`_G.<Class>` is the classdef, `classes.lua:71`, swapped for the built
class at `:1085`), so this is a **classdef-time install and it propagates through
flattening**. That matters more than the brief assumed: ⭐ **`customUniversalRocket` has FIVE
subclasses** — Dragon, Lander, Refugee, Trade, Zeus (`Data\XDef\customUniversal*Rocket.lua`)
— **and none of them declares an `Init` of its own**, so all six rocket variants inherit the
repair from the one wrap.

**Handles.** The rocket button carries `Id = "idBackToEarth"`, so it is found by id, never
by text. ⛔ **CORRECTED 2026-08-20 at the sitting (recorded by link 5, which found this
sentence still standing):** it is NOT "a direct child of the window `Init` built", as this
paragraph originally said — the infopanel reparents the buttons (measured live: kids=5, all
`InfopanelSection`), and the direct-child scan built on that claim was a NO-OP from the day
it was written. The button is resolved with the engine's own `XWindow:ResolveId`; the
heading tag above and the module header carry the full measurement. ⛔ The terraforming heading has no
id at all — its only handle is the English literal it renders, and the module says so in its
own header. The match requires a **plain Lua string**: once the control holds a `T` value
(ours, a patch's, or another mod's) it is not a match. ⇒ the day a patch re-words it, gives it
an id, or fixes it outright, the module **stands down with a reason line in our log and
nothing on screen**, which is the safe direction (`FIX_POLICY` §2).

**Both sites verify the remedy and the defect before touching anything**, at panel-build time
rather than apply time, so a mid-session language change re-runs the checks: the replacement
id must be in the loaded `TranslationTable`, and the rocket site reads the id **currently on
the control** (`TGetID`, `localization.lua:48-61`) instead of assuming it. Apply-time
self-checks additionally require both classes, both `Init`s, `T`, `TGetID` and
`TranslationTable`, plus two content checks — all three replacements enrolled, and neither
broken id enrolled (i.e. *the game has not fixed this upstream*). Each pass runs under
`pcall` because it executes inside engine UI construction; a cosmetic repair must never be
able to take a panel down.

**Save safety — layer 3, nothing of ours enters a save.** The module writes nothing: no
persisted class, no `GameVar`, no game-time thread, no `OnMsg.LoadGame`, no state at all. Its
wrapper bodies contain no `Sleep`/`WaitMsg`, so no frame can sit below a blocking call, and
the only things holding its functions are a class table and an X window — `XWindow.__persist
= false` (`XWindow.lua:4`). ⇒ free to add to any existing save and free to remove from one.

**Registered by hand** in `items.lua` and `metadata.lua`'s `code` list, same name, same
position (`H-10`); `upload_preflight` reads **0 FAIL** with the two lists agreeing at 77
entries. TestKit probe `LocalizedUIText` added as wave 12 (97 probes).

⛔⛔ **UNOBSERVED, AND THE PROBE DOES NOT CHANGE THAT.** The probe re-runs the localization
derivation live and can fail honestly — it goes red if the replacement ids stop resolving, if
either broken id starts resolving, if a wrapper is lost from an `Init`, or if the wrapper ran
and found neither handle — and on a **non-English** run it asserts the repaired readings
differ from their English literals. ⛔ But it reads the translation system, **never a
screen**, and on an English run it cannot tell a working fix from a broken one at all. No leg
of this project has ever watched a shipped-id string render in a non-English language
(`EF-039`'s closing note). The close-out chain's link 4 is the first eyes.
