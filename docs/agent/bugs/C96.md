### C96 — Rover requirement matching checks exact class, not kind-of, so a rover's own subclass can never satisfy a request for it (P2) `[cand 2026-09-14: mechanism SOURCE-VERIFIED on both trees; NOT reproduced]`

⛔ **The mechanism is real and verified in source on both trees; what is NOT
settled is reproduction in play.** Do not describe this as confirmed-live
until a sitting watches it.

#### The report (INHERITED, not verified)

In-game report + forum post #16, owner-provided 2026-09-14, poster **Harp**,
verbatim:

> *"Reported through the game as well, just listing here to check if this is
> just a quirk of my install (shouldn't be, no mods, nothing funky at all):
> When sending a rocket to a planetary anomaly requiring an RC Commander, it
> ignores the RC Seeker and will not load it. I'd mind less if the anomalies
> weren't being snatched from under my nose by the other colonies! I have
> everything I need to get there, but it won't load the Seeker, which is
> supposed to be a straight upgrade to and replacement for the Commander..."*

No log, no save, no mod list beyond the reporter's own "no mods" claim.

#### Our exposure: adjacent modules, different class entirely

**MEASURED:** `grep -rliE "ListAvailableRovers|GatherAvailableRovers|CargoTransporter" Code/`
hits four modules — `Fix_ArrivalDeaths.lua`, `Fix_LanderEmptyLaunch.lua`,
`Fix_RocketDroneChurn.lua`, `Fix_TradeRocketFuelRefresh.lua`. Every hit is
`CargoTransporterNew` (trade/supply rocket cargo requests) or a passing
mention in a comment — none wraps `CargoTransporter:ListAvailableRovers`,
`:GatherAvailableRovers`, or `RocketExpeditionBase`'s override, the classes an
anomaly-mission rocket actually uses. `CargoTransporterNew` and
`CargoTransporter` are separate classes in separate files
(`Lua/CargoTransporterNew.lua` vs `Lua/Buildings/CargoTransporter.lua`). This
mechanism is 100% vanilla.

#### The mechanism (SOURCE, game 1.1.0.403908, identical on 1.0.7.396349)

An anomaly rolls a rover requirement as one specific **leaf class id**, drawn
from the resupply-rover list:

```lua
-- PlanetaryAnomaly.lua:248-251
local list = GetAvailableResupplyRovers()
self.requirements.rover_type = table.rand(list, GetInteractionSeed("PlanetaryAnomaly.InitRequirements"))
self.requirement_type = "rover"
```

`GetAvailableResupplyRovers` (`:255-265`) walks the `Cargo`/`Rovers` preset
group, whose ids are the actual unit classes — `Data/Cargo.lua` lists
`RCRover`, `RCSensor`, `RCSolar`, `RCTransport`, `RCConstructor`,
`RCHarvester`, `RCTerraformer`, `RCDriller`, `RCSafari`, `ExplorerRover`. When
the roll picks `"RCRover"` ("RC Commander"), that string becomes
`expedition.rover_type`, then the manifest key:

```lua
-- RocketExpedition.lua:520-521
if expedition.rover_type then
    manifest.rovers[expedition.rover_type] = 1
end
```

which is consumed by the SHARED base-class matcher:

```lua
-- CargoTransporter.lua:418-432 (1.0.7.396349:421-435, byte-identical)
function CargoTransporter:ListAvailableRovers(class, quick_load, no_drones)
    local filter = function(unit)
        ...
        return unit.class == class and unit:CanBeControlled() and not unit.holder and (quick_load or unit:IsIdle())
    end
    local rovers_list = self.city.labels[class] or empty_table
    local available_list = table.ifilter(rovers_list, filter)
    return available_list
end
```

`unit.class == class` is a **strict equality on the unit's own leaf class
name** — not a `IsKindOf` polymorphism check. `RCSensor` ("RC Seeker") is a
genuine subclass of `RCRover` ("RC Commander") — `Lua/Units/RCSensor.lua:4`,
`__parents = { "RCRover", "ComponentAttach" }`, unchanged between 1.0.7 and
1.1.0 — so a Seeker's `unit.class` is `"RCSensor"`, never `"RCRover"`, and it
is filtered out of every `class == "RCRover"` request no matter how many
Seekers the player owns.

**The tell that this is an oversight, not a deliberate distinction:** the
very same file uses correct `IsKindOf` polymorphism a few lines below, for
adjacent purposes on the identical rover objects — `IsKindOf(g_Classes[item.class],
"BaseRover")` and `IsKindOf(rover, "RCRover")` in `CargoTransporter:SpawnRovers`
(~`:455`, `:462`). The module already knows how to ask "is this rover a kind
of RCRover" correctly; the availability filter just doesn't ask that
question.

#### Blast radius: this is a class-hierarchy bug, not a Seeker-specific one

The same exact-match filter breaks **every** RC subclass relationship in the
game, confirmed by class definition (identical on both trees):

| requirement (base class) | subclass that should qualify, and doesn't | relationship |
|---|---|---|
| `RCRover` ("RC Commander") | `RCSensor` ("RC Seeker") | `RCSensor.lua:4` |
| `RCRover` ("RC Commander") | `RCSolar` | `RCSolar.lua:3`, `__parents = {"RCRover", ...}` |
| `RCTransport` | `RCHarvester` | `RCHarvester.lua:3`, `__parents = {"RCTransport", ...}` |
| `RCTransport` | `RCConstructorBase` (→ `RCConstructor`, `RCTerraformer`) | `RCConstructorBase.lua`, `__parents = {"RCTransport"}` |
| `RCConstructorBase` | `RCTerraformer` | `RCTerraformer.lua`, `__parents = {"RCConstructorBase", ...}` |

Only the Commander/Seeker pair has a field report; the rest are read from
source, not independently observed failing.

#### What is NOT verified

Whether this reproduces on our own rig · whether the reporter's colony
actually had zero RC Commanders and only Seekers available (the report reads
that way but doesn't say so explicitly) · whether `city.labels[class]`
(keyed by the exact string `class`) actually contains subclass instances at
all before the filter runs — if the engine's native per-class label
registration already excludes subclasses from a base-class bucket, the filter
line would be redundant rather than the sole cause, though the internal
`IsKindOf` calls a few lines away strongly suggest the objects ARE reachable
and the filter is what discards them · whether the identical bug reaches
non-expedition rover requests (trade/supply auto-payload rover slots, if any
exist) through the same shared `CargoTransporter` base — not traced, this
entry only followed the expedition path · reporter's mod list beyond their
own "no mods" claim.

#### Not opened

Whether `RCDriller`/`RCSafari`/`ExplorerRover` sit in any subclass
relationship with another cargo-listed rover — not checked, no obvious
`__parents` overlap seen in the earlier grep · whether a `Dome`-style
auto-widening exists anywhere else in the codebase that this filter could
reuse (i.e., what the actual fix shape should look like) — not designed,
this entry only establishes the defect.
