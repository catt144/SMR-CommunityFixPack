### C97 — The 1.1.0 tutorial rewrite: four run-stranding stalls and five orphaned flag contracts (P3, tutorial-scoped) `[cand 2026-09-15: SOURCE-VERIFIED; NOT reproduced; no normal-play reach]`

⛔ **SCOPE FIRST, because it bounds everything below: nothing here can reach a normal
colony.** Every finding sits behind a `g_Tutorial` gate. `g_Tutorial` is a plain global
(`Lua/Tutorial.lua:33-35`), **not** a `GameVar` — it is never written to a savegame. It is
set only by `StartTutorial` (`:60`, `:75`) and cleared on leaving the tutorial map
(`OnMsg.DoneMap`, `:165-172`). Completing a tutorial runs `TutorialCleanup` and then returns
to the main menu or loads a different save (`:118-133`) — a tutorial never continues on into
a playable colony. With `g_Tutorial` false every gate below takes its permissive branch.
**Do not let this entry be read as a normal-play defect.**

⛔ **NOT REPRODUCED.** Everything here is source-derived. No leg ran the game.

⛔⛔ **THIS ENTRY HAS TEN KNOWN ERRORS AND THEY ARE NOT YET CORRECTED.** An Opus re-check on
2026-09-15 found them; the findings are in [`reports/C97_RECHECK.md`](../reports/C97_RECHECK.md) and
**applying them is owed work**. ⛔ **Do not write a fix or a control recipe from this entry until you
have read that report** — four of the errors are the kind that propagate. In particular:
the scope proof below argues from the wrong variable (the conclusion holds, the argument does not);
**Finding 4's code fence is the wrong function with an inverted truth condition**; Finding 3 lists one
read with the wrong polarity; Finding 1's "sibling objective" citation points at unrelated lines; the
"NOT OURS" module list is incomplete (three more modules sit on Finding 1's rocket path — none
defective, but uncleared); and "the run must be abandoned" is refuted by a one-click Restart Map
recovery. The report also carries three extra findings and closes Claim E's last escape hatch.

#### Why this was audited at all

The tutorial was rewritten wholesale for 1.1.0: the 1.0.7 five-file set (`Tutorial1.lua` …
`Tutorial5.lua`, ~107 KB) became one `Lua/TutorialsNew.lua` (86 KB, 2,689 lines) plus a
reduced `Tutorial.lua` and a new `TutorialUI.lua`. This project had never audited it — the
only prior entry is [[C72]], a narrow performance note on its polling loops. New, unvetted
code plus a run of player reports is why the pass was ordered.

#### Method, and what it cost the audit's own credibility to establish

Five subagent legs, each reading the whole file plus the step graph, each hunting a
different defect class (softlocks · resources/safety rails · nil-safety · step sequencing ·
1.0.7→1.1.0 capability diff). **The legs were deliberately blinded** — none was shown the
player reports, to keep them off a symptom. The orchestrator then re-derived every
load-bearing citation independently rather than inheriting it.

That discipline paid twice, and both are recorded because they bound how much to trust the
rest:

1. **Three orchestrator seed hypotheses were REFUTED by the legs** — `rocket.cargo.MachineParts`
   nil at `TutorialsNew.lua:1112` (unreachable: `CmdUnload` backfills every transportable
   resource into `self.cargo`, `CargoTransporterNew.lua:1450-1452`, and cargo keys are never
   deleted on this path), `Notifications[1].id` at `:1011` (the fixed tutorial savegame carries
   the entry, and `OnStart` runs under `sprocall` besides), and `HasOxygenConnectedBuilding`'s
   unguarded `ipairs(MainCity.labels[...])` at `:240` (our own **`EF-005`** — engine Lua
   tolerates `ipairs(nil)`/`#nil`). Our own facts index killed two of our own false positives.
2. **Two legs contradicted each other on the severity-determining point**, resolved at source:
   `ScriptableTutorialTask:Evaluate` calls `self.check_script(self)` (`TutorialsNew.lua:1651`),
   which routes through `ScriptProgram:__call` → `procall` (`CommonLua/Scripting.lua:413`).
   **A throw inside a check script is contained.** The "dead tick thread / bricked tutorial"
   reading is WRONG. What is true and load-bearing: `task:Evaluate(UIPlayer)` is called **bare**
   in the tick loop (`CommonLua/Libs/Tutorial/Tutorials.lua:218`), so anything throwing in an
   `Evaluate` body *outside* the check script — `expression`-typed callbacks, `HexAxialDistance`
   — would propagate and kill the tick thread, recovery branch (`:232-242`) included.

#### Our exposure: NOT OURS, both touching modules proven neutral in source

Two pack modules reference tutorial code. Neither changes tutorial behaviour:

- **`Fix_PayloadTemplateRefill`** replaces `resolve_loc_cargo_template` and reproduces the
  shipped tutorial branch verbatim; our F70 gate is placed **after** the
  `if g_Tutorial then … return end` block, so while a tutorial runs our gate is never
  reached (our `:207-233` against shipped `Lua/CargoRequestNew.lua:169-192`). The module's own
  header already warns the tutorial path is untested in play — that warning stands, but the
  source argument is unconditional.
- **`Fix_ScanDowngrade`** pre-wraps `MapSector:Scan` to block downgrades. Every tutorial scan
  is an upgrade on a fresh map: `GetSector("F3"):Scan("scanned")` (`TutorialsNew.lua:863`),
  `GetSector("F4"):Scan("scanned")` (`Data/TutorialStep.lua:983`), and the only status check in
  tutorial code is `GetSector("F4").status ~= "unexplored"` (`:956`), a not-equals. ⚠️ Residual
  named rather than dropped: were a sector already deep-scanned, our no-op would also skip the
  deposit-reveal side effect the tutorial deliberately forces by stubbing `IsDepositObstructed`
  around the call (`:861-864`) — unreachable on a fresh tutorial start.

### Finding 1 — Basics `Step031_GameSpeed` can hang permanently on a lost edge

`Data/TutorialStep.lua:157-207` (the step) · `:196-206` (the task) · `TutorialsNew.lua:625-660`
· `CommonLua/Libs/Tutorial/Tasks.lua:12-17` · `Lua/UniversalRocket.lua:355`, `:590`

The step's second objective, *"Wait for the `<em>`Rocket`</em>` to land"*, is a
`ScriptableTutorialTask` carrying **only** a `RocketUnloaded` reaction — **no `check_script`,
no fallback** (`:196-206`; contrast its sibling objective in the same step, which does carry
one at `:216-229`). `ScriptableTutorialTask` inherits `MessageReactionTutorialTask`
(`TutorialsNew.lua:1589-1590`), whose `Activate` registers reactions **when the step
activates** (`Tasks.lua:12-17`) — anything that fired earlier is lost.

The preceding step completes on `RocketLandAttempt`, which fires the moment the player
**designates** the landing site, before descent begins (`UniversalRocket.lua:348-356`, inside
the `from_ui` block, `Msg` at `:355`). That step then **waits for the player to press
Continue**, because `AppendClass.TutorialStep` gives `ManuallyComplete` default `true`
(`TutorialsNew.lua:634-638`) and `TutorialState:TryComplete` returns early without it
(`:654-657`). Everything the rocket does in that window — descent, `CmdUnload`, and
`Msg("RocketUnloaded", self)` at `UniversalRocket.lua:590` — happens with **no listener
registered**. Step031 then activates and waits forever for a message that already fired.

**No escape exists.** Continue is gated on `CanBeManuallyCompleted()`, which requires every
objective complete (`TutorialsNew.lua:625-632`), and the tick thread's recovery branch only
runs when *no* state is active (`Tutorials.lua:232-242`).

**Player sees:** the rocket sitting landed and unloaded, the objective unticked, Continue dead.
The run must be abandoned.

⭐ **Control:** on Basics, designate the landing site and let the rocket fully land and unload
**before** pressing Continue. If the objective still ticks, this is wrong — as it would be if
anything re-sends `RocketUnloaded`; no re-send was found.
⛔ **Reachability is a timing race and is NOT bounded by source.** How often a player presses
Continue after unload completes is unmeasured. Do not state a frequency.

### Finding 2 — two objectives are completable only by an arrow that can become unspawnable

`Data/TutorialStep.lua:1239-1246` (Basics `Step11_WaterExtractor` task 3) ·
`:2567-2575` (Colonists `Step01_Dome` task 3) · `TutorialsNew.lua:77-85`, `:768`, `:852`

Both objectives carry **no `check_script` and no reaction**. Their sole completion path is
`complete_task_after = 3000` inside the UI-arrow monitor (`TutorialsNew.lua:77-85`), which
fires only once the arrow is actually **visible** (`self:GetVisible() and self:GetTransparency() == 0`).
The arrow's target is resolved by digging the Infopanel for a `sectionConstructionSite`
(`Data/TutorialStep.lua:1242`). If no construction site can be selected — the building
finished, or the player cancelled it (`g_Tutorial.AllowCancelConstruction` is set by both
setups, `TutorialsNew.lua:768`, `:852`) and cannot re-place it — the arrow never becomes
visible and the objective can never tick.

⚠️ **Companion masking bug, same steps:** task 2 tests
`SelectedObj == (labels.X_Construction and labels.X_Construction[1])` (`:1219`, `:2557`). Once
that label is empty the right-hand side is nil, so the test is `SelectedObj == nil` — **true
whenever nothing is selected**. Task 2 self-ticks, so the player arrives at the stalled task 3
with no indication of what went wrong.

**Player sees:** *"Observe the lack of resources"* (Basics) stays unticked forever; Continue
never lights.

⭐ **Control:** let the Water Extractor finish building before ever selecting its construction
site. If the step still advances, this is wrong.

### Finding 3 — `g_Tutorial.SwitchToAutomode` is set and never cleared

Set: `Data/TutorialStep.lua:2317` (Asteroids Step09), `:2445` (Step10) — **both `= true`**.
Read: `Data/XDef/RocketAutoPayload.lua:96`, `Data/XDef/RocketManualPayload.lua:197`, `:228`,
`:250` (plus their `Lua/XDef/*.generated.lua` copies).

A tree-wide grep returns those writes and those reads and **no clear anywhere**, including
`TutorialCleanup` (`Lua/Tutorial.lua:174-199`). The reads gate the payload dialogs'
**CANCEL / Escape** action (`RocketAutoPayload.lua:96`) and the "SWITCH TO PASSENGERS"
(`:228`) and "SWITCH TO AUTOMATED MODE" (`:250`) buttons. From Asteroids Step09 onward the
payload screen loses its Escape exit for the remainder of that tutorial.

⚠️ Related, same family, lower confidence: `ManualRocketPayloadOnly` / `AutoRocketPayloadOnly`
are set in `RocketSetPayloadRequest:Activate` (`TutorialsNew.lua:2576`) and cleared only on
that task's own successful `Evaluate` (`:2677`); the class defines no `Deactivate`. An
abandoned step leaves them set.

⭐ **Control:** during Asteroids Step09/10, open the payload dialog with a non-matching payload
and press Escape. If it closes, some exit outside the action bar exists and this is wrong.

### Finding 4 — a half-guard stalls Colonists Step 15

`TutorialsNew.lua:2072-2076` (`CheckWorkshiftsPreciousMetalsExtractor`) and `:2078-2082`
(`CheckWorkshiftsDiner`), used as `check_script`s at `Data/TutorialStep.lua:3290`, `:3315`

```lua
local extractor = MainCity.labels.Spacebar_Small
extractor = extractor and extractor[1]
return extractor.closed_shifts and extractor.closed_shifts[2] and extractor.closed_shifts[3]
```

The `and extractor[1]` guards the **label**, then the result — which is nil whenever the label
is missing or empty — is dereferenced unguarded on the next line. `RemoveFromLabel` empties a
bucket but **never deletes it** (`CommonLua/LabelContainer.lua:68-93`), so a salvaged building
leaves an empty table, `[1]` is nil, and `.closed_shifts` throws. Salvage is permitted here:
`g_Tutorial.DisableDemolish` is set **only** by `TutorialSetup_1` (`TutorialsNew.lua:850`;
sole consumer `Lua/Buildings/Building.lua:912`), and Step 15 is in `TutorialColonists`.

**Severity, corrected from the audit's first reading:** the throw is **contained** by `procall`
(`:1651` → `Scripting.lua:413`), so the cost is that this objective can never complete — a
permanently stalled step, **not** a dead tick thread.

⚠️ **The author guards this exact construct correctly at `:1214` and `:2552`** — an internal
inconsistency, not a house style.

⭐ **Control:** salvage the Small Spacebar during Colonists Step 15 and see whether the step can
still advance after rebuilding. If it does, the label is nil'd rather than left empty, or
demolish is blocked there, and this is wrong.

### Finding 5 — the rewrite orphaned five tutorial-flag contracts whose consumers still ship

One root cause: the tutorial ids changed (1.0.7 `Tutorial1`…`Tutorial5`,
`Data/TutorialPreset.lua:6-50` → 1.1.0 `01TutorialBasics`, `TutorialColonists`,
`TutorialTrains`, `TutorialAsteroids`, `Data/Tutorial.lua:16,41,64,88`) and the per-tutorial
setup files were deleted, but the **consumer** side survived untouched in normal-play files —
and 1.1.0's own `Lua/Tutorial.lua` still documents the flags as supported knobs.

| flag | live consumer (1.1.0) | deleted setter (1.0.7) | effect in every 1.1.0 tutorial |
|---|---|---|---|
| `Id == "Tutorial2"` + `DisableReassignButtons` | `Lua/Units/Drone.lua:1989`, `:2018` | `Tutorial2.lua:189` set / `:227` clear | **Drone Reassign permanently greyed out** |
| `EnableOrbitalProbes` | `Lua/OrbitalProbe.lua:90` (doc `Tutorial.lua:26`) | `Tutorial2.lua:361` | **orbital probes unusable** |
| `RoverGatherResourceWorkTime` | `Lua/Buildings/SurfaceDeposit.lua:246` (doc `Tutorial.lua:29`) | `Tutorial3.lua:4` (half time) | rover gathering runs ~2× the designed length |
| `SectorScanBase` | `Lua/Exploration.lua:833` | `Tutorial2.lua:86` (×3) | scans at 1× (offset in Basics only, `FastScan`, `TutorialsNew.lua:859`) |
| `EnableResearchWarning` | `Lua/Research.lua:275` (doc `Tutorial.lua:11`) | `Tutorial2.lua:446`, `Tutorial5.lua:472` | "no research queued" never fires |

The drone row is the sharpest: the gate expression is **byte-identical** to 1.0.7's
(`Drone.lua:1783`/`:1813`), where it genuinely worked; `"Tutorial2"` and
`DisableReassignButtons` now appear **nowhere else in the entire 1.1.0 tree**. The button is
disabled for the whole of every tutorial while the game tells the player *"This feature has
been disabled during the tutorials"* (`Drone.lua:1998-1999`) — i.e. it reads as deliberate.

⭐ **Control:** any write anywhere in the 1.1.0 tree to one of these five names — or a renamed
replacement reaching the same consumer line — refutes that row. ⚠️ These absence claims rest on
name greps; a dynamic assignment through a computed key would evade them.

### Latent / not established — recorded so they are not re-derived

- **The MachineParts rail double-counts.** `ResourceSafetyRailsUpdate` adds `rocket.cargo.MachineParts`
  to `GetCityResourceOverview():GetAvailable()` (`TutorialsNew.lua:1106-1111`), but `GetAvailable`
  already includes landed rockets (`Lua/ResourceOverview.lua:142-155` → `UniversalRocket.lua:2522-2535`).
  Effective floor is ~2.5 units, not the 5 the code reads as. No stranding on its own.
- **Metals has no rail, zero tutorial supply, and unbounded demand.** Rails are armed only in
  `TutorialSetup_1` (`:866-872`) and protect MachineParts only — the one resource the tutorial
  already over-supplies. Metals costs include 1 per cable hex (`Lua/ElectricityGrid.lua:381`)
  and 1 per pipe hex (`Lua/LifeSupportGrid.lua:549`), with `MetalsExtractor` disabled in the
  whitelist (`:790`). ⛔ **INFERRED — the map's deposit inventory was never sampled.**
  Control: sum the surface Metals deposits on the tutorial map against ~16 plus the longest
  plausible cable/pipe routing.
- **`CommandUnitToMarkerTask:Evaluate` passes an unvalidated marker to `HexAxialDistance`**
  (`TutorialsNew.lua:1774-1794`: guarded at `:1782`, raw at `:1792`). This one sits **outside**
  the procall, so if reachable it kills the tick thread outright. Reach not established (only
  user is Trains Step01_1, `Data/TutorialStep.lua:3525-3535`).
- **`SpawnWorldArrow` dereferences a documented nil return** (`:134-142` against
  `TutorialUI.lua:154-169`). No reachable off-map target found; hardening candidate only.

### Who is actually affected — not only new players

`PromptTutorialStart` (`TutorialsNew.lua:2279-2309`) can offer a tutorial to an **established
player mid-colony** (`ShowDomesTutorialPrompt` → `TutorialColonists`, `:2238`). On accept the
game saves their colony as *"Before tutorial - `<name>`"* (`:2308-2309`) and the return trip
`LoadGame(g_TutorialReturnToSavegame)` runs **only on the completion path**
(`CommonLua/Libs/Tutorial/ClassDefs/ClassDef-Tutorials.generated.lua:95-98`). Two of the four
stalls above live in `TutorialColonists`. A player who hits one must quit to the menu and find
that save by hand. ⛔ No data loss — the save exists.

### What is NOT verified

Nothing was run in the game · the Step031 race's real-world frequency is unbounded by source ·
the Metals exhaustion side needs a map deposit sample · `HexAxialDistance`'s behaviour on a
boolean argument is assumed, not proven (it is a C export; `EF-005`'s tolerances cover
iteration and `#`, not this) · no field report was used to derive any of it, by design, so
none of these findings is matched to a reported symptom.

### Not opened

Whether the three advanced tutorials (Colonists/Trains/Asteroids) carry their own step-graph
stalls of the Finding 1 shape — only Basics' step graph was walked edge-by-edge · the
`Tutorial_Politics_*` popup set with no preset and no caller (`PopupNotificationPreset-NewTutorial.lua:519-589`;
harmless, `PromptTutorialStart:2288-2292` returns early) · whether the coverage gap left by the
rewrite (no counterpart for the old exploration/scanning/research or maintenance tutorials;
maintenance actively suppressed in all four via `NoMaintenance`) has any defect consequence —
treated here as design scope, not a bug.

### Engine facts worth promoting to `agent/facts/` if this entry is accepted

1. **The tutorial containment boundary.** `check_script` / `on_activate` / `get_*_script` /
   `OnStart` / `OnComplete` run through `procall`/`sprocall` (`Scripting.lua:413`, `:420`) and
   are contained; `task:Evaluate()` itself is called bare from the tick loop
   (`Tutorials.lua:218`) and `expression`-typed callbacks inside it are not contained. Nothing
   restarts that thread.
2. **Label buckets persist empty.** `RemoveFromLabel` removes the entry but never deletes the
   bucket (`CommonLua/LabelContainer.lua:68-93`); `labels[X]` is nil before the first member
   and an empty table forever after the last one leaves. Only `"Dome"` is pre-created
   (`Lua/City.lua:56`).
3. **`g_Tutorial` lifetime** — the scope proof at the head of this entry.
