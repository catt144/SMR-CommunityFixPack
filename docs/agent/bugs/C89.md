#### Is it ours? NO (SOURCE + grep, 2026-09-12)

#### The mechanism as shipped (SOURCE, game 1.1.0.403908; identical like on 1.0.7)

- **The like.** `Data/FactionDef/ProsperityForMars.lua:216-232` — `FactionLikeDomes` `ProsperityUnemployment`,
  Value −300 (min −3000), Explanation "Domes with more than 10% Unemployment", filter
  `#obj.labels.Unemployed * 100 >= 10 * #obj.labels.Colonist` **per dome** (so it is "10 % or more", and one idle
  colonist in a dome of ten is enough). 1.0.7: the same expression at `:232`.
- **The evaluator.** `Lua/Factions/FactionDef.lua:842-856` — walks every `Dome` on the map type; a dome with **no
  colonists returns 0** (`:855`), and only **working** domes count (`:862`). ⇒ an empty or switched-off dome cannot
  trigger it (the first hypothesis, refuted here).
- **Who is "Unemployed".** `Lua/Units/Colonist.lua:1681-1697` `UpdateEmploymentLabels`: no `workplace` **and**
  `CanWork()`; `Colonist:CanWork` (same file) excludes children, tourists, seniors (unless allowed), dying, leaving,
  **disappeared**, and the Earthsick/StressedOut/UnableToWork/low-health cases. The dome label and the city label are
  written together, so they agree whenever both are current.
- **Expedition crews do NOT count** (second hypothesis, refuted): `Lua/Units/Unit.lua:1223-1225` sets `disappeared`
  **before** `OnDisappear`; `Colonist:OnDisappear` (`Colonist.lua:4992-4997`) then calls `SetWorkplace(false)` — with
  `disappeared` already true, `CanWork()` is false and the colonist lands in **Employed**, not Unemployed — and
  `SetDome(false)` removes them from the dome's labels entirely. `ResourceOverview:GetUnemployedColonists`'s
  `Disappeared` filter (`Lua/ResourceOverview.lua:722-728`) is therefore defensive, not load-bearing.
- **What the player's two numbers actually are.**
  - The **top bar** "Unemployed" = `Infobar.lua:799-802` → `ResourceOverview.lua:722-728`: the **live** city label.
  - The **faction panel** and the "dislikes" notification = a **stored hourly snapshot**: `Lua/Factions/Factions.lua:716-724`
    (`OnMsg.NewHour` → `RecalcFactionsApproval`), which stores `likes_data` (`:665-688`) and fires
    `AddFactionLikeDislikeNotification` for any like id that was not in the previous hour's list (`:672-678`);
    the panel reads that stored list back (`:1167-1170`). "Angry" is the approval-level word
    (`FactionApprovalLevels`: NOT CONTENT below 0, UNHAPPY below −500).

#### Candidate cause (INFERRED, not observed)

At some top-of-hour, some working dome had ≥10 % of its colonists idle and able to work — a shift change, a
building switched off or destroyed, new arrivals or returning expedition members between jobs (`OnAppear` puts
them back with `workplace` false until `UpdateWorkplace` runs), or simply one idle colonist in a small dome. The
hour's snapshot recorded the like, the notification fired ("Prosperity for Mars dislikes: high unemployment"),
and the panel shows that line **until the next hour** while the top bar already reads 0. That is a sampling
weakness the game has by design (it samples once an hour and announces new dislikes), not a wrong expression —
so, as it stands, **file and watch**; a fix would be a design change (debounce or re-evaluate live), which is
`FIX_POLICY` §4's call and out of scope without a reproduction.

⚠️ The alternative — a stale dome `Unemployed` label that the city label does not share — was **not exhausted**:
`SetDome` (`Colonist.lua:412-478`) and death (`:340-352`) look symmetric, but no runtime check was made.

#### 2026-09-12, later — owner pushback: "this is oversight territory". Tested, and it holds (SOURCE, both trees)

The owner's claim was that no other faction has a dislike this easy to trip, and that on a large colony —
colonists shuffling, children coming of age, arrivals from Earth — such a faction could never stay happy. Both
halves were tested against the shipped presets rather than argued.

**1 · Five factions carry the identical per-dome test; only one guards it.** Every negative like in all
`Data/FactionDef/*.lua` was enumerated (1.1.0.403908):

| faction | like | value (per dome, floor) | filter |
|---|---|---|---|
| Justice Movement | `JusticeUnemployment` (`JusticeMovement.lua:104`) | −300 / −3000 | **`#Colonist >= 10 and`** `#Unemployed*100 >= 10*#Colonist` |
| Prosperity for Mars | `ProsperityUnemployment` (`ProsperityForMars.lua:225`) | −300 / −3000 | `#Unemployed*100 >= 10*#Colonist` |
| Mars Democratic Party | `UtopiaUnemployment` (`MarsDemocraticParty.lua:88`) | −300 / −3000 | same, unguarded |
| Workers' Party | `CollectiveUnemployment` (`WorkersParty.lua:114`) | −900 / −3000 | same, unguarded |
| New Sol | `NewSolUnemployment` (`NewSol.lua:47`) | −1500 / −3000 | same, unguarded |

The same asymmetry holds for the **Homeless** twin: Justice guards it (`:129`), the other three do not
(`MarsDemocraticParty.lua:107`, `WorkersParty.lua:133`, `NewSol.lua:66`). So the developers' own presets contain
the fix — a "dome has at least ten colonists" gate — in exactly one faction out of five. Without it a dome of
three with one idle colonist is "more than 10 % unemployment", and a dome of nine needs one. All five expressions
are byte-identical on 1.0.7 (Justice's guard at `JusticeMovement.lua:102` there), so this is not a 1.1.0 regression.
Every other per-dome dislike in the game keys on something structural (a missing building, a birth policy, a
comfort average, a shortage); the unemployment/homeless pair are the only ones keyed on a count that churns.

**2 · Polling — every like of every faction is the same hourly snapshot** (`Lua/Factions/Factions.lua`):
- `OnMsg.NewHour` (`:716-724`) → `RecalcFactionsApproval` re-evaluates the **whole** like list of every seated
  faction and stores it (`:665-688`); the panel reads the stored list (`:1167-1170`). A blip is held for one hour.
- A dislike **absent the previous hour** fires `AddFactionLikeDislikeNotification` (`:672-678`) — a like that
  flickers on and off notifies **every time it comes back**. That is the "becomes angry" the reporter sees.
- Hour 0 is the daily step (`FactionsUpdate`, `:693-699`): approval recalculated, then `EvalTension`
  (`FactionDef.lua:223-247`) — tension **rises** if that hour's approval is below `TensionApprovalThreshold` and
  falls only on days it is above. A midnight blip therefore costs a day of tension, and tension is what turns
  UNHAPPY into AT BREAKING POINT (`Factions.lua`, `GetFactionApprovalLevel`) and feeds the political crisis. Not a
  perpetual lock, but a ratchet that only releases on clean midnights.

**3 · The large-colony half is true, and the reason is a number:** a colonist who loses a job (building switched
off or destroyed, shift closed, kicked, back from an expedition) only looks for another at their own **heavy
update**, and that interval is `Clamp(#Colonist / 300, 0, 12) * HourDuration` (`Lua/City.lua:118`; 1.0.7 `:119`;
consumed at `Units/Colonist.lua:2338-2343`). 300 colonists → one hour; 1,500 → five hours; 3,600 and up →
**twelve hours** between a colonist's own job checks. (Arrivals and new adults are placed immediately via
`SetDome` → `UpdateWorkplace`, `Colonist.lua:448`; freed slots pull the unemployed in via
`Workplace:CheckWorkForUnemployed`, `Workplace.lua:917` — so the churn is the *lost-job* case, not arrivals.)
The bigger the colony, the longer each idle stretch, the more hourly samples land inside one, and the more domes
there are for the −300-per-dome to stack across (floor −3000 = ten domes).

**Classification.** A design oversight with the developers' own correction sitting in one of five presets: a
dev-report candidate (they are reading our list), and a possible **judgment-call** fix on our side — a DataPatch
adding Justice's `#obj.labels.Colonist >= 10` gate to the four unguarded Unemployment filters (and the three
Homeless ones), i.e. the game's own rule applied consistently. Anything broader (debouncing the hourly sample,
re-evaluating live) is a design change and stays with the developers. Owner decision: checklist 157.

## 2026-09-12 — BUILT: `Code/Fix_FactionDomeSizeGate.lua` ⚖️ A JUDGMENT CALL (owner ruling, checklist 157 (c))

Built from `prompts/C85_C88_BUILD.md` (now consumed), scope **unemployment + homeless** per the owner's
override slot. ⚖️ **This is not a repair of a code error and no surface may say the game was wrong** — it
applies one faction's own rule to four others, the way F40 (Biorobots) and F73 (asteroid vacuum) are carried.

**Shape.** A `SMRFixPack.DataPatch` (`changed_class = "FactionDef"`) that **wraps** each of the seven unguarded
likes' `DomeFilter.eval`, keeping the shipped expression in a closure:
`like.DomeFilter.eval = function(obj) return #obj.labels.Colonist >= threshold and orig(obj) end`.
The shipped expression is never rewritten and Justice is never touched.

**Why a live field replacement works here** (S2, confirmed on the shipped body): `FactionLikeDomes:CountDome`
reads `self.DomeFilter and self.DomeFilter.eval` **at call time** (`Lua/Factions/FactionDef.lua:857`), so
replacing the field on the live like object takes effect at the next hourly recalc. Nothing captured the old
reference — unlike C88's message reactions.

**The gate mirrors Justice byte-for-byte** and is safe to index: `CountDome` returns 0 on
`not next(dome.labels.Colonist)` **before** it reaches the filter (`:850`), and Justice's own shipped guard
indexes `#obj.labels.Colonist` the same way.

### ⭐ The threshold is read from the game, as BEHAVIOUR — not hard-coded, and not read by field name

Justice's own eval is probed on synthetic domes of 1..200 colonists with every colonist idle **and** homeless,
so the percentage clause is always satisfied and only a colonist-count gate can make it return false; the count
at which it flips false → true **is** its gate, and monotonicity is confirmed either side. That needs no
knowledge of `ScriptAND` / `ScriptCheckLabelCount` field names, follows the developers if they rebalance 10,
and declines if Justice ever loses its guard — because then the precedent this judgment call copies is gone.
Calling these evals is safe: each is a generated script-condition body doing arithmetic on two label arrays,
with no engine call, no allocation and no yield.

**A like already gated is SKIPPED, not double-gated**, and that test is behavioural too — the like's current
eval is called on a dome one colonist below the threshold. False ⇒ a gate is already there (the developers', or
our own earlier pass) ⇒ skip. That makes the pass **idempotent by construction**, which `DataPatch` requires,
and it stands the module down per like the day Paradox ships the same change. When all seven are already gated
the module latches **benign** — the RETIRE signal (`logscan`).

**All or nothing.** If any of the seven is missing, or its `DomeFilter.eval` is not a function, or the precedent
is not as expected, **nothing at all is patched** — a partial application would leave the five factions
inconsistent, which is the very thing this fixes.

### ⭐⭐ THE 1.0.7 BRANCH IS NOT INTERCHANGEABLE, and the dossier above is wrong about one thing

The dossier says all five expressions are byte-identical on 1.0.7. **The expressions are; the like IDS are
not.** On the archived 1.0.7 tree **three** likes are called `JusticeHomeless`:

| 1.0.7 | 1.1.0 | gated? |
|---|---|---|
| `JusticeMovement.lua:123` `JusticeHomeless` | `JusticeMovement.lua:129` `JusticeHomeless` | ✅ |
| `MarsDemocraticParty.lua:102` **`JusticeHomeless`** | `MarsDemocraticParty.lua:107` `UtopiaHomeless` | ⛔ |
| `WorkersParty.lua:128` **`JusticeHomeless`** | `WorkersParty.lua:133` `CollectiveHomeless` | ⛔ |

So 1.1.0 **renamed two duplicate like ids**. Consequences, both handled:
- `UtopiaHomeless` and `CollectiveHomeless` do not exist on 1.0.7, so only 5 of 7 targets are found ⇒ decline.
- More importantly, the precedent check must require **every** like carrying a precedent id to be gated, not
  just the first one `pairs` reaches — otherwise the outcome on 1.0.7 depends on table order. It does, so the
  module declines on 1.0.7 **deterministically**, naming the unguarded duplicate, before a single eval is
  wrapped. ⇒ 1.0.7 players (who run the live pack from the portals, per ck118/ck151) get **no gate at all**,
  which is the fail-closed direction. The desk harness runs that leg **six times** because the first draft's
  outcome was order-dependent.
⭐ That is the §2a branch guard doing its job with no version check anywhere.

### ⛔ A DEFECT IN OUR OWN CORE, FOUND HERE AND FILED — `bugs/C90.md`

A desk leg asked what happens when this module's `Require` fails. Answer: `DataPatch`'s runner re-reads the user
veto before every pass but **never the apply verdict** (`00_Core.lua`'s `run`), and its `OnMsg` handlers are
installed at file scope — so a module whose `apply()` DECLINED would still patch the shipped presets on
`ClassesBuilt` while the entry and the log both read `inactive`. The inverse of F87.
**This module carries the guard** (a module-local `self_check_passed` flag, read by the pass; ⚠️ *not*
`entry.status`, because `run_apply` writes the status only after `apply` returns, so a live Mod Options
re-apply legitimately runs the pass while the status is stale). **`Fix_SaintBlessing` and
`Fix_SinkholeIndestructible` have the same shape and no guard — filed as C90, not fixed here** (the brief's rule:
file it, do not fix it). Desk leg (k2) is the control and the template.

### Save safety (`FIX_POLICY` §3a) — layer 2, inert, and it is the trace vanilla already has

- **Nothing of ours is persisted.** Preset objects are persist **permanents**, keyed
  `Preset:<class>.<group>.<name>` (`CommonLua/Preset.lua:1417-1451`), so a `FactionDef` reached from a save is
  stored by NAME and restored by lookup. The wrapped eval lives only in the preset; removing the mod restores
  the shipped expression at the next load, and the next hourly recalc reads it.
- ⚠️ **One exposure, traced and inert.** `FactionsHolder:RecalcFactionsApproval` stores `likes_data` on
  `g_FactionsHolder`, and each row carries `like = <the FactionLikeDomes object>` (`FactionDef.lua:67`,
  `Factions.lua:685`). That **nested** object is not itself a permanent, so a save serialises it by value —
  `DomeFilter.eval` included. ⭐ **This is not new and not ours:** vanilla's `eval` is a function value on the
  same field of the same object, so every existing save already carries that shape. And **the field is DEAD** —
  nothing in the shipped tree reads `likes_data[*].like`; only `.id`, `.text`, `.value` and `.how_to` are read
  (`Factions.lua:674-676`, `:1169`, `_fixup.lua:2600`). The live evaluator reads the PRESET via `ForEachPreset`,
  never the snapshot, and the snapshot is overwritten every game hour. So a captured copy is never called, by us
  or by anyone; `__unpersisted_function__` (`CommonLua/Core/persist.lua:52-54`) is the backstop, not the
  mechanism.
- **A dislike that disappears fires no notification.** `AddFactionLikeDislikeNotification` is called only for a
  like id **absent from the previous hour's list** (`Factions.lua:672-678`), so a player installing this update
  sees dislikes stop arriving, never a burst. (S4.)
