### C88 — Building Codes skips prefab buildings; the description doesn't say so (P3) `[fixed 2026-09-12: Fix_BuildingCodesPrefab, option 1 + the law's own id (ck150 b); desk-controlled, UNTESTED in play — ck158]`

**Field report (INHERITED — owner screenshot, Steam, 2026-09-08):** "Minor bug with 'Building codes' law in 1.1.0. The
Building codes law does not apply to buildings deployed from prefabs. I assume it is a 'bug', as the law does not
specify prefabs as being exempt."

#### What the code does (SOURCE, game 1.1.0.403908)

- Lax (`Policy_BuildingCodesLax`) and Strict (`Policy_BuildingCodesStrict`) apply their maintenance change in a
  `ConstructionComplete` message reaction: `bld:SetModifier("maintenance_resource_amount", …, maintenance_change)`
  (`Data/LawDef/LawDef-Efficiency.lua:696-706` Lax, `:904-914` Strict), with `maintenance_change` +50 (`:688-689`) and −30
  (`:896-897`).
- **Both handlers open with `if from_prefab then return end`** (`:700`, `:908`).
- The flag: `local from_prefab = self.prefab` (`Lua/Buildings/ConstructionSite.lua:1729`), passed as
  `Msg("ConstructionComplete", bld, dome, from_prefab)` (`:1786`), declared in `Data/MsgDef.lua:280`, and also forwarded
  to a story-bit trigger (`Data/Trigger.lua:11`). INHERITED: the flag and both laws are new in 1.1.0 (1.0.7 had only the
  old cost-only law, now `Obsolete`).
- The descriptions promise "new buildings need <50%> more maintenance" (`:692`) / "<30%> less maintenance" (`:900`) — no
  prefab exception.
- The cost half has nothing to act on for a prefab, which pays no construction cost (INHERITED: a supplied site requests
  no resources, `ConstructionSite.lua:696-710`).

#### Effect (INFERRED from the lines above)

- **Strict:** prefab buildings miss the promised −30% maintenance — a LOSS against the law's text.
- **Lax:** prefab buildings avoid the +50% maintenance — a GAIN against the law's text.

#### Why a candidate, not a defect

The exemption is written explicitly, in the same update that added the laws — a deliberate developer choice that the
description doesn't disclose. Whether it is intended is Paradox's to say (`FIX_POLICY` §4: only unintended defects).
The owner (2026-09-11): a prefab is "just a basic buildable building that's packaged and shipped from Earth … so it
shouldn't be treated differently".

#### Waiting on the devs — what each answer means

- The owner is posting the code reading and the question in the reporter's Steam thread, where a PDX developer is active
  (text: `docs/FIELD_REPORT_REPLIES.md`, "Building codes vs prefabs").
- **"Intended"** → `wontfix` here; the gap is theirs to close in the description.
- **"Not intended"** → the owner's call between (1) matching the text for both laws (drop the exemption) and (2)
  repairing only Strict's loss. The implementation route (wrapping a LawDef preset's `MsgReaction` handler) is NOT
  explored.
- **No answer** → stays `cand`; revisit at the next release planning.

#### The devs' answer (2026-09-11) — "Not intended"

Owner screenshot, the reporter's Steam thread, post #7, `ivanassen [developer]`, verbatim:
> "Excluding prefabs is wrong, and will be fixed in the next patch - until then, please include it in your mod."

- **Status:** the exemption is a confirmed defect (the developer's word), so `FIX_POLICY` §4's "intended?" question is
  answered. The owner still picks the shape (checklist 150): (1) drop the exemption for both laws, which matches the
  developer's wording and their coming patch (recommended), or (2) repair only Strict's loss.
- **When built:** their next patch fixes the same thing, so the module must stand down on its own by a behaviour probe
  (`FIX_POLICY` §2a), e.g. the handler no longer exiting on a prefab building. It must never be a version check. The route
  (wrapping a LawDef preset's `MsgReaction` handler) is still NOT explored.
- The same post says they are merging the pack's fixes into the game, could not reproduce F37 (see F37's 1.1.0 section),
  and asked where we collect our bugs (reply draft: `docs/FIELD_REPORT_REPLIES.md`).

## 2026-09-12 — BUILT: `Code/Fix_BuildingCodesPrefab.lua` (owner ruling, checklist 150 (b) = option 1)

Built from `prompts/C85_C88_BUILD.md` and `prompts/C88_PREFAB_BUILD.md` (both now consumed). Shape = **option 1**:
both laws apply to prefab buildings, Lax's +50 % and Strict's −30 %, exactly as their text says and as the
developer said they will ship it. Modifier id = **the law's own id**, also per the owner's ruling.

**Shape.** An additive `OnMsg.ConstructionComplete` (`FIX_POLICY` §1 technique 2) that fires only when
`from_prefab` is truthy, then mirrors vanilla's three conditions per law — `ActiveLaws[law_id]`,
`IsKindOf(bld, "RequiresMaintenance")` — and calls
`bld:SetModifier("maintenance_resource_amount", law_id, 0, law:GetParameterValue("maintenance_change"), law.display_name)`.
⛔ 50 and −30 are never hard-coded; both are read from the preset's own `Parameters`, so a rebalance or another
mod's edit is respected. Costs a live game one truthiness test per completed building.

**Why additive and not a preset edit** (the registration semantics, re-confirmed on the shipped bodies): a
preset's handlers are registered **by function reference** — `RegisterMsgReactions` walks `self.msg_reactions` and
calls `RegisterMsgReaction(self, reaction.Event, reaction.Handler)` (`CommonLua/Reactions.lua:130-137`), which
appends the instance and handler into `MsgReactions[event_id]` (`:469-479`). Editing
`LawDefs.Policy_BuildingCodesStrict.msg_reactions[1].Handler` afterwards changes nothing, and re-registering means
`ReloadMsgReactions()`, which rebuilds the table for every preset in the game — far too wide, and not something
the owner was asked to accept. Vanilla's handler is meanwhile a verified no-op for exactly our case (it returns at
`:700`/`:908` when `from_prefab`), which is the shape §1's technique-2 note describes.

### ⭐ It degrades to nothing when Paradox ships their fix — measured, not argued

`Modifiable:SetModifier` is keyed by `(id, prop)`: it finds an existing modifier by id and, when the amounts are
unchanged, takes neither the change nor the add branch and does **nothing at all**
(`Lua/Modifiers.lua:181-204`). Both handlers write the same id, prop and value, so whichever runs second is a
no-op. ⭐ Desk leg **(f4)** drives this with the **real shipped `SetModifier` body**, not a stub: with vanilla's
repaired handler AND ours both running on the same prefab, the building ends with **one** modifier and **one**
modifier write.

⚠️ **The cost of the law's id, stated because it is real.** Our modifier is then indistinguishable from
vanilla's, so the uninstall / save-rescue path (D13) cannot identify it as ours. The owner accepted that in
exchange for repeal and the shipped savegame fixup treating it as the game's own. The alternative — our own id —
would **stack** with vanilla's once their patch lands (two ids, double effect), a player-visible harm and the same
failure shape as F-2. Desk variant `v5_own_id` fails legs (b) and (b2), so the ruling is enforced by a leg.

### ⛔ BUILDINGS ALREADY STANDING CANNOT BE REPAIRED — and no heuristic is attempted

`from_prefab` occurs in exactly eight places in the whole tree (the two handlers, `Data/MsgDef.lua:280`,
`ConstructionSite.lua:1729`/`:1786`, `Data/Trigger.lua:11`) and **nothing stores it on the finished building**, so
a building already up cannot be identified as prefab-deployed. Guessing from shape, template or missing
construction cost would silently change maintenance on buildings the law never touched. ⇒ **The fix applies to
buildings completed after it is installed.** That is a scope statement, not a hedge, and it is stated in this
entry, in the outbox entry and in the reply draft.

### S1 ANSWERED — vanilla LEAKS this modifier on repeal, and it is filed as `bugs/C91.md`

The brief's open question was what removes the maintenance modifier when the player repeals the law. **Nothing
does.** Each law's **cost** half is a `LawEffectModifyLabel` with an `OnStop` and is reverted; the **maintenance**
half is the `MsgReaction` above, and a `MsgReaction` has no stop hook. Every `OnMsg.LawDeactivated` handler in the
tree was enumerated — `Laws.lua:463` (approval only), `Laws.lua:393`/`:884` (debug asserts),
`Legislature.lua:425` (governing law + Efficient Assembly queue) — and none touches
`maintenance_resource_amount`. The only clear-down in existence is the **one-shot**
`SavegameFixups.RemoveRepealedBuildingCodesMaintenance` (`Laws.lua:465-473`), whose very existence says the
developers met this leak in the field and swept it rather than fixing repeal.

⇒ **Filed as C91 and the build CONTINUED**, which is what the brief directs once the id is the law's: because our
modifier carries the **law's own id**, it leaks exactly as vanilla's does and is cleared by exactly the same
fixup — one more building inside an existing leak, never a new kind of leak. Had we used our own id we would have
created a second, unswept leak.

### ⛔ TWO BUGS THIS MODULE ACTUALLY HAD, both caught at the desk, both now leg-covered

Recording them because each would have shipped a silently dead module and the first harness draft passed both.

1. **`GameVar` reads `false`, not `nil`.** `GameVar(name, value)` rawsets the global to **false** at declaration
   and `OnMsg.DoneGame` sets it back to false (`CommonLua/Core/lib.lua:1061-1093`). `ActiveLaws` is a GameVar
   (`Legislature.lua:1`), so at the menu it is `false`. The first draft's "no game loaded" test read `~= nil`,
   which is **true** there — the probe would have declined and **the module would have gone inactive on every
   single boot**. The test is now `nil or false`; variant `v7_nil_not_false` fails five legs.
2. **The branch guard must not run at apply time (the F75 lesson).** A preset GlobalMap is present but **empty**
   before `DataLoaded`, and mod code always loads first on a cold boot — so capturing the two handlers in
   `apply()` would have found nothing and declined on every **cold** boot while working on the enable path. The
   guard now runs from `SMRFixPack.OnDataReady`, fires on the cold-boot, enable and reload paths alike, and is
   idempotent; `apply()` requires only what a game update could remove and that exists at the menu (`IsKindOf`,
   `IsValid`, `Modifiable.SetModifier`/`FindModifier`), with `ActiveLaws` deliberately **not** a `Require` entry
   (the F110 rule). Variant `v8_guard_at_apply` fails five legs.

⚠️ The first harness draft modelled `ActiveLaws = nil` and populated `LawDefs` **before** loading the module, and
so passed both bugs. It now models the real menu value and the real cold-boot order.

### Branch guard (`FIX_POLICY` §2a) — a real behaviour probe, no version check

The probe **calls the shipped handler** with `from_prefab = true`. Safe and complete: the body's first statement
is `if from_prefab then return end`, so the call is one comparison and a return — no global read, no allocation,
no yield. And it **discriminates**, because `ActiveLaws` carries no law table while no game is loaded:

* shipped shape → returns at the first line, never reaching `ActiveLaws`: clean.
* their patch → the exit is gone, so it reaches `ActiveLaws[self.id]`, indexes a non-table and **throws**. A
  throw is a decline, so the module stands itself down and logs "already correct, RETIRE candidate".

⚠️ When a game **is** already loaded the probe cannot discriminate, so the module stays **undecided** rather than
banking a verdict either way, and an undecided guard is not permission — the handler applies nothing (legs (h),
(h2)). In practice the first firing is always at the menu.

### Manifest (`FIX_POLICY` §2b)

`SRC: none` + `DEFECT@Data/LawDef/LawDef-Efficiency.lua: if from_prefab then return end` (two occurrences, Lax and
Strict). ⭐ **That pin is this module's retirement signal**: `bodycheck` prints DEFECT-GONE the day Paradox's patch
removes the prefab exit, which is the day this module should be **deleted**, not merely stood down. `bodycheck`
2026-09-12: 1 SRC-NONE, 1 OK.

### Save safety (`FIX_POLICY` §3a) — layer 1 for us

One synchronous `OnMsg` handler. No thread, no persisted field of ours, no new GameVar, no function value stored
anywhere. The only write is a modifier under the **game's own id**, which the game already writes for every
non-prefab building under that law. SAVE FOOTPRINT: none of ours — see C91 for vanilla's.
