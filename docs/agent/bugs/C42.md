### C42 — Passage traversal clears `unit.holder` directly, leaving a permanent stale entry in a passage element's `units`  `[filed 2026-08-03 by the F11/F99 chain (prompt 1) — cand, source-only, unobserved, nothing built]`

**How it was found.** Not by looking for it. Point 8 of the F11 second-opinion
derivation asked for an enumeration of everything that can desync a `Holder`'s
`units` list from its members' `holder` field. The search was
`grep -rn "\.holder = "` across `Lua/` and `CommonLua/` — four hits, of which
three are benign (`Colonist.lua:4305` only clears an already-invalid holder,
`Train.lua:390` is the train's own holder, `SurfaceDeposit.lua:154/426` is an
unrelated field). This is the fourth, and it is not benign.

**The defect.** `PassageBase:TraverseTunnel` — `Lua/Passage.lua:1037-1066`:

```lua
unit:PushDestructor(function(unit)
	...
	while IsValid(self) and element_idx >= 1 and element_idx <= #self.elements do
		el = self.elements[element_idx]
		element_idx = element_idx + step
		local entrance = el:GetEntrance(unit, "passage_entrance")
		el:LeadIn(unit, entrance)
	end
	unit.holder = nil --last el would be holder, no need to exit we are already out
	...
end)
```

The comment is the author telling you exactly what they did and why they thought
it was safe: the unit is physically out of the passage, so no exit sequence is
needed. **But `holder` is not just a position — it is one half of a two-way
link.** The engine's only maintainers of the other half are
`Holder:OnEnterHolder` / `OnExitHolder` (`Lua/Buildings/Holder.lua:27-41`), and
both are reached **only** through `Unit:SetHolderOnMap` (`Lua/Units/Unit.lua:702-717`):

```lua
if holder then holder:OnExitHolder(self) end     -- table.remove_entry(self.units, unit)
self.holder = building
```

A raw `unit.holder = nil` skips that call. **The last element's `units` list keeps
the colonist in it, and nothing ever removes them.**

**Why it is not cosmetic.** `Holder:Done` → `Holder:KickUnitsFromHolder`
(`Holder.lua:6-25`) walks `self.units` when the element is destroyed:

```lua
assert(IsValid(unit), "(Shielded) Something went wrong. Units should not be invalid")
assert(unit.command_thread ~= cur_thread or IsKindOf(self, "ElevatorBase"), "Probable destructor interuption")
if IsValid(unit) then
	unit:KickFromBuilding(self)
end
```

`Unit:KickFromBuilding` (`Unit.lua:276-286`) then does `Detach`, `ClearPath`,
`SetPos(building:GetImmediateExitPos(...))`, `SetHolder(false)` and
`SetCommand("Idle")` — **on a colonist who walked through that passage at some
arbitrary earlier point and is now somewhere else entirely.** Player-visible
shape: demolish or destroy a passage, and unrelated colonists teleport to it and
drop whatever they were doing. Both asserts fire on the way.

Note the `ElevatorBase` exemption in the second assert: the engine already knows
this class of destructor interaction is delicate and carved out one case. Passage
elements did not get the carve-out; they got a raw assignment instead.

⚠️ **The honest limits — this is a reading, not an observation.**

1. **Unobserved.** No log line, no player report, no reproduction. It is filed
   because chain rule 3 says route rather than drop, and because the mechanism is
   the same one F11 exists for.
2. **One untraced link.** The claim depends on `el:LeadIn(unit, entrance)`
   actually setting `unit.holder = el` (which is what the comment "last el would
   be holder" asserts). `LeadIn` was **not** traced through to a `SetHolder`
   call. If `LeadIn` does not set the holder, there is no stale entry and this
   row is void. **That is the first thing to check and it is cheap.**
3. **Lifetime unknown.** If passage elements are rarely destroyed while a colony
   is running, the impact is near-zero even if the mechanism is exactly as
   described. Nobody has counted.

**What would settle it.** A console read on a live colony after some passage
traffic:

```lua
*r local a=0 for _, c in ipairs(Cities) do for _, p in ipairs(c.labels.Passage or empty_table) do for _, el in ipairs(p.elements or empty_table) do for _, u in ipairs(el.units or empty_table) do if u.holder ~= el then a=a+1 end end end end end ConsolePrint(print_format("C42STALE", a))
```

Non-zero confirms the desync exists. Then demolish that passage and watch whether
an unrelated colonist teleports.

**Not ours.** Vanilla `Lua/Passage.lua`; no pack code involved. **Nothing built**
— it is `cand`, and FIX_POLICY §4a (WHO BENEFITS) is not yet satisfied because
the harm is inferred rather than seen.

**Adjacent to** [F11](F11.md) — the same desync class on a different `Holder`.
F11's guard is what the engine does when it *finds* a stale `units` entry; this
is shipped code *creating* one.
